# 任务：把现有串行批处理改造成"零依赖本地批处理管线"

## 背景与硬约束（务必遵守）
这是一个本地运行的日文知识库 ingest 项目。当前批处理是 `kb_admin/services.py` 的 `upload_files()` 在一次上传请求里同步串行调用 `_ingest_file()`，状态写在 `data/kb_admin/*.json`，前端轮询显示进度。现在要改造成稳、可续跑、可并行的本地管线。

**绝对约束：**
- 只能用 Python 标准库 + 项目已安装的包（PaddleOCR、paddlepaddle、Azure AI Search SDK）。**禁止 pip 安装任何新依赖**（机器断网、PyPI 和网页都被公司系统 blocked）。因此不许引入 Redis / RQ / Celery / Huey 等。
- **绝对不要删除或改动 PaddleOCR 模型缓存目录**（断网无法重下）。
- 运行环境是 Windows，多进程用 spawn，务必遵守下面的 spawn 规则。
- Azure AI Search 是现有的检索/向量库，继续用它写索引，不要换。
- 目标：POC 和上线用同一套代码，稳定、可恢复、成本为 0。

## 需要实现的改造（按顺序）

### ① 用 SQLite 取代 JSON 状态存储
- 新建一个 `kb_admin/state_store.py`，用标准库 `sqlite3`，开 `PRAGMA journal_mode=WAL`。
- 建表 `files`：`id, batch_id, path, file_hash(UNIQUE), status(pending/processing/completed/failed/dead), attempts, error, updated_at`；建表 `batches`：`batch_id, file_count, status, created_at`。
- 提供函数：`enqueue_files(batch_id, paths)`、`claim_pending(limit)`、`mark(status, file_id, error=None)`、`batch_progress(batch_id)`。
- 保留 `json_store.py` 的对外接口签名不变，内部改成读写 SQLite（或加一层适配），让上层 `services.py` 改动最小。

### ② 抽象 OCRProvider 接口
- 新建 `kb_poc/parsing/ocr_provider.py`，定义抽象基类 `OCRProvider`，方法 `recognize(image_path: str) -> list[TextBlock]`（**只接收文件路径，不接收 PIL/ndarray**，为多进程 pickle 和之前的稳定性修复服务）。
- 实现 `LocalPaddleProvider`：内部持有一个 PaddleOCR 实例（`lang='japan'`, `use_angle_cls=False`, `cpu_threads=1`）。
- **关键：修复之前 PP-Structure 与 PaddleOCR 抢实例导致的崩溃**——每个 Provider 实例在构造时只初始化它需要的那一个引擎，全生命周期复用，绝不在每张图/每个变体里重新 new。
- 上层 `ingestor.py` / `ppt_ocr.py` 改成只依赖 `OCRProvider` 接口，不直接 new PaddleOCR。

### ③ 新增独立 worker 进程
- 新建 `kb_admin/worker.py`，作为**独立启动的脚本**（不在 web 服务进程里跑）。
- 用 `concurrent.futures.ProcessPoolExecutor(max_workers=8, initializer=init_worker)`；`init_worker()` 在每个子进程里创建一个 `LocalPaddleProvider`（8 进程 × cpu_threads=1，匹配 10 物理核）。
- 主循环：从 SQLite `claim_pending(8)` 取任务 → `submit(process_one, path)` → `as_completed` 回收结果 → 成功则切片 + 写 Azure AI Search + `mark('completed')`；异常则 `attempts+1` 并 `mark('failed', error=...)`；`attempts >= 3` 的转 `dead`（死信）。
- **每个文件的处理必须包在 try/except 里，单文件失败绝不中断整批。**
- 幂等：处理前用 `hashlib` 算文件哈希，已 `completed` 的哈希直接跳过。
- 续跑：worker 重启后自动只捞 `pending` 和 `attempts<3` 的 `failed`，已完成的不重跑。

### ④ 上传接口改成"入队即返回"
- 改 `kb_poc/ui/api_admin.py` 的 `/api/admin/upload` 和 `kb_admin/services.py` 的 `upload_files()`：收到文件 → 保存 → 算哈希 → `enqueue_files()` 写 `pending` → **立即返回 batch_id（HTTP 202）**，不在请求里做 OCR。
- 状态接口 `/api/admin/batches/{batch_id}` 改成从 SQLite 用 `batch_progress()` 计数返回（completed/failed/pending/dead + current）。前端 `modern_chat_page.js` 的轮询逻辑基本不动。

### ⑤ Azure AI Search 写入健壮化
- 改成**批量上传** chunk（而非一条条），遇到 429/503 用指数退避重试。

## Windows + 多进程（spawn）硬性规则
- `init_worker` 和 `process_one` 必须是**模块顶层函数**，不能是闭包/lambda。
- 传给子进程的参数**只能是文件路径字符串**等可 pickle 对象，不要传 PIL 图、ndarray、OCR 实例。
- worker 启动代码放在 `if __name__ == "__main__":` 下。

## 验收标准
- 一次上传上百个文件，请求秒返回 batch_id，OCR 在后台跑。
- 全程只有 8 个 OCR 实例（每进程一个），不再每张图新建实例。
- 单个坏文件失败只标记该文件，不中断整批；失败满 3 次进 `dead`。
- 中途 kill 掉 worker 再重启，能从未完成处续跑，已完成的不重复处理、不重复写 Azure。
- 不新增任何 pip 依赖；不触碰 PaddleOCR 模型缓存。
