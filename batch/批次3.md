# 任务：批处理第三批「体验优化」（流式上传 + 预扫描拆子批 + 先文本后 OCR）

## 背景与约束
在第一、二批（止血 + 护栏）完成基础上做体验优化，不牺牲已有的稳定性。只用标准库 + 现有依赖，禁止新增 pip 包；Windows；先输出计划和 diff，确认后再实现。

## 改动 1：流式上传（上传不占内存）
- 改上传接口（/api/admin/upload）：接收文件时**分块流式写入磁盘**，不要把整个请求体/整个文件读进内存（避免 await request.body() / read() 全量）。
- 用框架的流式方式逐块写盘（如逐块 read 后 write，或 shutil.copyfileobj）。
- 目的：一次传很多/很大的文件时，上传阶段内存不飙升。

## 改动 2：预扫描 + 拆子批（进度更平滑、内存更可控）
- 一次上传后，先做一次轻量预扫描：统计文件数、总大小、重文件个数（复用第二批的重量估算，不做实际解析）。
- 把大批次拆成若干子批（如每子批 N 个文件或按总重量切分），按子批依次投递处理。
- 前端进度按"子批 x/共 y + 当前子批内进度"展示，让用户看到稳定推进而不是一个长条卡很久。
- 目的：大批量时进度可预期、内存分摊，不会一次性把几百个文件全压进来。

## 改动 3：先文本后 OCR（分两阶段，文档更快可用）
- 对 PPT/Excel/PDF 采用两阶段处理：
  1. 阶段一：先抽取原生文本（快、省），立刻切片 + 写 Azure AI Search，使该文档**尽快变得可检索**，状态可标 text_done。
  2. 阶段二：再对内嵌图片跑 OCR，补充/更新该文档的 chunk，完成后标 completed。
- 阶段二可作为后续任务排队，不阻塞阶段一；OCR（重、易出问题）被隔离在第二阶段。
- 目的：文档上传后很快就能被问答检索到（先有文本），OCR 慢慢补齐；也把最耗时/最易崩的 OCR 单独隔离，感知延迟大幅下降。

## 验收标准（请给出验证步骤）
1. 上传大文件时上传阶段内存平稳（确认是流式写盘，无全量读入）。
2. 大批量上传时前端显示"子批 x/y"平滑推进，内存分摊。
3. 传一个含大量图片的 PPT：先文本阶段完成后该文档即可被问答检索到，之后 OCR 阶段完成再补齐图片内文字。
