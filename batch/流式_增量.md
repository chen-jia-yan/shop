# 任务：把 chunk 构建改成"流式/增量"，让内存峰值与文件大小脱钩

## 背景
现有子进程处理（process_one / 重文件的 process_one_file）里，build_chunks_for_stage() / write_chunk_batches() 会**一次性把整份 List[DocumentChunk] + 全部 embedding + metadata 驻留在内存**再写出。大文件在这里内存峰值过高 → 原生崩溃(0xc0000005)。索引侧已是流式（begin/append/finalize），但**生产侧（构建+embedding）还是全量驻留**。本任务把生产侧也改成流式。

## 目标
按"文档的自然单元"逐块处理并立即落盘释放，使子进程内存峰值≈单个单元+一个 embedding 批的大小，**与文件总大小无关**。

## 硬约束
- 只用标准库 + 现有依赖，禁止新增 pip 包；Windows；不改 chunk 内容/字段、不改 chunk_id 生成规则（doc_id+hash+序号，保持幂等）；不破坏两阶段状态机与索引 begin/append/finalize。先输出计划和 diff，我确认后再实现。

## 具体改造
1. 把文档来源改成**按自然单元迭代的生成器**：PPT 按页/张、Excel 按 sheet（或按行块）、PDF 按页、其他按段/按 N 个 chunk。用 yield 逐个产出，不要一次性把整份文档/全部页读进内存。
2. 对每个单元执行"**构建 → embedding（分批，沿用 EMBED_BATCH）→ 追加写 JSONL → 释放**"的循环：
   ```
   for unit in iter_document_units(path, phase):     # 生成器，逐单元
       chunks = build_chunks(unit)                   # 只这一单元
       embs   = embed_texts(chunks, batch=EMBED_BATCH)
       append_jsonl(out_path, chunks, embs)          # 立即落盘（追加）
       del chunks, embs                              # 显式释放，进入下一单元
   ```
3. **任何时刻都不得**在内存里同时持有：整份 List[DocumentChunk]、整份 embedding、或整份待写 JSONL 列表。JSONL 一行一条、追加写、定期 flush。
4. OCR 也要逐图/逐页处理：不要一次性把大文件里所有图片解码进内存；每张图 OCR 完即释放。
5. 轻文件路径（共享池 process_one）和重文件路径（process_one_file）**复用同一套流式构建函数**，避免两份逻辑。
6. 索引侧维持现有 begin/append/finalize，消费这份增量 JSONL，不变。

## 验收标准（请给出验证步骤）
1. 处理一个很大的文件时，子进程内存**基本平稳、不随文件增大而单调爬升**（对比改造前的内存曲线）。
2. 之前会崩的大文件（如大 Excel）现在能跑完，或内存峰值显著下降、不再触发原生崩溃。
3. 输出的 chunk 内容、数量、chunk_id 与改造前一致（流式不丢数据、不改 id）。
4. JSONL 是在处理过程中逐步增长的（可观察文件大小随处理递增），而非最后一次性写出。
