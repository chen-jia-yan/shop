### 1. `TapIngestClient.__init__` 和 `ingest` 的完整签名；是否需要 `work_dir` 或临时目录；`ingest` 内部是否会写本地文件，写在哪里
结论：
- `work_dir` 不是必填参数，但 SDK 设计上会依赖本地临时目录。
- `TapIngestClient.__init__` 默认把工作目录设到系统临时目录下的 `tap_ingest_sdk`。
- 真正发生本地写文件的代码在 `SourceDocument.resolve_to_path()`：当输入是 `stream` 或 `content` 而不是现成 `path` 时，会把内容物化到 `tempfile.gettempdir() / "tap_ingest_sdk"`（或调用方传入的 `work_dir`）下面。
- 已确认事实：`TapIngestClient` 自己创建了 `self._work_dir`；我的判断：当前这版调用链里 parser 主要走 `materialize_source(source)`，而 `SourceDocument.resolve_to_path()` 的默认落地目录就是系统临时目录 `tap_ingest_sdk`，所以即使不显式传 `work_dir`，仍会写本地临时文件。

### 2. 传入 `idempotency_key` 后，`document_id` 如何得出
结论一句话：传入 `idempotency_key=X` 时，`document_id` 就等于 `X`；只有没传时才退回 `compute_document_id(path)` 生成 `doc::<文件内容SHA256前16位>`。完整调用链：
- `SourceDocument.idempotency_key`
- 各 parser 的 `document_id = source.idempotency_key or compute_document_id(path)`
- `adapt_parsed_document(..., document_id, version_id)` 产出 `ProcessedDocument.document_id`
- `TapIngestClient._ingest_one()` 里把 `document.document_id` 写进 `FileIngestResult.document_id`

### 3. `indexed_count` 和 `chunk_count` 分别怎么计算；Azure 部分写入失败时这两个值是什么
结论：
- `chunk_count = len(document.chunks)`，就是 chunker 切出来的 chunk 数。
- `indexed_count` 不是固定等于 `chunk_count`，而是每个 sink 返回的 `result.indexed_count` 里取最大值：`indexed_count = max(indexed_count, result.indexed_count)`。
- 对 Azure 这条链，通常会接近“最终索引里该文档的 chunk 数”；因为 Azure repository 的 `finalize_document_upsert()` 返回的是 `get_document_chunk_stats(document_id).chunk_count`。
- Azure 部分写入失败时，`_ingest_one()` 会进入异常分支，最终 `FileIngestResult(status="failed")`，不会填 `chunk_count / indexed_count / document_id / version_id`，所以这两个值都保持 dataclass 默认值 `0`。

### 4. 什么情况下返回 `status="skipped"`
结论：
- 只有一种显式 `skipped` 场景：同一批次里某个 markdown 文件引用了一张图片，而这张图片又作为独立 `source` 传进来，且 `skip_referenced_images=True`（默认就是 True）时，这张图片会被跳过。

### 5. `paddleocr` 在哪些文件中被 import；是顶部导入还是函数内部导入；不安装时 `import tap_ingest_sdk` 和 `ParserRegistry.default()` 会不会报错
结论：

## 9.d 重新入库时如何撤销旧关系；prune_orphans 做什么
结论：
- 重新入库时先：
  i. _RETRACT_RELATIONS：把该文档从业务关系边的 doc_ids/chunk_ids 里删掉；如果这条关系边没有别的文档支撑了（weight=0），就删边
  ii. _RETRACT_ENTITIES：把该文档从实体节点的 doc_ids 里删掉
  iii. _DELETE_CHUNKS：删掉该文档旧 chunk 节点及其边
  iv. 然后再写新 Document/Chunk/MENTIONED_IN/业务关系
- prune_orphans() 是额外清理动作：删除当前 scope 下 doc_ids 已空且完全没有任何边的孤儿实体节点。

> ensure_schema=True 时会创建：
> - Entity(scope,id) 唯一约束
> - Chunk(scope, chunk_id) 唯一约束
> - Document(scope, document_id) 唯一约束
> - entity_norm 普通索引
> - entity_label_ft 全文索引
> - 如果开启实体向量，还会创建 entity_embedding 向量索引
> - 因为语句都用了 IF NOT EXISTS，重复执行是安全的。

| /tap/ai/kg/nodes/{node_id} | 部分能。Neo4j Entity 有 id/type/label，但 kg_api 期望 properties 是一个字典；Neo4j 里 Entity 属性能部分映射，但字段名/来源不完全一致。 |
| /tap/ai/kg/nodes/expand | 部分能。Neo4j 本身最适合做 expand，但 kg_api 的返回格式仍要求先转成 NodeData/EdgeData 那套结构。 |
| /tap/ai/kg/nodes/chunks/list | 基本能，但缺页内细节适配。Neo4j 有 (:Entity)-[:MENTIONED_IN]->(:Chunk)，可知道实体关联了哪些 chunk；但 kg_api 还要 source_file/page_or_sheet/label/direction 。其中 source_file 有，page_or_sheet 在当前 Neo4j Chunk 节点没有写进去，这是明确缺项。 |
| /tap/ai/kg/chunks/{chunk_id} | 缺关键字段。Neo4j Chunk 节点有 chunk_id/document_id/source_file，但没有 chunk 正文 content，也没有 page_or_sheet；而 kg_api 这个接口强依赖 chunk_content.csv 和 Chunk.metadata_json.page_or_sheet。 |

总判断：
- 不能直接满足。SDK 写入 Neo4j 的数据，最多只能覆盖 kg_api 8 个接口中的一部分图结构需求。
- 最关键缺口有两个：
  i. 没有 chunk content 正文（kg_api 的 /chunks/{chunk_id} 直接读）
  ii. Chunk 节点没写 page_or_sheet（chunk 列表/详情接口字段不全）
