一、先记住一句话

分层明确、契约先行、类型清楚、注释讲边界、测试重回归、装配集中、默认保守。

可以压成 7 个字来记：层、契、型、注、测、装、守。

字

意思

一句话

层

分层

先想清楚代码属于哪一层，再动手

契

契约先行

核心层只依赖 Protocol（接口），不依赖具体实现

型

类型清楚

Pydantic、dataclass、类型标注，过 mypy

注

注释讲边界

写”为什么、约束、坑”，不翻译代码

测

测试重回归

用假对象隔离外部依赖，测行为、状态和回归场景

装

装配集中

依赖统一在 bootstrap 里创建和组装

守

默认保守

配置有上下限，错误统一包装，不把内部细节返回给前端



二、核心：六层各管什么

一个请求进来会这样走：HTTP 请求

  → api/            薄路由：收参数 → 调服务 → 把结果映射成响应

  → application/    用例编排：串流程、管事务、推进状态

  → core/           纯规则：判断、计算、策略（不碰数据库和 HTTP）

      ↑ 只依赖

    contracts/      Protocol、请求模型、跨层数据结构

      ↑ 实现

    plugins/        外部能力：模型、工具、知识库

    persistence/    Repo 和 ORM：数据库读写

bootstrap.py / container.py：把以上组装起来

最好记的方式是记住每层”不该做什么”：

层

该做

不该做

api

收参数、调服务、映射成 DTO

写业务判断、直接操作数据库

application

编排流程、管事务边界、推进状态

写复杂规则；知道 FastAPI 的细节

core

业务规则、纯逻辑

import persistence、plugins、api、prompts

contracts

定义接口和数据结构

放具体实现

plugins

对接外部服务

被 core 直接 import

persistence

围绕实体做增删改查

塞业务分支



用评估模块对一下，很好理解：

- ‎⁠api/library_eval.py⁠：10 个路由，都是薄壳

- ‎⁠application/library_eval.py⁠ 的 ‎⁠EvalService⁠：编排”建任务 → 后台跑 → 汇总”

- ‎⁠core/library_eval/⁠：判官、分类、汇总，都是纯逻辑，还有架构测试保证它不 import 外层

- ‎⁠contracts/library.py⁠：‎⁠QaAnswerPort⁠ 就是一个”插座”

- ‎⁠bootstrap.py⁠：组装 ‎⁠EvalService(qa_port=None)⁠

这就是依赖倒置：core 只认识 ‎⁠QaAnswerPort⁠ 这个接口，不关心背后是真问答还是测试用的 ‎⁠FakeQa⁠。所以评估模块能在问答还没接上的情况下先写完、先测完。

三、每层怎么写（示意代码）

1. contracts：用 Protocol 定义插座from typing import Protocol

from pydantic import BaseModel, Field

class QaResult(BaseModel):

    answer: str

    evidence: list[EvidenceItem] = Field(default_factory=list)

class QaAnswerPort(Protocol):

    async def answer(self, *, question: str, mode: AnswerMode, top_k: int) -> QaResult: ...

要点：

- ‎⁠Protocol⁠ 是结构化类型，实现方不用继承它，只要方法签名对得上就行。

- ‎⁠*⁠ 后面的参数只能按关键字传，调用时必须写 ‎⁠question=...⁠，参数多了也不容易传错位置。

- 列表默认值要用 ‎⁠Field(default_factory=list)⁠，不能直接写 ‎⁠= []⁠，否则多个实例会共享同一个列表。

2. api：路由是薄壳router = APIRouter(prefix="/tap/ai/library/eval", tags=["library-eval"])

@router.post("/runs/add", response_model=EvalRunStartData)

async def add_run(req: EvalRunAddRequest, svc: EvalService = Depends(_service)):

    result = await svc.start_run(req)

    return EvalRunStartData(run_id=result.run_id, status=result.status)

要点：路由里只有”收参数、调服务、映射 DTO”三步，没有任何 ‎⁠if⁠ 业务判断。

3. application：显式注入依赖，用早返回做校验class EvalService:

    def __init__(self, *, settings, session_factory, prompt_library,

                 model_gateway, qa_port: QaAnswerPort | None = None) -> None:

        ...

    async def start_run(self, req: EvalRunAddRequest) -> EvalRunStartResult:

        if self._qa_port is None:

            raise BusinessError("问答服务未配置")

        if not self._settings.library_eval_judge_model:

            raise BusinessError("判官模型未配置")

        ...

要点：所有依赖都从构造函数传进来，不用全局单例；校验失败立刻返回或抛错，减少嵌套。

4. 事件和状态：结构化表达@dataclass(frozen=True)          # 不可变，事件发出后不能被改

class ChatEvent:

    type: ChatEventType          # 用 Enum 或 Literal，不散落魔法字符串

    data: dict[str, Any]

5. persistence：Repo 只管读写，事务交给调用方决定def update(self, run_id: str, *, status: str, commit: bool = True) -> int:

    """按 id 更新状态；软删除的记录不会被更新。返回受影响行数。"""

    ...

    if commit:

        session.commit()

‎⁠commit: bool = True⁠ 让外层可以把多个操作放进同一个事务。比如评估模块建 run 和建所有 item 是在一个事务里完成的。

6. config：配置就是契约class Settings(BaseSettings):

    model_config = SettingsConfigDict(env_prefix="TAP_AI_")

    library_eval_max_concurrency: int = Field(default=2, ge=1, le=8)  # 防止把模型网关打爆

‎⁠ge⁠ / ‎⁠le⁠ 限制取值范围，配错值启动时就会报错，不会等到运行时才出事。

7. 错误处理：分类处理，不外泄内部信息raise BusinessError("评估集不存在")   # 全局处理器统一转成 HTTP 200 + {"code": "CCB001", ...}

还有两个异步场景里的硬规矩：try:

    ...

except asyncio.CancelledError:

    raise                         # 取消信号绝不能吞掉

except Exception as exc:  # noqa: BLE001 - 单题失败不能影响整个任务

    await self._fail_item(item, f"{type(exc).__name__}: {exc}"[:2000])

8. 测试：用假对象，测行为@dataclass

    result: QaResult

    calls: list[str] = field(default_factory=list)

    async def answer(self, *, question, mode, top_k):

        self.calls.append(question)

        return self.result

async def test_判官收到的证据就是问答返回的证据():

    ...

    assert gateway.messages[-1] 包含 fake_qa.result.evidence 的内容

测试函数名直接写”场景_预期结果”，断言要验证的是行为（证据有没有原样传给判官），而不只是”没报错”。

四、用评估模块看”违反风格”的例子

拿上一轮看到的问题对照这份风格文档，印象会更深：

评估模块里的问题

违反了哪条

‎⁠application⁠ 直接 import ‎⁠persistence⁠

层：应该通过 Repo 或 port 注入

badcase 分析的 user 提示词写死在 ‎⁠analyzer.py⁠

契：提示词应该放进 prompts/，经 PromptLibrary 取用

‎⁠EvalAnalysisData⁠ 漏了 ‎⁠llm_analysis⁠ 字段

api 层的映射不完整，DTO 和服务层不一致

‎⁠classify()⁠ 调用时少传了 answer、evidence

输入是随手拼的 dict，没有用结构化对象；改用 dataclass 的话，类型检查就能发现漏传

mypy 报 ‎⁠CursorResult⁠、‎⁠min(key=dict.get)⁠

型：类型没标严

改完代码不跑测试就算完成

测：这份文档特别提到要警惕”0 个测试”“只收集没执行”这类假通过



第 4 行最值得记：用 ‎⁠dict[str, Any]⁠ 在层与层之间传数据，是这类 bug 的根源。项目风格要求”先建清晰的数据对象”，正是为了防这种问题。

五、要掌握的知识（按优先级）

必须掌握（直接决定能不能写对）

1. Python 类型标注：‎⁠str | None⁠、‎⁠list[str]⁠、‎⁠Callable⁠、‎⁠AsyncIterator⁠、‎⁠Literal⁠、‎⁠Protocol⁠；会读懂并修 mypy 报错，比如 ‎⁠cast⁠ 的用法。

2. Pydantic v2：‎⁠BaseModel⁠、‎⁠Field(ge, le, default_factory)⁠、‎⁠field_validator⁠、‎⁠BaseSettings⁠、‎⁠AliasChoices⁠。

3. asyncio：‎⁠async⁠/‎⁠await⁠、‎⁠create_task⁠ 要保留任务引用（否则可能被垃圾回收）、‎⁠wait_for⁠ 超时、‎⁠Semaphore⁠ 或 worker 控制并发、‎⁠CancelledError⁠ 必须往外抛、‎⁠finally⁠ 里释放资源。

4. FastAPI：‎⁠APIRouter⁠、‎⁠Depends⁠、‎⁠response_model⁠、全局异常处理器、lifespan 启动和关闭钩子。

5. 分层和依赖倒置：能判断一段代码该放在哪一层，理解为什么 core 只依赖 contracts。

6. pytest + 假对象：手写 Fake 类、用 ‎⁠pytest-asyncio⁠ 测异步代码、在 ‎⁠conftest.py⁠ 里放公共夹具、隔离 ‎⁠.env⁠。

应该掌握（写出”像这个项目”的代码）

7. SQLAlchemy 2.0：‎⁠Session⁠、事务边界、‎⁠rowcount⁠ 判断更新是否成功、软删除、分页时保证排序稳定、模糊查询要转义 ‎⁠%⁠ 和 ‎⁠_⁠。

8. dataclass：‎⁠frozen=True⁠、‎⁠field(default_factory=...)⁠，以及什么时候用 dataclass、什么时候用 Pydantic（内部数据用 dataclass，需要校验的边界数据用 Pydantic）。

9. Enum 和状态机：把状态显式列出来，明确写出状态之间的流转（参考评估模块的 queued → running → succeeded/failed/cancelled/interrupted）。

10. ruff + mypy：行宽 88，import 分组，知道 ‎⁠noqa⁠ 什么时候能用、必须写明原因。

11. 流式响应 / SSE：模型网关的流式输出要用 ‎⁠async for⁠ 拼接，结束后关闭流；要处理”终帧”和断线。

可以扩充（加深理解）

12. Ports & Adapters（六边形架构）、轻量 DDD：这个项目的骨架就是这两种思路。

13. 幂等、原子更新：比如 ‎⁠increment_progress⁠ 用 SQL 里的原子加法，不先读再写，避免并发下计数丢失。

14. 可观测性：Langfuse 记录模型调用，日志里带上 trace_id。

15. 多实例部署的问题：心跳、过期任务回收、任务队列，也就是评估模块”断了不能续跑”背后的知识。

六、写代码前的自检清单

1. 这段代码属于哪一层？有没有 import 不该 import 的东西？

2. 需要依赖外部能力吗？如果需要，先在 contracts 里定义 Protocol，再到 bootstrap 里注入。

3. 层与层之间传的是结构化对象，还是随手拼的 dict？

4. 错误是用 ‎⁠BusinessError⁠ 返回固定错误码，还是把原始异常直接漏给前端？

5. 异步代码有没有吞掉 ‎⁠CancelledError⁠？有没有设超时？

6. 新加的配置有没有默认值、上下限，有没有写注释说明为什么这样定？

7. 注释写的是”为什么、约束、坑”吗？

8. 测试有没有用假对象？断言验证的是行为和状态吗？测试真的执行了吗（要看到 passed 的数量，不能是 0）？

9. ruff 和 mypy 都过了吗？
