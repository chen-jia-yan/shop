评估板块不用大改。整体框架是对的：任务表、后台执行、心跳、取消、恢复、判官都没问题。毛病集中在两处：一是数据没传全，二是接口没把结果完整返回给前端。改 7 处小地方，再加一个问答适配器，就能把整条链路跑通。完整报告已经在新标签页打开，里面有改动示意代码、接口字段表和逐条验证用例。下面的代码示意都是根据导览和《后端评估》写的，我没看过实际代码。

1. 要修的地方（按建议顺序）

1. 分类缺输入（library_eval.py:421-430）：分类时补上答案、证据和”判官输出是否解析失败”。根据导览里的规则推断，现在分类看不到证据，所以很可能把正确性低于 3 分的题都判成”没检索到内容”。最好把输入改成一个固定结构的数据对象，以后再漏传，类型检查能直接报出来。

2. badcase 分析缺输入（:614-623）：同样补上答案和证据，过长的内容要截断。分析时直接用库里存好的分类，不要再重新算一遍，保证两处结果一致。

3. 前端拿不到大模型分析结果：分析接口的返回结构（EvalAnalysisData）里加上 llm_analysis 字段，字段要写成明确的结构，前端才好渲染。

4. 判官调用没有超时：加上超时。不然模型网关卡住时，这道题会一直挂着，心跳却照常更新，任务永远结束不了。

5. 按 id 查询的 3 个接口没校验租户：加上 saas_id 校验，否则拿到别的租户的 id 就能读到对方的数据。

6. 判官模型没配置时：保持报错，不要退回用默认模型。默认模型很可能就是被测的问答模型，等于让它给自己打分。

7. 分析用的 user 提示词还写死在代码里：挪到 prompts/ 目录。

8. 新增问答适配器，分两步：先写一个只在开发环境打开的测试用适配器，按题目前缀 [empty]、[miss]、[error]、[slow] 返回不同结果，然后再写接真实问答的适配器。

2. 给前端的接口字段

- 报告里有 10 个接口的请求字段、返回字段和前端用法，还有所有枚举值，以及什么时候停止轮询。列表接口的筛选字段是我根据导览推断的，要以 Swagger 为准。

- 最需要趁现在定下来的一点：runs/add 返回的是 run_id，查询任务详情返回的却叫 id。建议对外统一叫 run_id，前端还没接，现在改没有成本。

- 交给前端时，直接给 /openapi.json，不用另写一份字段文档。每个字段写上说明和示例，前端可以直接生成类型。

3. 只用 Swagger 和后端怎么验证

- 关键就是上面那个测试用适配器。真实问答还没接上，但每种问题分类和每条出错路径都能人为触发。

- 我设计了一个 7 道题的测试评估集和 20 条用例，覆盖参数错误、发起、进度、每种分类、超时、取消、中断、跨租户访问，以及前面每个修复点。

- 有些结果要到数据库里看，比如进度计数和明细对不对得上、题目快照有没有存下来。报告里附了查询语句。

- 有几项 Swagger 测不到，要单独确认：

  - 跨域：Swagger 和后端在同一个域名下，测不出前端会不会被拦。

  - 前端实际走的网关地址和登录 token。

  - 生成的前端类型和后端字段是否一致。

  - 多实例部署下取消能不能生效。
