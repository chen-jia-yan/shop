## 一、K9 安装方式：我的推荐
先说结论： 首选公司私有包仓库（比如 Azure Artifacts）装固定版本的 SDK；私有仓库还没准备好的话，先用 git 依赖并固定到某个 tag 过渡。
不过在讨论"怎么装"之前，有个前提必须先解决：
SDK 要求 Pillow<11、pypdf<5，后端用的是 Pillow>=11.1、pypdf>=5.1。两边的范围没有交集，不管用哪种方式装，同一个环境里都装不上。所以第一步要请同事放宽 SDK 的版本限制，并把很大的 paddleocr 改成可选安装（例如 tap-ingest-sdk[ocr]）。

方式 优点 缺点 结论
私有包仓库 + 固定版本 有版本号，构建能复现；后端不需要 SDK 源码的权限；升级就是改个版本号，PR 里看得清清楚楚 要有人配私有仓库和构建认证 ✅ 首选，生产项目的标准做法
git 依赖 + 固定 tag 不用搭仓库，马上能用；
uv.lock 会锁定到具体提交 构建机要有 git 仓库的读权限；SDK 每次发版要记得打 tag ⚠️ 过渡方案

本地路径依赖（../fwd-tap-common/...） 本机最省事 换台机器、换个 CI 或镜像就找不到路径 ❌ 不能用于生产
把 SDK 代码复制进后端 没有安装问题 两份代码会越改越不一样，同事修了 bug 你这边没有 ❌

SDK 单独跑成一个服务，后端通过接口调用 依赖彻底隔离，OCR 再重也不影响后端 要多部署、多维护一个服务 备选：只有同事不肯放宽版本时才考虑

为什么这么推荐：
1. 固定版本是生产必需的。 不固定的话，同事某天改了 SDK，你这边下次构建时入库行为就悄悄变了，出了问题很难查。
2. 设计不用改。 我们的设计已经留了入库接口（IngestPort）。SDK 不管是装在后端里，还是单独跑成服务，都只是 K9 那个插件的写法不同，K1–K8 的代码一行都不用动。
3. 装依赖这件事不该由你或 Copilot 来做。 你的电脑是离线的，uv lock 需要联网下载。而且我们的规则不允许改 pyproject.toml。所以：改 pyproject.toml 和 uv.lock 这一步，请负责构建的同事在能联网的机器上做，或者你拿到明确授权后，在能联网的环境里做。K9 只写插件代码。

三、K5 补充（追加在原 K5 提示词末尾）
我发现的 bug： 原提示词里，重试用的是"文档当前的 storage_path"。可按 K4 的写法：
- 文档的 storage_path 只有入库成功时才会写入，所以新文件第一次就失败的话，它是空的，结果被判成"没有可重新处理的文件"，根本没法重试。
- 如果是"文件已更新"后新版本失败了，文档的 content_sha256 已经是新版本的，storage_path 却还指向旧版本的文件。这时重试，入库的会是旧内容。
修法： 重试改为使用这个文档最近一次失败任务里记录的文件信息，不再用文档上的。
