# 常用提示词模式

每种模式都有现成模板（工具包 templates 目录），挂件“提示词”页可一键生成。

## 1. 先计划，后执行（plan → implement）
适合：任何超过 2 个文件的改动、迁移。
做法：第一条提示词只要计划（用 kit-planner 代理，它没有编辑权限）；用户确认计划后，开**新会话**按步骤执行。
好处：计划阶段便宜、可审查；执行阶段上下文干净，不会被探索过程的长输出挤占。

## 2. 先复现，后修复（debug）
适合：报错、测试失败。
做法：要求先给出复现命令和原始输出，再提假设、验证，最后最小修复 + 回归测试。
好处：避免“猜一个原因就改”，减少反复。

## 3. 只读评审（review）
适合：执行完成后验收。
做法：用 kit-reviewer 代理（只能读），要求每个问题带 文件:行号 和改法，最后生成修复提示词。
好处：评审者没法“顺手改”，结论更客观。

## 4. 给例子（few-shot）
适合：要求“和项目风格一致”。
做法：给 1～2 个项目里的现成文件路径作为参照，说明“照这个结构写”。比描述风格有效得多。

## 5. 明确停止条件
适合：容易越做越多的任务。
做法：写清“做到 X 就停，不要继续做 Y”；遇到需要改范围外文件时“停下来报告，不要自己决定”。

## 6. 自我核对（checklist）
适合：所有执行类任务。
做法：最后要求逐条回答核对表，每条写“是/否 + 证据”。模型在逐条核对时会发现自己漏掉的部分。

## 7. 一次一件事
适合：需求里有多个目标。
做法：拆成多条提示词按顺序执行，每条做完验证、提交，再开始下一条。
好处：出问题容易定位和回退；每条提示词更短，注意力更集中。

## 8. 固定前缀（省额度）
适合：新版本、按 token 计费。
做法：通用规则放在最前面，每次一字不差；变化的内容（任务、文件）放后面。同一会话不要换模型或推理强度。
好处：前缀超过约 1024 个 token 且完全相同时，可以命中缓存，这部分按约 10% 计费。
