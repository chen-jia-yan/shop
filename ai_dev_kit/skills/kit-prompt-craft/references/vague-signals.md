# 含糊说法与该追问的问题

| 用户说的 | 问题在哪 | 该追问 / 改写成 |
|---|---|---|
| 优化一下 | 没有方向：快？省内存？好读？ | “优化的目标是哪一个：响应时间从多少降到多少 / 减少重复代码 / 让报错更清楚？” |
| 处理一下 / 搞一下 / 弄一下 | 没有动作 | “具体是：修复报错 / 增加功能 / 删除 / 改配置？” |
| 看看 / 看一下 | 不知道要不要改 | “只要结论（只读），还是看完直接修？” |
| 完善一下 | 没有完成标准 | “完善到什么程度算完：补哪几种情况的测试 / 补哪几个字段？” |
| 相关的代码 / 这块 | 没有位置 | 自己 grep 找到候选文件，列出来让用户确认 |
| 尽量 / 最好 | 不清楚是不是必须 | “这是必须满足，还是做不到可以不做？” |
| 跟之前一样 | 不知道“之前”是哪次 | “参照哪个文件 / 哪次提交的写法？” |
| 有问题 | 没有现象 | “具体现象：报错信息、错误的返回值、还是变慢？贴一下原始日志。” |
| 都改了吧 | 范围无边界 | “列出要改的文件清单，清单外的不动，可以吗？” |
| 能用就行 | 没有验证方法 | “用哪个命令或者哪个接口调用来证明能用？” |
| 然后 / 还有 / 另外 | 一次多件事 | 拆成多条提示词，每条一件事，按依赖顺序执行 |

## 自查口诀
写完提示词，问自己四句话：
1. 换一个完全不了解背景的人，能照着做吗？
2. 做完以后，能用一条命令证明做对了吗？
3. 哪些地方绝对不能碰，写了吗？
4. 我希望它最后交回来什么，写了吗？
