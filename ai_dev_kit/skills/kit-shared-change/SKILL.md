# 改共享模块：可以改，不能改坏

## 用户会这样说
- 问答插件这里有问题，帮我改一下
- 优化一下知识插件
- 守卫说要先记录测试基线
- 这个改动会不会影响同事那边
- 共享模块改完要同步给同事
风险：会改文件

## 不适用
- 改只属于本任务的新代码（直接按 /kit-write-code）
- 配置里写的锁定区域（一个字都不能改，问用户）

## 为什么
共享模块不是某一个人的代码，可以修、可以优化；但同事的功能依赖它，改坏了会直接影响对方。所以“能改”的前提是：有基线可以对比、接口保持兼容、改了什么说得清。

## 绝对禁止
1. 没记录基线就改（守卫会拦）。
2. 改函数签名、配置字段名、返回结构、事件名等对外接口而不保留旧的用法。
3. 为了让对比通过去改或删共享模块的测试。
4. 顺手重构共享模块里和本次无关的代码。

## 步骤
1. **记录基线**（改之前，只需一次）：
   `{{PYTHON}} {{KIT_ROOT}}/tools/run_checks.py --shared-baseline`
   它在删除保护下跑一次测试，记下通过 / 失败数量（存在项目的 .ai-dev-kit/shared.json，不会被提交）。
2. **找出对外接口**：用 grep 找共享模块里被别处引用的名字（`from <模块> import`、配置字段、路由、事件），列成清单。改动只能是：内部实现、新增可选参数（带默认值）、新增函数；要改已有接口时，保留旧的写法并标注“兼容保留”。
3. **改代码**：按 /kit-write-code，一次把要改的地方改完。
4. **对比基线**：`{{PYTHON}} {{KIT_ROOT}}/tools/run_checks.py`（会自动对比）。通过数变少或失败数变多 = 改坏了，先修好再继续。
5. **写变更说明**（给同事）：
```
【改了共享模块的哪些地方】文件 — 一句话
【对外接口】没变 / 新增了 …（旧用法仍然可用）
【为什么改】……
【怎么验证】基线 通过 N → N'，失败 M → M'
【同事需要做什么】无 / ……
```
6. 需要时清掉基线重新记录：`run_checks.py --shared-baseline clear`。
