# 清单：设计与可读性（依据 Google 工程实践 code review 指南）

逐条回答“是/否/不适用”，“否”的写出 `文件:行号`。

## 设计
- [ ] 这次改动放在了正确的层吗？（接口层只做参数和响应；业务规则在服务层；数据库读写在仓储层）
- [ ] 和项目里同类功能的结构一致吗？（找一个现成例子对比）
- [ ] 有没有为“将来可能用到”而写的抽象、开关、参数？（过度设计——没有当前需求就删）
- [ ] 新增的公共函数/类，是不是项目里已经有现成的可以复用？

## 功能
- [ ] 正常输入下结果对吗？（自己脑中走一遍）
- [ ] 边界：空列表、None、空字符串、超大文件、重复提交、并发两次调用？
- [ ] 失败路径：外部服务超时/报错时，用户看到的是什么？会不会留下“半成品”数据？
- [ ] 默认值：新功能默认开启时，缺配置会不会直接报错？（应当：缺配置 → 关闭或给出清楚的错误）

## 复杂度
- [ ] 有没有一个函数超过 60 行、或者嵌套超过 3 层？能否拆成名字清楚的小函数？
- [ ] 读的人能在一分钟内看懂这段在做什么吗？

## 命名
- [ ] 名字说清了“是什么”，而不是“怎么做”？
- [ ] 改名了吗？所有引用都改了吗？（grep 旧名字，结果应为 0）
- [ ] 标识符都是 ASCII（没有中文变量名、全角字符）？

## 注释与文档
- [ ] 注释解释“为什么”，而不是复述代码？
- [ ] 删掉的逻辑，相关注释也删了吗？
- [ ] 对外行为变了（接口参数、返回值、配置项），文档或 README 更新了吗？

## 一致性与风格
- [ ] 日志、异常、返回结构的写法和项目已有代码一致？
- [ ] 没有无关的格式改动（整文件重排、改引号）？
