# 代码评审（只读）

## 用户会这样说
- 帮我评审一下这次改动
- 它说做完了，到底做得对不对
- 提交前帮我把把关
- 看看这个 PR 有没有问题
- 验收一下第二步
风险：只读

## 不适用
- 直接帮我改好（评审只读；修复要用户先选，再交给 /kit-write-code）

## 什么时候用
- 一个步骤做完，准备提交前。
- 用户拿到执行报告，想知道“它说做完了，到底做得对不对”。

## 依据
- Google 工程实践的评审要点：设计、功能、复杂度、测试、命名、注释、风格、一致性、文档；不要过度设计。
- 安全：Veracode 2025 报告显示约 45% 的 AI 生成代码含 OWASP Top 10 类漏洞，所以安全清单必须逐条过。
- 本项目的真实事故（见 references/checklist-ai-pitfalls.md）。

## 绝对禁止
1. 绝对禁止修改任何文件；只读、只报告。
2. 绝对禁止读取 .env 等密钥文件。
3. 绝对禁止只看执行报告就下结论：必须自己 view 改动的代码、自己跑或核对验证输出。
4. 绝对禁止笼统评价（“整体不错”“建议优化”）；每个问题都要有 `文件:行号` 和具体改法。

## 步骤
1. **拿到改动范围**：运行只读命令 `git --no-pager diff --stat` 和 `git --no-pager diff`（如果有基准分支，用 `git --no-pager diff <基准>...HEAD`）。对照修改范围（scope）确认有没有范围外的文件。
2. **先跑客观检查**（省得人工找）：
   `{{PYTHON}} {{KIT_ROOT}}/tools/checks.py --project <项目名>`
   把它报出的问题列入结果（它查的是：编码、嵌套 ORM 类、删掉的公开名字、隔离模块导入、测试读 .env、getattr(settings)、禁止标记、永远成立的断言、范围外改动、子模块脏状态）。
3. **逐文件人工评审**，按顺序加载并对照这些清单：
   - references/checklist-google.md（设计、功能、复杂度、命名、注释、一致性）
   - references/checklist-python-backend.md（分层、接口、数据库、配置、日志）
   - references/checklist-tests.md（测试是否真的证明了行为）
   - references/checklist-security.md（注入、密钥、权限、输入校验、日志泄露）
   - references/checklist-concurrency.md（线程、进程池、超时、锁、后台任务）
   - references/checklist-ai-pitfalls.md（AI 最常犯、本项目真实出现过的错误）
4. **共享模块和数据安全**：改了共享模块的，检查对外接口（函数签名、配置字段名、返回结构）是否兼容，基线对比是否通过；新增代码里有删除数据的写法的，检查是否有条件、是否只在用户同意后执行、测试是否用假对象。
5. **核对“说做了”的事情**：执行报告里每一条“已完成”，在代码里找到对应改动；找不到就记为“未完成但声称完成”（严重）。
6. **分级**：
   - 严重（必须改）：会出错、会丢数据、安全问题、越界修改、假测试、声称完成但没做。
   - 一般（应该改）：不符合项目风格、缺少边界测试、可读性差。
   - 建议（可以改）：命名更好、注释补充。
7. 按 references/output-format.md 的格式输出。

## 不要做
- 不要建议大范围重构；问题要在本次改动范围内解决。
- 不要因为“代码能跑”就放过假测试。
- 不要把个人偏好当成严重问题。
