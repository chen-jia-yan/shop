# 删除数据：先评估，等同意

## 用户会这样说
- 把这批测试数据清掉
- 删掉 hk 范围里重复的节点
- 重建一下索引
- 测试报了 KitDeleteBlocked
- 这些脏数据帮我处理掉
- 把旧的文档记录删了重新导入
风险：会改文件

## 不适用
- 删除本地的临时文件、构建目录（那是删文件，守卫会单独问）
- 只是查询有多少条重复数据（只读，直接做）

## 原则
删数据不是不能做，是**不能乱删**。删错了通常无法恢复，而且数据和同事共用。所以每一次删除都要：评估 → 告诉用户 → 等用户明确同意 → 只执行用户同意的那一条。

## 守卫怎么配合
- 你运行删除命令时，守卫会先拦下（什么都没执行），附上一份风险评估，并记一条“等待同意”。
- 用户在对话里回复“同意 / 可以删 / 确认删除”后，**原样**再运行同一条命令，守卫放行一次；同意只生效一次，下次删除要重新问。
- 用户回复“不要 / 取消”后，守卫会一直拦；用户问“有多少条 / 是哪个库”时继续等。
- 测试和脚本在 `kit_run.py` 下运行，里面的删除调用没经同意会报 `KitDeleteBlocked`（数据没删）；用户同意后用 `{{PYTHON}} {{KIT_ROOT}}/tools/kit_run.py --allow-delete -- <原命令>` 重跑，每一次删除都写进日志。

## 绝对禁止
1. 用户没回复同意之前执行删除；把“用户没反对”当成同意。
2. 被拦下后换写法、拆命令、换工具、改环境变量来绕过。
3. 为了“重来一次”顺手清空数据；为了让测试通过去删真实数据。
4. 在共享库上“试一下”删除语句。

## 步骤
1. **先只读计数**：用同样的条件做一次查询，拿到会删的数量和样例（例如 `MATCH (n:Doc {scope:'x'}) RETURN count(n)`、`SELECT COUNT(*) ... WHERE ...`）。
2. **写风险评估**（守卫给的评估是粗略的，你要补充具体数字）：
```
【要删除】语句或接口原文（一条一行）
【连接的是】哪个库 / 索引 / 环境（只写名字，不写地址和密码）
【范围】会删多少条（只读计数的结果），条件是什么
【风险】高 / 中 / 低，理由
【能否恢复】有没有备份、快照、能不能重新导入
【建议】删之前先做什么（导出、备份、改成软删除、先在测试库试）
【替代做法】（能不删就别删：打标记、过滤掉、写入新版本）
请回复“同意”执行，或者告诉我怎么调整。
```
3. **停下来等用户**。用户提出调整（缩小范围、先备份），改完重新评估、重新问。
4. **用户同意后执行**，执行完再做一次只读计数，告诉用户实际删了多少、和预计是否一致。

## 风险分级参考
| 级别 | 典型情况 |
|---|---|
| 高 | DROP / TRUNCATE；不带条件的 DELETE；`MATCH (n) DETACH DELETE n`；线上或共享库；云上的索引、存储 |
| 中 | 带条件但范围不确定；通过接口或客户端按参数删除 |
| 低 | 本地或测试库里、带明确条件、数量很少、可以重新生成 |
更多写法和对应的只读计数方式见 references/delete-patterns.md。

## 测试里的删除
- 单元测试一律用假对象，不连真实库，就不会有删除问题。
- 集成测试需要清理时，优先：写入带唯一前缀的数据并保留；或者用一次性的测试库。确实要删，按上面的流程问用户。

## 输出格式
按“步骤 2”的风险评估格式；执行后补一行【实际结果】删除前 N 条 → 删除后 M 条。
