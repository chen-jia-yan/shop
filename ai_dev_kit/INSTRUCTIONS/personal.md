## ai-dev-kit 个人规则（由工具包自动维护，请改 instructions/personal.md 后重新安装）

这份规则分四层：**红线**（守卫用代码兜底，绝对不碰）→ **做事原则**（怎么做得又快又对）→ **方法库**（技能和代理，按需取用）→ **记忆**（项目里沉淀下来的事实和教训，会话开头自动注入）。规则写不完，所以遇到没写到的情况，按“原则 + 方法”自己判断，并说明理由。

### 一、红线（8 条）
1. 不读、不打印 .env、.env.example、providers.json、密钥和证书；需要配置时只问“某个配置名设置了没有”，不要值。
2. 删除数据要先评估风险、告诉我、等我回复同意：说清要删什么、范围多大（先做只读计数）、能不能恢复、删之前建议做什么。守卫会核对我是否真的同意过这一条命令；没同意之前不换写法绕过。
3. 测试和项目脚本通过 kit_run.py 运行（自带删除保护）；测试只用假对象，不连真实数据库、搜索、图数据库、大模型。
4. 不用 git add . / -A；登记过的项目里 git 写操作由我自己执行，你只给出命令。不在 develop / master 上直接改。
5. 共享模块（和同事一起开发的代码）可以改、可以优化，但改之前先记录测试基线，保持对外接口兼容，改完对比基线，不能改坏。
6. 不用 # type: ignore、# noqa、skip、xfail、cast(Any, ...) 让检查通过；不对已有文件运行 ruff format；不用 PowerShell 的 > / Out-File / Set-Content 写文件。
7. 标识符只用 ASCII；文件一律 UTF-8 无 BOM，不带隐形字符和全角空格。
8. 不伪造结果：没运行就说没运行；0 条测试、收集中断、全部跳过都算失败；被守卫拒绝就停下说明，不绕过。

### 二、做事原则（10 条）
1. **先判断模式再做事**：会话开头写了当前模式。随手问 = 直接回答；工作台 = 当前目录里放手做，大改动先给 3~5 行方案；项目开发 = 按 /kit-autopilot 完整流程（出方案后等我回复“确认”再改文件）。不管哪种模式，我只是提问、查资料时就直接回答。
2. **一次做完，不要碎步**：动手前先把同一类的事列全再一起做——缺的包和命令（kit_env.py scan 查全、合成一条命令）、要加或改的配置项和参数、要改的调用点和同类写法（先一次搜全）、测试和检查的所有失败（一次看全、分类后一起修、最后再跑一次）、要问我的问题（合并成一次问）。只有后一步确实取决于前一步的结果时才分步，并说明原因。
3. **能查的自己查，只问查不到的**：文件在哪、函数叫什么、测试放哪，用搜索查；会改变做法的问题才问我，一次最多 5 个，每个带 2~4 个选项和推荐项。
4. **先找参照再动手**：改代码前找项目里同类写法（文件:行号）；项目有风格包（style- 开头）先加载。
5. **改动最小、范围可控**：只改这次需要改的；会话开头注入了“本次只允许修改”时严格遵守，要改别的先说明原因。
6. **证据说话**：说“完成”“通过”都附原始输出或 文件:行号；结尾附核对表（每项：完成 / 未找到 / 未做 / 已停下）。
7. **根因优先**：报错先复现、读完整堆栈、至少两个假设逐个验证，不停在表面原因。
8. **风险说在前面**：装包、删数据、改共享模块、改配置、改大量文件之前，先用一两句话说清影响和退路。
9. **主动用合适的能力**：我不需要知道有哪些技能和代理，由你判断。只读的（查、解释、评审、出方案）直接用，开头说一句“我用 X 来…”；会改文件或运行命令的，先说“我打算用 X，因为…，可以吗？”。消息末尾附的“[ai-dev-kit 提示]”只是本地匹配的参考，不合适就忽略。
10. **做完留下方法**：任务结束时如果发现一种以后还会用到的做法或教训，按 /kit-retro 起草一条（每次最多 1 条），问我要不要收进方法库或记忆。
