# 切片审核后端调研与实施方案
状态：待确认的设计提案，不代表功能已经实现。调研日期：2026-11-23；已根据用户补充的范围和对比要求更新。

范围：依据当前后端代码、`chunk_part` 目录中的三份资料和页面截图，设计前后端联调接口与分步实施方案。本次不修改业务代码、不更新现有导览、不调用真实服务、不删除接口或数据。

## 1. 结论与需要先确认的方向
1. 当前已有文件、切片读取和草稿管理路由；没有调参重切预览接口。草稿提交虽然有路由，但当前装配的发布器为 `None`，不能认为“应用到知识库”已可用。
2. 用户已明确一期只做搜索文件、调参、对比预览和保存草稿，不做正式应用入库。截图中的“应用到知识库”应由前端禁用并说明原因；后端不新增正式发布能力。
3. 不建议现在删除任何已有接口或字段。仅凭截图和后端代码不能证明外部前端、网关或其他调用方不再使用；后文列出待核查项和下线条件。
4. 截图是界面参考，不是运行时事实。图中的模型、维度、默认值和文件数量不能直接写死到接口。
5. 用户已确认对比方向：六类变化均纳入方案，能可靠识别的先实现，无法判断的明确标记“待人工确认”；复杂情况如无法达到要求，先报告再决定是否暂缓。本提案中的新增接口名、字段、状态、分表方式和范围仍是建议，不是当前接口或已确认契约。

### 现有字段和约束
- 文件项：`file_id`、`source_file`、`doc_type`、`chunk_count`；详情增加 `locators`。
- 当前切片：`chunk_id`、`file_id`、`source_file`、`page_or_sheet`、`part_index`、`content`、`metadata`。
- 草稿切片：`chunk_id` 可空、`page_or_sheet` 可空、`content`、`origin`（source / edited / added）；更新接口目前整个数组上限为 5000，允许空数组但服务会检查每项内容及 ID 规则。
- 草稿记录有 `status`、`base_chunk_count`、publish结果、时间及操作人，但没有调参快照、预览来源、真实内容版本或乐观锁。
- 草稿列表调用仓储时按传入范围过滤；仓储对 `None` 条件不加过滤。详情、更新、删除等按 ID 的仓储方法自身附带租户条件。请求身份绑定不等于已完成对象级授权，需设计可信范围校验和跨租户测试。
- 既有 `PageQuery` 的 `page_size` 没有上限；建议为新增接口设置明确上限，旧接口不能无确认地收紧或删除字段。

## 5. 建议的一期接口契约（待确认）
### 5.1 通用约定
- 只新增 GET/POST，路由前缀沿用 `/tap/ai/library`，Pydantic 请求/响应模型、EnvelopedRoute、业务错误码、分页风格以当前代码为参照。
- 鉴权依赖复用 `get_request_context`；服务端使用上下文中的租户、工作区、项目、用户，不信任请求体中的身份值。需要允许跨范围管理时，必须另有明确的授权规则。
- 以下 JSON 为 data 内容示意，非已上线响应。字段采用兼容性只增不改；不存在时明确标注 nullable 或错误，不能以空数组/成功掩盖数据源故障。
- 预览操作只针对一份明确的源文件和参数快照；客户端不能传任意服务器路径。

## 5.2 创建预览任务
建议：`POST /tap/ai/library/chunk-previews/add`

请求示意：
```json
{
  "file_id": "doc::example",
  "chunk_size": 700,
  "chunk_overlap": 100
}
```

以上数值只作格式示意，不代表实际默认值或已验证的允许范围。`ocr_language`、`chunk_type` 暂不列为确定字段：分别需确认业务需求、实际 SDK 签名和与旧版本的兼容性。

建议响应 `data`：`preview_id`、`file_id`、`status`、`create_time`。状态建议为 `pending / processing / completed / failed`；失败返回可安全展示的业务原因，不返回原始堆栈、内部路径或原文。

为何这样写：截图中 PDF/PPT/OCR 可能耗时，同步长请求和重复点击不可靠；新建异步任务并返回 ID 可让前端查询状态，预览和正式入库分开。是否复用现有 worker 机制还需验证其不会触发 sink 或清理。

建议行为：校验可信范围和文件归属 → 检查可读取的原始文件及源版本 → 固定参数快照、限流、幂等键 → 创建任务；同一文件的重复请求与并发限制需具体确定。若源文件不可用，应明确报“无法预览”，不把旧切片冒充新预览。

## 5.3 查询预览状态与摘要
建议：`GET /tap/ai/library/chunk-previews/{preview_id}`

响应 `data` 建议包含 `preview_id`、`file_id`、`status`、参数快照、源版本、创建/完成时间、`chunk_count`、可安全展示的失败码/提示；只有已完成结果才可读取和保存。对不存在、越权、失效、未完成分别按项目错误契约明确表达，不泄露其他租户对象是否存在。

为何这样写：页面可按固定频率轮询，并展示处理中/失败/完成；不把大量正文塞进每次状态轮询。轮询间隔、超时、取消能力待确认，避免无限轮询。

## 5.4 读取预览切片
建议：`POST /tap/ai/library/chunk-previews/chunks/list`

请求：`preview_id`、`go_page`、`page_size`；响应：`items`、`total_items`、`total_pages`。每项建议包含临时 `preview_chunk_id`、`part_index`、`page_or_sheet`、`content`；可选字段必须来自实际解析结果。`preview_chunk_id` 仅用于预览内稳定引用，不冒充正式索引的 `chunk_id`。

为何这样写：延续现有列表接口分页样式，限制单次正文大小；对照页可独立加载当前及预览两侧。排序必须稳定；请求页大小、正文长度和整个文件限制在 SDK 能力确认后设定。

## 5.5 保存预览为草稿
建议：`POST /tap/ai/library/chunk-previews/save-draft`

请求：`preview_id`、客户端幂等键；必要时另传预览版本或结果指纹。响应：既有草稿信息，只追加预览来源、参数快照、源版本等字段；扩展位置、JSON 结构和数据库迁移需按最终设计确定。

建议默认每次保存生成新草稿版本；重复提交同一幂等键只返回同一次结果，不覆盖别人草稿。保存前同一事务核验预览完成、归属、指纹及源版本，保存实际预览切片，而不是再次解析生成可能不同的结果。

为何这样写：旧 `/chunk-drafts/add` 的语义是从线上当前切片复制，改用该接口承载预览会改变既有行为；独立接口保留兼容性，也保证“看到的”与“保存的”一致。

## 5.6 页面配置/能力接口
先核查现有模型目录、系统配置和主系统知识库列表是否能安全提供所需字段；不足时建议新增只读接口，例如 `GET /tap/ai/library/chunk-review/capabilities`，仅返回有依据的模型标识、向量维度、可用参数约束、预览/发布能力状态。未知值明确为 `null` 或返回不可用原因，不返回机密。此接口命名与字段需二次核对对现有能力后锁定。

## 5.7 查询对比映射
建议：`POST /tap/ai/library/chunk-previews/diff/list`。请求 `preview_id`、`go_page`、`page_size`；响应仍按 `items`、`total_items`、`total_pages` 返回映射分组。完成态预览详情额外返回该次对比的摘要；映射分组与切片的对应和分页规则见第 11 节。

为何这样写：用户已确认需要对比，长文档的完整映射不适合塞进每次状态轮询。采用分页分组，能同时返回一对多、多对一以及无法确认的情况，不把两栏各自的同一页序号强行当作对应关系。

## 6. 预览实现与数据设计
### 6.1 只读预览链路
1. 根据可信租户和 `file_id` 查找当前文件；现有 `KbDocumentRepo.find_by_document_key(saas_id, document_key)` 能按租户和文档键精确查询候选文档。必须进一步核实该索引的 `file_id` 确实等于其 `document_key`，并确认文件归属及源文件版本；两者不可仅凭文件名猜测。
2. 通过既有存储端口读取有权限的原文件；历史索引文件可能没有知识库记录或原文件，需返回明确不可预览原因。
3. 新增与入库隔离的预览端口和 SDK 适配器：只做解析/OCR/切片，不构造正式 sink，不发 embedding，不修改索引/图谱/正式切片。不要直接调用现有 `ingest_file`。
4. 在允许的存储中保存预览任务、参数快照和结果，支持分页、异常状态、对象级授权、失败重试约束。推荐持久化任务而不是仅放本进程内存，避免多实例/重启丢失；具体表、容量、留存期限及迁移需确认。
5. 保存草稿时将预览结果作为快照写入草稿，明确来源与原文件版本；预览结果和草稿正文属敏感数据，禁止原文进日志或外部错误信息。

需要先核验：项目实际安装 SDK 的来源、版本、`TapIngestClient` 是否有不计算 embedding 的解析/切分入口，以及 `parser`、`chunker` 参数签名。此次在常见本地虚拟环境和相邻 SDK 路径未找到源码，未运行 Python 或安装依赖；因此“可以完全复用 SDK 某方法”目前只能作为待验证假设。

### 6.2 参数与记录
- `chunk_size` 与 `chunk_overlap` 的单位、最小值、最大值、各文件类型行为由 SDK 实际签名及测试确认，不能沿用截图的数字作为规则。
- 保存源文件不可伪造的版本标识（如现存内容哈希及文档版本信息）以及当前切片版本/摘要；仅比较 `base_chunk_count` 不能发现数量相同但正文改变。
- 预览参数、预览结果、SDK 版本或可追溯的算法版本应一并记录；不存在可靠版本信息时明确标未知。
- 草稿编辑和保存增加可验证的乐观并发版本，状态变更条件更新；兼容既有数据，迁移脚本只做增量变更，不删除旧表或旧列。
- 不在方案中默认过期清理、自动删文件或删数据库记录；保留时间、清理方式、范围及恢复能力须另行确认和授权。

### 6.3 当前数据一致性风险
正式发布涉及新旧切片、向量、索引、图谱引用、MySQL 正文与文档状态。现有 worker 的数据库成功事务不能为外部索引和图谱提供跨系统原子性；旧切片数量减少后如何移除残留、失败补偿及切换均尚未证明。

截图中的“应用”不能简单等价于重新运行入库：预览草稿可能被人工编辑，重新解析也可能得到不同结果。未来正式发布必须明确以已确认草稿快照还是重新解析结果为准、如何保障可回退，以及如何处理向量和图谱。

若方案需要删除/覆盖旧索引文档、数据库正文、图谱或存储文件，必须先列目标、只读计数、恢复方式与备份建议，获得对具体操作的单独同意；不可把“做这个功能”的确认当成删除数据授权。

# 11. 补充：六类对比的具体方案与验收
## 11.1 本次调整和项目事实
用户已指定以原方案为基础，并确认六类均纳入、无法判断时提示人工确认。因此本文此前“可先只做左右展示”的建议已撤回。六类不是已有功能，需要新增对比模型、计算逻辑、查询接口和测试。
- 当前旧切片字段在 `contracts/library.py`：正文、`chunk_id`、可空的 `page_or_sheet` 和 `part_index`；索引读取按 `chunk_index` 排序，见 `azure_chunk_source.py`。
- 正式入库结果的数据结构 `IngestChunk` 有正文和定位信息，但它并不证明预览已实现；见 `contracts/library_kb.py`。
- 当前接口未给出统一的原文起止坐标；正文重复、切片 overlap、定位符缺失、跨页和 OCR 漂移时，无法仅凭切片文本保证唯一对应。对比结论是审核辅助，不是正式发布或原始文档变更的权威判定。
- 既有草稿校验要求 `source / edited` 有旧 `chunk_id`，`added` 的 `chunk_id` 必须为 `null`，见 `library_chunks.py`。重切结果不应把 SDK 临时 ID 当作线上 ID。最保守的预览转草稿做法是按预览顺序保存为 `origin=added`，`chunk_id=null`，并另存对比来源；它不改变旧验证规则，也不暗示未来正式发布的 ID 策略已经解决。

## 11.2 六类的边界与复杂度
| 标记 | 示例 | 本期建议 | 复杂度和风险 |
| ---- | ---- | ---- | ---- |
| `unchanged` 未变化 | ABC → ABC | 正文按约定的换行规范化后完全一致，且对应唯一时标记。 | 低；重复文本必须避免误配。 |
| `split` 拆分 | ABCDEF → ABC、DEF | 最多检查连续 3 个新切片；在可证明顺序和重叠拼接唯一的简单场景识别。 | 中；重叠区有多种拼接可能时不能硬判。 |
| `merge` 合并 | ABC、DEF → ABCDEF | 最多检查连续 3 个旧切片；使用与拆分相同的保守规则。 | 中；旧切片可能已经重叠。 |
| `modified` 修改 | ABC → ABD | 只对唯一的 1:1 候选给出建议匹配；匹配阈值及归一化规则需用样例校准，不给没有统计依据的置信概率。 | 中至高；相似文本不一定是同一位置，OCR 变化还会增加歧义。 |
| `added` 新增 | 无旧对应 → XYZ | 仅当完整快照、定位/相邻锚点和规则能证明该片不属于未解析候选时标记。 | 中至高；找不到对应不等于新增。 |
| `removed` 删除 | XYZ → 无新对应 | 与新增对称；仅是对比结果，不执行真实删除。 | 中至高；找不到对应不等于删除。 |
| `uncertain` 待人工确认 | 重复段落、跨页、多拆多合、匹配冲突 | 返回候选两侧片段，展示待确认；不计入已确认的六类统计。 | 必须保留，避免把猜测当事实。 |

复杂度是静态判断，不是工期保证或准确率结论。对于无法证明唯一对应的新增、删除、修改、拆分或合并，一律进入 `uncertain`；六类中的某一类在真实样本上无法达到标准时，先报告并由用户决定是否暂缓，不用猜测补齐数字。

## 11.3 一期规则流程（拟定）
1. **先固定基线**：每个预览关联该次读取的当前切片快照及预览快照，包含顺序、定位符和原文；摘要与映射均来自同一快照，分页时不重新读在线索引。两次读取期间若基线发生变化则失败或标记过期，不用不一致的数据生成确定映射。如何原子识别索引版本需先核实；没有可信版本时不得宣称强一致。
2. **安全预处理**：只规范 CRLF / CR 为 LF；不删除日文空格、标点、不做全半角折叠，不改变展示正文。定位符只在可靠且格式一致时作为辅助约束；缺失、跨页或版本不一致不当作强证据。
3. **唯一精确锚点**：按顺序找正文一致且在相应候选范围唯一的旧/新片段；重复正文或顺序冲突保留待确认，避免单凭相同文本乱配。
4. **局部拆分/合并**：在相邻可靠锚点之间匹配连续窗口，单侧最多 3 片；只有对每一种相邻片的精确重叠去重方式都能得到唯一、完整对应时才确认。无重叠直接拼接；多种结果、超 3 片、1:N 与 N:1 同时成立、N:M 或跨范围均为待确认。
5. **修改与新增/删除**：对单条剩余候选，在明确顺序、定位及双向唯一的前提下，可以用标准库文本相似度提供“修改建议”；阈值先基于测试样本提出，未经验证不得宣称准确率。没有可靠锚点、存在竞争候选或截断时，统一待确认。新增/删除只在可证明其他候选均排除的完整区段给出，否则待确认。
6. **汇总和输出**：按旧切片顺序、再按新切片顺序形成稳定分组；每条旧切片和每条预览切片恰好属于一个分组，统计 `unchanged / split / merge / modified / added / removed / uncertain` 的分组数。分组数不是切片数；另返回当前及预览切片数。摘要与分页分组汇总必须一致。

# 12. 补充：可执行的数据流、接口和阶段
## 12.1 源文件、搜索和身份
1. 搜索入口优先保留现有 `/files/list`，兼容索引中尚无 MySQL 管理记录的历史文件；若页面需要文件类型、状态、上传时间筛选，评估并优先复用 `POST /tap/ai/library/kb/documents/list`，其请求已支持 `keyword/status/file_types`，见 `library_kb.py` 和 `library_kb.py` 契约。两种列表数据源、ID 和覆盖范围不同，不可悄悄把一种替换成另一种。
2. 选中现有索引文件后，以可信 `saas_id` 加该文件的 `file_id` 与 `document_key` 精确查询文档；仅当所选索引的 ID 语义经过核实，且文档未删除、源路径可读取时，允许预览。历史同步文件如果没有原文，应明确提示“该文件暂无可原文，不能预览”，仍可浏览现有切片。
3. `StoragePort.download_stream` 仅接受服务端查询到的路径，不能由请求传入；限制文件大小和并发，读取失败时返回安全业务错误，不把路径或异常堆栈返回前端。
4. 身份以 `identity.py` 的可信上下文为准；草稿和预览每次读写均应在数据库查询条件中绑定授权范围，而不是只先查 ID 再由调用方判断。工作空间/项目空值、跨租户草稿共享规则需业务确认，不能默认所有人可见。

## 12.2 预览和草稿的事务边界
- **创建预览**：接收受限参数及请求幂等键 → 校验用户、文件、源文件版本 → 生成预览 ID 和 `pending` 记录 → 处理器条件领取 `processing`。建议异步任务，具体队列与重启恢复策略在确认运行架构后落定，不复用会实际写索引的入库任务。
- **计算预览**：读取原文件并验证文件摘要 → 用已确认版本 SDK 的解析/OCR/切片接口产出结果 → 读取有界的当前切片基线 → 计算对比 → 同一事务提交快照、结果和 `completed`。任一失败记 `failed` 和安全错误，不写索引、不写正式切片、不调用 embedding/图谱。
- **任务恢复**：明确领取租约、心跳、超时、重复领取和最大重试；只有持有当前租约的执行者可提交结果。进程中断不能把半成品标记为完成；任何隔离临时文件的清理须遵循数据安全规则，不将其扩展为删除用户原文件或历史数据。
- **保存草稿**：请求携带 `preview_id` 与幂等键 → 在事务内验证预览归属、完成态和结果版本 → 按次序复制预览切片 → 保存基线切片数量、源文件/预览版本、参数和 diff 摘要 → 新建 `draft`。同一租户和同一幂等键的并发重试返回同一草稿；不同键生成不同版本；不能以 `file_id` 覆盖已有草稿。`DraftRepo.add(commit=False)` 支持同事务写入，但还需设计数据库唯一约束处理并发。
- **不可变语义**：预览完成后的结果不允许被后台覆盖；重新调用创建新的预览 ID。草稿后续编辑不反向修改预览。预览保存后是否允许编辑及保留多久须确认。
- **状态显示**：处理失败、源文件缺失、切片读取失败、索引缺排序字段、超限、对象越权各自给出不泄露数据的提示。请求校验错误走当前项目统一的校验信封；见 `envelope.py`，不要假定一定是 HTTP 422。

## 12.5 剩余决策，不阻碍阅读方案
