我看完了，结论是方向对，可以执行，但要先做两件事：确认 SDK 能不能”只切片、不入库”，再把一期范围砍小。 另外方案漏掉了几处对调参体验影响很大的设计。下面依次说：方案的设计对在哪里，问题在哪，建议怎么改，怎么验证。

## 一、方案做对的地方

这几点是方案的骨架，要保留：

- 预览和入库彻底分开：不调用现有的 ingest_file，单独新建一个只做解析和切片的适配器，不写索引、不调 embedding、不写图谱（6.1 节）。这是整个功能安全的前提。

- “应用到知识库”按钮先禁用：发布器现在是 None，不能让页面看起来像发布成功了。

- 保存草稿另开一个接口：不复用 /chunk-drafts/add，因为那个接口的意思是”复制线上切片”。另外要求保存的就是用户看到的那份预览结果，不重新解析一遍。

- 对比结果拿不准时标 uncertain：不让算法乱猜，在审核场景里这个原则是对的。

- 点出了几处已有的风险：草稿按 ID 读写时没有显式按租户限定范围；JP 旧索引可能缺 chunk_index；文件列表有扫描上限，列表可能不全。这些不管做不做预览都该修。

## 二、主要问题

1. 最大的阻塞项：SDK 能力没有确认（方案自己也承认）

方案第 0 步写明：没找到 SDK 源码，不知道 TapIngestClient 有没有”只解析和切片、不算 embedding”的入口。这一步不通过，后面全部不能动工。 这一步要你先去确认，见第五部分。

2. 漏了一个关键设计：解析结果应该缓存，调参只重新切片

这是方案最大的遗漏。调参的典型用法是：同一个文件，把 chunk_size 从 500 调到 700 再到 900，反复看效果。

- 耗时的是解析和 OCR（PDF、PPT 可能要几十秒）。改 chunk_size 和 overlap 只影响切片这一步，不影响解析结果。

- 方案每次预览都走”读原文件 → 解析 → 切片”的全流程，每调一次参数就要重新 OCR 一次，体验差，成本也高。

- 建议：parse_id（按文件内容哈希加解析器版本生成）对应一份解析结果，缓存起来；每次预览只基于这份解析结果重新切片。缓存命中时，切片通常是毫秒到秒级。

- 前提还是第 1 点：SDK 的解析器和切片器得能分开调用。

3. 一期做得太重

方案按”可靠的分布式任务系统”来设计：持久化的任务表、租约、心跳、重复领取、幂等键、唯一约束、增量迁移，分 8 个步骤。对”预览一下切片”来说，这套设计偏重。

- 和你的要求可能冲突：你说”暂时不落库”。方案却新增了预览表和迁移，预览结果要写进 MySQL。

  - 我理解你说的”不落库”是”不写入正式知识库”（索引、向量），因为草稿本身就是存在 MySQL 的草稿表里。

  - 但”预览结果要不要单独建表”值得重新考虑，见第三部分。

- “不自动清理”会让数据一直增长（6.2 节）。每次调参都产生一份完整的切片快照，又不清理，表很快会膨胀。预览本来就是临时数据，应该设过期时间，比如 24 小时。

4. 对比算法可以更简单、更准

方案的六类对比靠文本匹配：找精确锚点、在 3 个切片的窗口里拼接、用相似度判断。它自己也承认，重复段落、overlap、跨页、OCR 漂移时很多结果只能判为 uncertain。这部分复杂度最高，风险也最高。

更好的做法是用位置区间对比：

- 如果”调参前”和”调参后”都是从同一份解析文本切出来的，每个切片就有确定的起止字符位置。

- 对比就变成看区间有没有重叠：旧区间被几个新区间覆盖就是 split，多个旧区间落进一个新区间就是 merge，位置相同就是 unchanged。这个判断是确定的，重复文本、overlap 都不会造成歧义，基本不会出现 uncertain。

- 关键问题是：”调参前”指的是什么？

  - A. 当前线上索引里的切片：这些是以前入库时切的，可能用的是旧解析器，也没有存位置信息，只能用方案里那套文本匹配，复杂度高。

  - B. 同一个文件用旧参数重新切一遍：两边都有位置信息，对比简单、准确。不知道旧参数时，可以用”上一次预览”作为对比基线。

- 建议一期按 B 做（预览和预览之间对比，或者用”默认参数”和”新参数”对比）。线上切片在左栏照常展示，不做精细对比。这一点需要你确认，它决定了这个功能最难的部分做不做。

5. 对调参真正有用的信息没提

调参时，用户最想知道的其实是这些统计信息：

- 切片数量；长度分布（最短、平均、最长，或者直方图）

- 超过 embedding 模型 token 上限的切片有几个（会被截断）

- 太短的碎片切片有几个（检索噪音）

- overlap 部分在页面上高亮

这些计算便宜、价值高，前端很好展示。建议把它们加进预览详情接口，和对比结果放在一起。

6. 单位问题要特别注意

方案提了”单位待确认”，但没说清楚它的影响：日语和中文按字符数和按 token 数算，差别很大（同一段文字，token 数可能是字符数的 1–2 倍）。如果滑块上写的是”字符”，SDK 实际按 token 切，用户调出来的效果就会和预期不一样。第 0 步要把这一点一起确认。

7. 篇幅上的小问题

- 方案有很多篇幅在讲接口下线流程、删除授权、数据安全，和这次的需求关系不大，是 Copilot 自己的保守规则。读的时候可以跳过，不用作为方案内容去评审。

- 分页风格：这里用的是 go_page、total_items、total_pages，评估模块用的是 page、page_size、total。同一个项目里有两套分页写法。 新接口跟着切片模块现有的写法走就行，但建议记一笔，以后统一。

## 三、建议的一期范围（精简版）

方案原设计 建议

持久化异步任务、租约、心跳 解析异步，切片同步：第一次解析走后台任务（只轮询解析状态）；解析好之后，每次调参同步返回结果

新建预览表，不清理 解析结果和预览结果放进 Blob 临时目录（ai/{saas_id}/chunk_preview/{id}.json），或者在表里加过期时间，24 小时后清理；只有草稿进 MySQL

和线上切片做六类文本对比 一期：预览之间按位置区间对比；线上切片只并排展示。和线上切片的精细对比放到二期

8 个步骤 5 步：确认 SDK → 解析和切片适配器 → 区间对比纯逻辑 → 预览接口 → 保存草稿

无统计 加上长度分布和超长切片数

接口可以收敛成 4 个：
POST /chunk-previews/parse            {file_id} → {parse_id, status}     已解析过就直接返回 completed
GET  /chunk-previews/parse/{id}       → status, page_count, text_length  轮询用
POST /chunk-previews/add              {parse_id, chunk_size, chunk_overlap, base_preview_id?}
                                      → {preview_id, stats, diff_summary}  同步返回
POST /chunk-previews/chunks/list      {preview_id, go_page, page_size}   每片带 start, end, diff 分组
POST /chunk-previews/save-draft       {preview_id, idempotency_key}      → 草稿信息


base_preview_id 为空时，就和默认参数切出来的结果对比。

方案里那些该保留的东西照样保留：租户上下文、对象级授权、”应用”按钮禁用、功能开关默认关闭。

## 四、怎么验证

1. 纯逻辑单元测试（不需要 SDK）

- 区间对比：用固定的 [(0,100),(100,200)] 对 [(0,200)] 这类数据，测出 merge；反过来测出 split；overlap 区间也覆盖到。

- 断言每个切片恰好出现在一个分组里，分页读取后不漏、不重复，汇总数和明细一致（方案 11.5 节的这些标准保留）。

2. 适配器隔离测试（最重要的安全测试）

- 用假的 SDK，断言 parser 和 chunker 收到的就是前端传的参数，sink、embedding、图谱的调用次数都是 0。

- 同一个文件预览两次，断言解析只执行了 1 次，第二次命中缓存。

3. 用 Swagger 跑一遍（和评估模块的思路一样，先接一个测试用的适配器）

- 选文件 → 解析 → 轮询到完成 → 用 500/50 预览一次 → 用 900/100 再预览一次，base_preview_id 填第一次的 → 看对比结果和统计 → 保存草稿 → 用 /chunk-drafts/{id} 查出草稿，切片内容和第二次预览逐条一致。

- 异常场景：overlap ≥ size → 参数错误；预览别的租户的 file_id → “不存在”；对没有原文件的历史文件发起解析 → 明确提示”不能预览”；同一个幂等键重复保存 → 返回同一份草稿。

- 查表或查存储，确认：索引和切片表没有任何变化，草稿表多了一条记录。

4. 用真实文件的回归测试（这条最能说明预览可信）

- 用和当初入库相同的参数预览一个已经入库的文件，再把结果和线上切片比一下。

  - 应该几乎完全一致，这说明预览确实复现了入库时的切片逻辑。

  - 如果差别很大，说明解析器版本或者参数和当时不一样。这时候拿预览结果和线上做对比本身就不可靠，这也是我建议一期先做”预览对预览”的依据。

- 用 PDF、PPT、Excel 各选一个，记录解析耗时和切片耗时，用这些数据决定”切片同步返回”是否可行。

五、要你确认的 4 件事

1. SDK 在哪、什么版本？解析器和切片器能不能分开调用？chunk_size 按字符算还是按 token 算？这是能不能动工的前提。

2. “不落库”具体指什么？是只不写正式知识库（预览结果可以临时存起来），还是预览结果连临时表都不想进？

3. “调参前”指什么？是线上切片，还是上一次预览？这决定一期的对比是简单版还是复杂版。

4. 截图里的”类型”下拉框和”重新切片”按钮是什么意思？方案第 9 节也问了这个问题，需要产品给出答案。
