# 任务：修复"文件列表能看到文件，切片预览却返回'预览源文件不可用'"

## 背景（已确认的事实）
- /tap/ai/library/files/list 只按租户读 Azure 索引，用 document_id 做分组，然后列出文件。keyword 是对 source_file 去掉首尾空格、转小写之后做包含匹配。
- /tap/ai/library/chunk-previews/baseline 会先查 MySQL 的 library_kb_document，条件是：租户、非空的 workspace/project/user、document_key=file_id、status=indexed、deleted=0。查到后还要检查文件名、路径、哈希、大小，全部通过了才去读 Azure 切片。以上任何一项失败，返回的都是同一句"预览源文件不可用"（library_chunk_preview_common.py:134 附近）。
- 正常上传时，document_key 是 doc:: 加 16 位随机十六进制，并作为 idempotency_key 传给 SDK，所以 Azure 的 document_id 和它相等。SDK 单独入库时，如果没有传 key，document_id 会用 doc:: 加文件 SHA-256 的前 16 位。所以索引里可能有一些文件，在 MySQL 里没有对应记录，或者 ID 对不上。
- 实例：document_key=doc::e26586aaea2b4d36，saas_id=hk，带有 workspace_id、project_id，user_id=223078，status=indexed，deleted=0，哈希、路径齐全，大小约 3MB。用这个 key 调 baseline，仍然返回"不可用"。按哈希推出来的默认 ID 是 doc::f0b2480448e6a67a。

## 第 1 步：通用修复（不管是哪种情况都要做）
A. 文件列表返回预览状态
- FileSummary 和 LibraryFileData 新增字段 preview_status: Literal["ready", "unavailable", "metadata_incomplete", "unknown"]。
  - ready：MySQL 里能找到记录，并且范围、状态、元数据都满足要求。只表示静态检查通过，不保证预览一定成功。
  - unavailable：找不到记录，或者不在当前身份的范围内。这两种情况对外合并成一种，避免泄露文件归属。
  - metadata_incomplete：有记录，但缺路径、哈希、文件名，或者大小不合规，或者状态不是 indexed。
  - unknown：MySQL 查询出错时用这个值，不能返回一排 false 假装已经检查过。
- 在 persistence 层新增一个批量查询，只查当前页的 file_id，参数化 IN 查询，每批不超过 200 个，避免 N+1。范围判断和 baseline 用同一个函数，不要复制一份逻辑。
- 只在 application 层的 list_files 里补这个字段，不改分页、不改排序、不改 total 的统计口径。
- 新字段在 api/dto.py 里加上 Field(description=...)，Swagger 里要能看到可选的取值。

B. 把 baseline 的失败原因拆开
- 把范围判断和元数据检查抽成同一个纯函数，比如 check_preview_source(document, scope) -> PreviewSourceCheck(reason, ...)，文件列表和 baseline 都调用它。
- 对外的提示只拆成两种：
  - "预览源文件不可用"：找不到记录，或者不在范围内
  - "源文件信息不完整，请重新上传后再预览"：元数据缺失、状态不对
  错误码保持 CCB001 不变，五种语言的 message key 都要补上。
- 详细原因写进 logger.info，字段固定为 event=preview_source_rejected、reason、file_id，身份信息做脱敏。这条日志要长期保留，代替临时日志。
