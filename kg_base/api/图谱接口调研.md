## 一、知识图谱相关模块与内容分布

### 1.1 当前项目里，知识图谱不是一个单独微服务，而是三层结构

从代码证据看，KG 相关能力分成：

| 层级 | 作用 | 关键文件 |
| --- | --- | --- |
| 图谱浏览/检索层 | 面向查询、浏览、问答时使用   Neo4j 图数据 | `src\tap_ai\application\library_kg.py`   `src\tap_ai\plugins\extensions\knowledge\backends\neo4j_graph.py`   `src\tap_ai\plugins\extensions\knowledge\service.py` |
| 入库层 | 文件解析、切片、embedding、把结果写进 Azure Search 和 Neo4j | `src\tap_ai\plugins\ingest\sdk_ingest.py`、`src\tap_ai\plugins\ingest\embedding.py` |
| 切片读侧 | 从索引里反查文件和 chunk，给管理端浏览/草稿编辑/回溯使用 | `src\tap_ai\plugins\library\azure_chunk_source.py`、`src\tap_ai\application\library_chunks.py`   `src\tap_ai\api\library_chunks.py` |

这说明：图谱抽取、图谱存储、图谱浏览、切片回查不是一段代码包打天下，而是拆在 ingestion / knowledge / library 三个区域里。

## 二、抽取图谱后，数据怎么写入 Neo4j 和向量库；当前向量库怎么实现
这一部分直接说结论：

### 2.1 当前正式入库链路不是“先抽图谱、再分别手写两套存储”
而是通过 `tap_ingest_sdk` 的统一 pipeline：
1. 解析文件
2. 切片
3. 生成 embedding
4. 交给多个 sink 同时写出

关键文件：`src/tap_ai/plugins/ingest/sdk_ingest.py`

最核心证据：
```python
client = TapIngestClient(
    parser_registry=ParserRegistry.default(),
    chunker=DefaultChunker(),
    embedding_provider=self._embedding_provider,
    sinks=sinks,
    work_dir=temp_dir,
)
document = client.process(source)
```
```python
for sink in sinks:
    result = sink.upsert(document)
```
这段非常关键，说明：
- 抽取 / 切片 / embedding 是由 `TapIngestClient.process(source)` 完成的
- 结果通过多个 sink 分发落库
- 不是业务代码自己逐条写 Azure / Neo4j，而是 SDK 统一处理 document 后再 sink.upsert

### 2.2 Neo4j 怎么写入：通过 Neo4jGraphSink
还是在 `sdk_ingest.py` 的 `_sinks_factory`：
```python
from tap_ingest_sdk.sinks._neo4j import Neo4jGraphSink
```

真正实例化写 Neo4j 的地方：
```python
if shared_driver is not None:
    sinks.append(
        Neo4jGraphSink(
            uri=kb.neo4j_uri,
            user=kb.neo4j_user,
            password=...,
            scope=index_name,
            database=kb.neo4j_database,
            driver=shared_driver,
        )
    )
```

能确认的事实有四个：
1. Neo4j 写入不是本仓库自己实现 Cypher upsert，而是交给 SDK 的 `Neo4jGraphSink`。
2. 只有当 Neo4j 配置齐全时才会加这个 sink，也就是：
```python
password = kb.neo4j_password.get_secret_value()
if kb.neo4j_uri and kb.neo4j_user and password:
```
3. 写入时会传 `scope=index_name`。这点很重要，说明在线正式链路里，Neo4j 图谱数据是按 Azure Search `index_name` 当 scope 来分区的。
4. 所以图谱写入是否发生，不是“总会发生”，而是Neo4j配置存在时才一起写。

### 2.3 向量库怎么写入：通过 AzureAISearchSink
同样在 `_sinks_factory`：
```python
from tap_ingest_sdk.sinks._azure import AzureAISearchSink
```

实例化代码：

这说明当前项目里“向量库”并不是 Milvus / Qdrant / FAISS / PGVector，而是：
> Azure AI Search 索引本身既存 chunk 文本，也存向量字段。

也就是说，当前“向量库”的实现方式是 Azure AI Search 充当向量检索库。

### 2.4 当前向量库实现的直接证据：有向量字段维度校验
如果只是普通关键词索引，不会做向量维度校验。但项目明确在装配阶段校验索引向量字段维度。

代码证据：
```python

```
里面会读取 Azure Search index 的某个字段：

而知识库配置里也写死了默认向量字段名：

文件：`src/tap_ai\plugins\extensions\knowledge\settings.py`
```python

```

这个证据足够说明：
- Azure Search 索引中存在向量字段 `content_vector`
- 入库向量维度必须与该字段维度一致
- 所以当前向量存储的载体就是 Azure Search index

### 2.5 当前 embedding 是怎么生成的
embedding 提供者在：`src\tap_ai\plugins\ingest\embedding.py`

核心类：
```python
class GatewayEmbeddingProvider:
```
核心实现：
```python
def embed(self, texts: Sequence[str]) -> list[list[float]]:
    items = list(texts)
    vectors: list[list[float]] = []
    for start in range(0, len(items), self._batch_size):
        batch = items[start : start + self._batch_size]
        if not batch:
            continue
        vectors.extend(self._gateway.embed(model=self._model, texts=batch))
    return vectors
```
这段代码说明当前向量写入不是由 Azure 自动算，而是：
1. chunk 文本先交给 `GatewayEmbeddingProvider.embed(...)`
2. 它再调用模型网关 `self._gateway.embed(...)`
3. 得到向量后，SDK 在 sink 写入前把向量回填到切片上

这一点文件头注释也直接写了：
> SDK 在写 sink 之前调用 `embed`，把返回的向量回填到切片上

### 2.8 总结：当前 Neo4j 与向量库存储实现方式
可以非常明确地下结论：

**Neo4j 存储**
- 正式链路：`tap_ingest_sdk.sinks._neo4j.Neo4jGraphSink`
- 由谁触发：`SdkIngestAdapter.ingest_file()` 中 `TapIngestClient.process(source)` 之后，统一 `sink.upsert(document)`
- 何时启用：配置了 `neo4j_uri + neo4j_user + neo4j_password` 时
- 存什么：从查询代码和 POC 脚本可以确认至少包含 `Entity / Chunk / Document` 以及它们之间的关系

**向量库存储**
- 当前实现不是独立向量数据库，而是 Azure AI Search 索引
- 写入类：`tap_ingest_sdk.sinks._azure.AzureAISearchSink`
- 向量字段：`content_vector`
- 向量来源：`GatewayEmbeddingProvider -> model_gateway.embed(...)`
- 写入时机：同样是在 `sink.upsert(document)` 阶段写入索引

## 三、怎么获取切片进行抽取
这一部分要分清楚：你问的“获取切片进行抽取”，在代码里实际上有两条链路。
1. 正式入库抽取链路：文件 -> parser -> chunker，切片是在 ingest pipeline 内部生成的
2. 图谱/管理回查链路：已入库后，再从 Azure Search 把 chunk 读出来

这两条链路不要混在一起。

### 3.1 正式抽取时，切片不是先从数据库查出来的，而是 TapIngestClient 现场切出来的
文件：`src\tap_ai\plugins\ingest\sdk_ingest.py`

最直接证据：201行
```python
source = SourceDocument.from_bytes(
    content,
    filename=file_name,
    idempotency_key=document_key,
    document = client.process(source)
```

这段已经很清楚：
- 输入是文件二进制 `content`
- 先包装成 `SourceDocument`
- 使用 `ParserRegistry.default()` 做解析
- 使用 `DefaultChunker()` 做切片
- `client.process(source)` 产出 `document.chunks`

也就是说：

抽取用的切片，在正式入库链路里，是 SDK 解析文件后现场生成的，不是业务代码先查某个 chunk 表再拿去抽。

### 3.2 切片结果如何回到业务层
同一个文件里，`SdkIngestAdapter` 会把 SDK 的 chunk 对象转成业务契约层的 `IngestChunk`。

代码证据：
```python
chunks = tuple(_to_ingest_chunk(chunk) for chunk in document.chunks)
```

转换函数：
```python
def _to_ingest_chunk(chunk: Any) -> IngestChunk:
    metadata = chunk.metadata
    part_index = getattr(metadata, "chunk_index", None)
    return IngestChunk(
        chunk_id=str(getattr(metadata, "chunk_id", "") or ""),
        part_index=int(part_index) if isinstance(part_index, int) else 0,
        content=str(chunk.content or ""),
        page_or_sheet=getattr(metadata, "page_or_sheet", None) or None,
    )
```

这说明抽取出来的 chunk 至少包含：
- `chunk_id`
- `chunk_index`
- `content`
- `page_or_sheet`

### 3.3 如果是管理端/浏览端要看切片，是从 Azure Search 反查，不是从 Neo4j 读正文
文件：`src\tap_ai\plugins\library\azure_chunk_source.py`

切片读取接口：107行
```python
async def list_chunks(
    self, *, saas_id: str, file_id: str, page: int, page_size: int
) -> tuple[list[ChunkView], int]:
```

它的实现是直接查询 Azure Search：112行
```python
results = await self._search(
    client,
    search_text="*",
    filter_expression=_document_filter(file_id),
    select=_CHUNK_SELECT,
    order_by=["chunk_index asc"],
    top=page_size,
    skip=(page - 1) * page_size,
    include_total_count=True,

```

而 `_CHUNK_SELECT` 明确只取这些字段：
```python
_CHUNK_SELECT = (
    "chunk_id",
    "document_id",
    "source_file",
    "page_or_sheet",
    "content",
    "chunk_index",
)
```

这就是“怎么获取切片”的第二条证据链：
- 对已入库文件，切片内容从 Azure AI Search 读
- 不是从 Neo4j 读全文
- Neo4j 更多是用来存实体/关系/chunk 关联，不是全文主存储

# 四、把三件事串起来后的整体结论

问题1：知识图谱模块与内容是什么？

结论：
- 图谱浏览/检索模块：`application\library_kg.py`、`plugins\extensions\knowledge\backends\neo4j_graph.py`
- 图谱增强问答模块：`plugins\extensions\knowledge\service.py`
- 图谱写入并不在 browse 层，而在 ingestion pipeline 里通过 SDK sink 完成：`plugins\ingest\sdk_ingest.py`
- 图模型从现有 Cypher 和查询代码看，至少包含：`Entity`、`Document`、`Chunk`、`HAS_CHUNK`、`MENTIONED_IN` 以及多类业务边

问题2：抽取图谱后数据怎么存入 Neo4j 和向量库？当前向量库怎么实现？

结论：
- Neo4j 写入：通过 `tap_ingest_sdk.sinks._neo4j.Neo4jGraphSink`
- 向量库存储：不是独立向量 DB，而是 Azure AI Search 索引里的向量字段 `content_vector`
- 向量生成：`GatewayEmbeddingProvider` -> `model_gateway.embed(...)`
- 统一写出机制：`TapIngestClient.process(source)` 之后，遍历 sinks 执行 `sink.upsert(document)`

问题3：怎么获取切片进行抽取？

结论：
- 正式抽取时的切片来源：不是查库，而是 `TapIngestClient` 通过 `ParserRegistry.default()` + `DefaultChunker()` 现场从原始文件生成
- 抽取完成后回看切片：通过 `AzureChunkSource.list_chunks()` 从 Azure Search 反查 `chunk_id/document_id/content/chunk_index/page_or_sheet`
- 图谱按实体反查 chunk：先在 Neo4j 走 `Entity -[:MENTIONED_IN]-> Chunk` 拿 `chunk_id`，再由检索侧去取正文
