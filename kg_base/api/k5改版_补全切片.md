【任务 K5 改版】从 Azure AI Search 的 jp-poc 索引补全 Neo4j 中 jp-poc 的切片：对齐切片编号、补正文摘要、修正文件名和页码。Azure 只读；Neo4j 只写 scope='jp-poc'。
（先贴【通用规则】）

【背景】
Neo4j 中 jp-poc 有 16,427 个切片，只有 1,300 个有摘要（preview）；部分 source_file 是乱码；切片编号是 POC 的算法 sha256(正文)[:12]，和 Azure 索引的主键（sha1(source_file:locator:part)[:12]）不同。Azure 的 jp-poc 索引里有完整正文和正确文件名。
做法：读取 Azure 中 jp-poc 索引的全部切片，对每条正文计算 sha256[:12]，与 Neo4j 中的切片编号对上；对上的，把切片编号改成 Azure 主键（旧编号保存在 poc_chunk_id），并用 Azure 的数据补全摘要、文件名、页码、文档编号。改完后满足全系统的约定："Neo4j 的 Chunk.chunk_id = Azure 切片主键"。

【要做的 6 件事】

1. 读取 Azure（只读）：
   a. get_document_count()；超过 100,000 退出
   b. search(search_text="*", select=[C4 的 5 个字段], top=1000) 分页读取全部切片
   c. 对每条：poc_id = sha256(正文.encode("utf-8")).hexdigest()[:12]；同时计算 sha256(正文.strip()) 的结果作为备用
   d. 建两个对照表：poc_id → [Azure 切片...]（同一 poc_id 可能有多条）；备用 id → [Azure 切片...]

2. 读取 Neo4j 中 scope='jp-poc' 的全部 Chunk：chunk_id、poc_chunk_id、document_id、source_file、page_or_sheet、remap_status
   - 已有 poc_chunk_id 且 remap_status='matched' 的：跳过（可重复运行）

3. 匹配分类（每个 Neo4j 切片恰好落入一类）：
   matched_hash      ：chunk_id 在第 1 个对照表中恰好对应 1 条 Azure 切片
   matched_strip     ：第 1 个表没对上，在备用表中恰好对应 1 条
   matched_locator   ：前两个表对应多条时，用"修正后的文件名 + 页码"筛选后恰好剩 1 条
   ambiguous         ：对应多条且筛选后仍不止 1 条
   unmatched         ：一条都对不上
   conflict          ：目标 Azure 主键已被另一个 Neo4j 切片占用，或两个 Neo4j 切片对上同一条 Azure 切片
   文件名修正函数 fix_mojibake(s: str) -> str：
     尝试 s.encode("cp437").decode("utf-8")；成功且结果含日文或中文字符时返回结果，否则原样返回。写中文注释说明：
     "POC 压缩包解压时把 UTF-8 文件名当成 cp437 读了，这里还原"
     比较文件名时两边都先 fix_mojibake 再去掉首尾空白

4. 写入（只有加 --write 才执行；默认只预演）：
   a. 写前：调用全局计数函数，打印所有 scope 的节点数
   b. 三种 matched：
      SET c.poc_chunk_id = 旧 chunk_id（已有就不覆盖）,
          c.chunk_id = Azure 主键,
          c.preview = Azure 正文前 200 个字符,
          c.source_file = Azure 文件名,
          c.page_or_sheet = Azure 页码（Azure 为空时保留原值）,
          c.azure_document_id = Azure 文档编号,
          c.remap_status = 'matched',
          c.remap_method = 'hash' / 'strip' / 'locator',
          c.remapped_at = 当前毫秒时间戳
      注意：不改 c.document_id（它是 Neo4j 中 Document 节点的关联键，改了会断开文档和切片的关系）
   c. ambiguous / unmatched / conflict：只 SET c.remap_status、c.remapped_at；chunk_id 不变；c.source_file = fix_mojibake(原值)；c.preview 为空时不处理
   d. Document 节点（scope='jp-poc'）：filename / source_file 改为其下 matched 切片中出现次数最多的 Azure 文件名；没有 matched 切片的，改为 fix_mojibake(原值)。document_id 不变
   e. 每批 500 条，用 UNWIND；所有语句经过 kg_import_poc.py 的 scope 检查执行函数（能 import 就 import，不能就照抄同名函数并注明来源）
   f. 写后：再次调用全局计数函数；除 jp-poc 外任一 scope 的数字有变化，打印醒目警告并以非 0 状态退出
   g. 写入前检查唯一性：所有将要写入的新 chunk_id 互不重复，且不与 jp-poc 中现有的其他 chunk_id 重复；有重复的切片归入 conflict，不写 chunk_id

5. 输出（预演和正式运行都打印）：
   - Azure 切片数、Neo4j jp-poc 切片数、本次跳过数
   - 六种分类各多少；matched 合计占比
   - 预计补上摘要的切片数；修正文件名的 Document 数
   - ambiguous / unmatched / conflict 各打印前 5 个例子（chunk_id、修正后文件名、页码），不打印正文
   - 最后一行：预演时打印"预演结束，未写入任何数据"；正式运行打印"写入完成"

   e. --write 模式：写语句的参数中 scope 都是 jp-poc；没有修改 document_id；conflict 的切片没有改 chunk_id
   f. 源码断言：不出现第【绝对禁止】中列出的 Azure 写方法和 SearchIndexClient；不出现 CREATE、MERGE、DELETE、REMOVE、DROP
