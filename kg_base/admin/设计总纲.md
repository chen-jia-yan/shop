D. 状态
- 文档 status：pending（待处理）→ processing（处理中）→ indexed（已索引）/ failed（失败）
  · 已索引的文档上传了新版本：回到 pending，旧版本的切片在新版本处理成功之前仍然可以检索到
- 任务 status：pending → processing → succeeded / failed
  · 处理失败、attempts < max_attempts：任务回到 pending，记下错误
  · 处理失败、attempts >= max_attempts：任务记为 failed，文档记为 failed，last_error 写入失败原因
  · 心跳超时：同样按上面两条处理

E. 数据表（sql/003_create_library_kb_tables.sql，只写文件、不执行）
通用列、租户字段、COMMENT、字符集、引擎、索引命名，全部照抄 sql/002 中 library_chunk_draft 的写法。
1. library_kb_document（一个文件一行）
   file_name VARCHAR(512)：原始文件名（只用于显示）
   name_key VARCHAR(512)：规范化后的文件名，用于判断是不是同一个文件
   file_ext VARCHAR(16)、size_bytes BIGINT、content_sha256 VARCHAR(64)（从索引同步来的文档为空字符串）
   storage_path VARCHAR(1024) NULL：当前版本文件在存储中的路径
   document_key VARCHAR(64)：传给 SDK 的固定文档编号（idempotency_key），创建后永远不变
   status VARCHAR(16)、chunk_count INT、last_error TEXT NULL
   origin VARCHAR(16)：upload（上传）/ index_sync（从索引同步）
   indexed_time BIGINT NULL
   唯一索引：(saas_id, name_key)、(saas_id, document_key)；普通索引：(saas_id, status)、(saas_id, content_sha256)
2. library_kb_job（每处理一次一行）
   document_id VARCHAR(32)、batch_id VARCHAR(32)：同一次上传的文件，batch_id 相同
   file_name VARCHAR(512)、content_sha256 VARCHAR(64)、size_bytes BIGINT、storage_path VARCHAR(1024)
   status VARCHAR(16)、attempts INT、max_attempts INT
   error_code VARCHAR(64) NULL、error_message TEXT NULL、chunk_count INT NULL
   heartbeat_time BIGINT NULL、started_time BIGINT NULL、finished_time BIGINT NULL
   索引：(status, create_time)、(status, heartbeat_time)、(document_id)

F. 规则（core/library_kb/rules.py，纯函数，不做任何 IO）
1. normalize_name(file_name)：去掉路径部分，只留文件名；去掉首尾空白；Unicode NFKC 规范化；转小写
2. 文件名安全：包含 ..、/、\、控制字符，或者规范化后为空 → 拒绝"文件名不合法"
3. document_key 生成：新文档用 "doc::" + uuid4().hex[:16]（和 SDK 的文档编号格式一致）；从索引同步的文档，用索引中已有的 document_id
4. classify_upload(...)：输入是本次上传的文件信息，加上按 name_key、content_sha256 查到的已有文档。按顺序判定，命中第一条就返回：
   ① 类型不在白名单 → rejected "不支持的文件类型"
   ② 大小为 0 → rejected "文件为空"；超过上限 → rejected "文件超过大小上限"
   ③ 同一次上传中 name_key 重复 → 第二个及之后的 rejected "同一批次中文件名重复"
   ④ 同名文档存在、状态为 pending 或 processing：内容相同 → skipped "已在处理中"；内容不同 → rejected "该文件正在处理中，请稍后再上传"
   ⑤ 同名文档存在、内容相同、状态为 indexed → skipped "内容未变化"
   ⑥ 同名文档存在、内容相同、状态为 failed → queued "重新处理失败的文件"（沿用原文档）
   ⑦ 同名文档存在、内容不同 → queued "文件已更新"（沿用原文档和 document_key）
   ⑧ 没有同名文档，但同一租户下有另一个文档内容相同 → skipped "与 {那个文档的 file_name} 内容相同"
   ⑨ 其他 → queued "新文件"（新建文档）
   返回值：result（queued / skipped / rejected）、reason（上面的中文原文）、existing_document_id（沿用时）

G. 插座（contracts/library_kb.py）
from dataclasses import dataclass
from typing import Protocol

@dataclass(frozen=True)
class IngestOutcome:
    succeeded: bool
    chunk_count: int = 0
    error_code: str | None = None
    error_message: str | None = None

class IngestPort(Protocol):
    # 同步函数：由后台处理用 asyncio.to_thread 调用。只处理一个文件；不抛异常，失败通过 IngestOutcome 返回
    def ingest_file(self, *, saas_id: str, document_key: str, file_name: str, content: bytes) -> IngestOutcome: ...

@dataclass(frozen=True)
class IndexedDocument:
    document_key: str
    source_file: str
    chunk_count: int

class IndexInventoryPort(Protocol):
    # 只读：列出这个租户的索引中已有的文档
    async def list_documents(self, *, saas_id: str) -> list[IndexedDocument]: ...

I. 上传的处理步骤（application/library_kb.py 的 upload）
1. 校验：saas_id 非空；文件数量 1 到上限（0 个 → "未选择文件"，超过 → "上传文件数量超过上限"）；IngestPort 不为 None
2. 对每个文件：分块流式写入存储，路径为 {storage_prefix}/{saas_id}/{新的任务 id}.{扩展名}，边写边计算 sha256 和大小；
   超过大小上限时立即停止写入，删除已写入的部分
3. 按 name_key、content_sha256 查询已有文档，调用 classify_upload
4. skipped、rejected 的文件：删除刚才写入的存储文件
5. queued 的文件：在同一个数据库事务里，写入或更新文档（status=pending）并新增任务（status=pending）；
   更新已有文档时，用带条件的更新（文档当前状态不是 pending、processing 才能更新），更新失败就按 ④ 处理
6. 新建文档时违反唯一索引（另一个请求同时上传了同名文件）：这个文件记为 rejected "该文件正在被其他请求上传"，并删除存储文件
7. 写一条审计记录，写法照抄 application/files.py 中的 _upload_audit_event（action 为 "library_kb.upload"）

J. 后台处理（application/library_kb_worker.py）
- 只有 library_kb_worker_enabled 为 True、并且 IngestPort 不为 None 时才启动；在 main.py 的启动流程中启动，关闭时停止（等当前文件处理完或超时，再取消）
- 循环：每隔 poll_sec 秒：
  ① 恢复中断的任务：status=processing 且 heartbeat_time 早于 now - stale_sec 的任务，按 D 节规则处理
  ② 取出最多 concurrency 个 pending 任务（按 create_time 升序），逐个"抢"：
     UPDATE ... SET status='processing', attempts=attempts+1, started_time=now, heartbeat_time=now WHERE id=? AND status='pending'，
     影响行数为 1 才算抢到（多个实例同时运行时，只有一个能抢到）；同时把文档改为 processing
  ③ 处理一个任务：从存储读出文件内容 → 启动心跳（每 heartbeat_sec 秒更新 heartbeat_time）→
     await asyncio.wait_for(asyncio.to_thread(ingest.ingest_file, ...), timeout=job_timeout_sec) → 停止心跳
  ④ 成功：任务 succeeded（写入 chunk_count、finished_time）；文档 indexed（chunk_count、indexed_time、content_sha256、size_bytes、storage_path 更新为这个任务的值，last_error 清空）；
     删除文档上一个版本的存储文件（路径与新版本不同时才删，删除失败只记 warning）
  ⑤ 失败（IngestOutcome.succeeded 为 False、抛异常、超时）：按 D 节规则处理；超时时注明"处理超时"
- 单个任务的任何异常都不能让整个循环停止。循环本身出错时记 warning，下一轮继续
- 已知限制：超时后线程无法强制停止，会在后台继续运行到结束，结果被丢弃（写进代码注释）
