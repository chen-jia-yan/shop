# worker 日志问题分析
> 问题现象：看一下运行的worker的log情况，没有一个上传完成，分析下

PowerShell查看进程命令
```powershell
Get‑CimInstance Win32_Process | Where‑Object { $_.Name ‑eq 'python.exe' } | Select‑object ProcessId,ParentProcessId,ExecutablePath,CommandLine
```

## 结论先说
现在不是“worker 没跑”，而是现场被两个 worker 叠在一起了，并且还混出了 base Python 子进程，导致状态和进程树都被污染，所以才会看起来一直没有一个真正完成。这不是单一文件慢那么简单，是运行现场不干净 + 新 bug + 旧 processing 残留一起叠加。

## 已确认事实梳理表

| 已确认事实 | 依据 | 意味着什么 |
|---|---|---|
| 目前有 2 个 worker 主进程 | PID 3872 是 `.venv312\\python -m kb_admin.worker`，PID 22724 是 base Python `python.exe -m kb_admin.worker` | 你现在不是单 worker 在跑，现场已经重叠了 |
| heavy 子进程也出现 双层进程 | 例如 22724 ‑> 27404(.venv312 process_one_file) ‑> 4960(base Python process_one_file) | 又回到了之前那个“base Python / venv Python 混跑”的问题 |
| 15:35 之后这轮新 worker 确实启动了 | worker.log 有 `worker started ... heavy_limit=2`，并且 started heavy file_id=129/130 | 调度主循环是活的，不是假卡 |
| DocumentChunk 的错已经过去了，但又撞上新错 | 15:56 和 16:02 报：`'AzureSearchStore' object has no attribute 'count_document_chunks'` | 现在真正卡住完成的是索引/同步链路 bug，不是 parser 参数 |
| state.db 裡有 12 条 processing 一直挂著 | 多数 error 是 `worker restarted while files were in‑flight` | 这批不是正常 processing，而是历史残留/重启污染後没收乾净 |
| 两条正在跑的 heavy 是 18 和 62 | 日志16:02 开始；进程树也对上 | 现在机器其实在真跑，但不是在健康现场裡真跑 |

## 最关键的根因
1. 你现在现场有两个 worker：
    一个是 `.venv312` 的，另一个是 base Python 的。这会导致同一个 `state.db` 被两套 worker 竞争 claim、启子进程、写状态。
2. base Python 混入问题没有彻底消失。虽然 worker.log 显示 .venv312 启动了 worker，但进程树证明 base Python 仍在跑 `kb_admin.worker` 和 `kb_admin.process_one_file`。
3. 当前没有“上传完成”的直接技术原因，是新的 Azure 同步 bug：
    ```
    error='AzureSearchStore' object has no attribute 'count_document_chunks'
    ```
    这说明文件前半段很可能已经跑到索引/同步附近了，但在管理层同步或索引统计这一步炸掉了，所以没法落到 completed。
4. processing 状态被污染得很重。12 条 processing 裡，大部分错误信息其实已经是 `worker restarted while files were in‑flight`。这批不代表“正在健康处理”，而是“之前重启中断後遗留下来的 processing”。

> 所以，现在不是让我们继续盯 log 就能解决，要先把现场清乾净，再修 `count_document_chunks` 这个索引同步 bug。不然就算再重启，也只是在脏现场裡反覆 claim 和 crash。

## 明确判断
- 第一优先 bug：`AzureSearchStore` 缺少 `count_document_chunks`
- 第一优先现场问题：双 worker + base Python 混跑
- “没有一个完成”不是因为 OCR 本身完全跑不动，而是跑完前后链路又炸了
