# 项目专属(本项目;换项目时只改这一段)

## 项目背景

- 日文保险知识库agent:保险文档(含 PPT/Excel/PDF 图片里的日文)处理后入库,供业务员检索问答。

- 技术栈:Python 3.12;本地 PaddleOCR;Azure AI Search;embedding 用 text-embedding-3-large

- 环境:Windows,虚拟环境 .venv312(底座是 AppData 的 Python,venv 为启动壳)。

## 处理流程(单趟,已不是两阶段)

- 上传 → 入队(SQLite)→ worker 领取 → 解析 + OCR(一趟做完)→ 切片 → embedding → 写入 Azure AI Search。

- 状态机:`pending → processing → completed / failed / dead`(两阶段已合并,不再有 text_done/ocr_pending/ocr_processing)。

## 关键文件(以实际代码为准)

- `kb_admin/worker.py`:worker 主循环、claim、进程池与崩溃恢复、单实例锁。

- `kb_admin/state_store.py`:SQLite `files` 状态机(claim_pending / enqueue_files / mark)。

- `kb_admin/process_one_file.py`:重文件隔离子进程。

- `kb_admin/ingestion.py` / `kb_poc/ingestion/ingestor.py`:切片(`_chunk_document` / `_chunk_profile`,参数读模块级全局)。

- `kb_poc/parsing/ppt_ocr.py`:OCR 封装。`kb_poc/retrieval/embedding.py`:embedding。

- `kb_poc/ui/api_admin.py`:上传接口。`kb_chunk_studio/`:切片可视化工作台(独立模块)。

- 全量入库:`python -m kb_poc ingest`(单进程,最稳)。

## 硬性约束

- 不下载新依赖;不动 PaddleOCR 本地模型缓存;全本地,数据不外发第三方。

- Windows 多进程用 spawn;启动进程的代码放在 `if __name__ == "__main__":` 下。

- 派生子进程、运行都用 .venv312 的 `sys.executable`。

## 已知坑(别再犯)

- 子进程一律用 `sys.executable`,绝不用裸 `python`/系统 Python312(否则跑到无依赖的 base,导入失败/幽灵进程)。

- worker 不要再启动另一个 worker。

- OCR 引擎每进程只初始化一次并复用(否则极慢);mkldnn 本机可能卡死,慎开。

- embedding 是共享受限资源:别多进程猛发(会 429);全局限速 + 请求内批量 + 尊重 Retry-After。

- 不因重跑就清空库/索引;靠文件哈希做增量。硬杀后 `worker.pid.lock` 需手删。
- embedding 单输入上限 8192 token;保留表格完整性会超 → 在 embedding 层分窗合并兜底,不改切分。
