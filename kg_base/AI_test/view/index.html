需求分析模块

PRD 文档 → AI 解析 → 结构化测试点
▼

🎯 为什么这样设计

测试人员最大的时间黑洞不是写用例，而是读需求——一份 50 页的 PRD，逐字读完再提取测试点，半天就没了。所以这个模块不是"辅助阅读"，而是AI 直接产出结构化测试点，人只做确认。这就是为什么它排在流水线第一位：它是整个链条的入口，这里出错，后面全错。

架构决策
选用 Azure AI Document Intelligence 做文档预处理（而非直接丢全文给 GPT-4o），原因是：PDF 里的表格、图片、分栏布局，直接塞给 LLM 会丢失结构信息。先用 Document Intelligence 转成结构化 Markdown，再送给 GPT-4o 做语义理解，准确率提升 30%+。

⚠️ 难点

  • 长文档截断：GPT-4o 上下文窗口 128K，但一份 200 页的 PRD 可能超。需要做分段 + 摘要 + 合并，分段策略本身就可能丢失跨章节的关联信息。
  • 需求质量评分的主观性：AI 评分"完整性/无歧义性/可测试性"本身就有歧义——不同 prompt 模板打出的分可能差 20 分。需要校准集。
  • 与 Azure DevOps 的双向同步：DevOps 里的 User Story 可能随时被 PM 修改，平台里的解析结果会过时。需要 Webhook 监听变更事件，触发重新解析。

💡 亮点

  • 置信度分层：每个提取的测试点都带 confidence 字段（0.0~1.0），低于 0.7 的标记为「待人工确认」，高置信度的直接放行。这避免了「AI 全对或全错」的二元困境。
  • 历史需求相似度匹配：新需求来了，AI Search 先检索有没有类似的历史需求，如果有，直接复用之前的测试点结构，减少重复工作。

🕳️ 可能踩的坑

  • 需求文档里嵌了截图，但截图里的文字 Document Intelligence 识别不出来（手写、特殊字体），导致 AI 分析遗漏。
  • PM 用「应该」「大概」「可能」这类模糊词，AI 无法判断，需要人介入。
  • DevOps 同步延迟：如果 PM 改需求的同时测试已经在跑，结果可能对不上。

测试用例生成模块

测试点 → RAG 检索 → GPT-4o 生成 → 用例清单
▼

🎯 为什么这样设计

单纯让 AI 硬想用例，它会产出大量格式正确但毫无价值的废话——"验证登录功能正常"这种用例谁都会写。真正有价值的是「结合历史用例库 + 需求上下文」生成的有针对性的用例。所以这里用了 RAG 模式：AI Search 向量检索 → 召回相似历史用例 → 注入 Prompt → GPT-4o 生成。

策略选择器
Azure Function 根据需求特征自动推荐测试策略：涉及数值范围 → 边界值分析；多条件组合 → 判定表；状态流转 → 状态迁移。测试人员可以在 Power Apps 中切换策略，但默认推荐已经覆盖 90% 的场景。

⚠️ 难点

  • Token 溢出：一条需求可能生成 50+ 条用例，每条用例 5-10 个步骤，一次性输出可能超 max_tokens。解决方案是分批生成（每批 20 条），但分批可能导致上下文断裂。
  • 用例去重：AI 生成的新用例和已有用例可能有 80% 的语义重叠。用 AI Search 向量相似度做去重，阈值设太高误杀，设太低留冗余。
  • Prompt 模板的选择：功能测试、API 测试、UI 测试、性能测试、安全测试 5 类模板，各有不同的输出结构。选错模板，生成的用例结构对不上 Dataverse 表字段。

💡 亮点

  • 温度双轨：生成用例用 temperature=0.3（保证稳定性），但「边界条件头脑风暴」用 temperature=0.8（鼓励发散），两种模式在同一个 Function 里切换。
  • AI 自动标注 testDataType：Positive / Negative / Boundary / Error 四类，AI 生成时就标注好，不用人再分类。

🕳️ 可能踩的坑

  • 生成的用例里「预期结果」字段为空——AI 觉得「显而易见」就省略了，但人执行时需要明确的验证点。
  • RAG 检索到的历史用例质量差（本身就是垃圾用例），AI 会「学习」这些坏模式。
  • 批量生成时，第 1 批和第 3 批的风格可能不一致（因为每批是独立的 API 调用）。

用例评审模块

AI 四维度打分 → 低分拦截 → 人工评审 → 反馈闭环
▼

🎯 为什么这样设计

传统评审的痛点是：评审人花 80% 时间在挑低级错误（步骤不完整、预期结果缺失、重复用例），只剩 20% 精力关注业务逻辑。这个设计把 AI 放在人工评审之前——AI 先筛一遍低级问题，评分低于 60 分的直接退回，不进入人工队列。人工只关注「业务逻辑是否正确」。

四维度评分体系
完整性（步骤是否完整、预期结果是否明确）· 正确性（逻辑是否自洽、与需求是否一致）· 可执行性（是否有明确的执行条件）· 冗余度（与本模块其他用例/历史用例是否重复）。每个维度独立打分，加权平均，低于阈值直接拦截。

⚠️ 难点

  • AI 评审的「正确性」判断不可靠：AI 可以判断用例逻辑是否自洽，但「与需求是否一致」这个维度需要理解业务上下文，AI 经常误判。
  • 冗余度检测的误杀：两条用例虽然相似但覆盖不同场景，AI 可能判定为重复。
  • 评审反馈闭环的冷启动：评审人的修改和驳回记录要作为 AI 的训练数据，但初期数据量不够，AI 不会变聪明。

💡 亮点

  • 低于阈值直接退回：完整性 < 60 分的用例不进入人工队列，减少无效评审。退回时附 AI 具体修改建议，不是笼统的「请修改」。
  • 评审反馈闭环：每次人工驳回时记录原因（结构化 code + message），定期汇总后用于 prompt 优化，形成「越用越准」的正循环。

🕳️ 可能踩的坑

  • 评审人直接「全部通过」而不看 AI 建议——需要设计「必须逐条确认」的交互，不能一键通过。
  • AI 建议过于保守，什么都说「建议补充」，导致通过率过低。

自动化脚本生成模块

用例 → GPT-4o-mini → Playwright 脚本 → 冒烟验证
▼

🎯 为什么这样设计

脚本生成是成本最敏感的一环——一个项目有几百条用例，每条都要生成脚本。如果用 GPT-4o，Token 费用会爆。所以这里用 GPT-4o-mini（成本是 GPT-4o 的 1/10），并且生成后自动跑冒烟验证（只验证脚本能跑起来，不验证逻辑正确性）。

三种生成策略
UI 测试：优先 Playwright，支持三种定位方式——先录后改（Playwright Codegen 录制 → AI 优化）、AI 根据截图+描述推断选择器、手动补充 selector。API 测试：直接生成 Playwright APIRequestContext 代码。数据验证：SQL 查询或 API 断言代码。三种策略共用一个代码生成 prompt 模板，但注入不同的上下文。

⚠️ 难点

  • 元素定位是最大痛点：AI 生成的 selector（如 page.locator('#login-btn')）在真实页面上可能不存在。需要 Page Object Map 表（Dataverse ElementMap）做定位映射。
  • 生成代码的 lint 通过率：AI 生成的 TypeScript 可能语法错误，需要 ESLint + TypeScript 编译检查，失败后自动修复 1-2 轮。
  • 代码风格一致性：AI 每次生成的代码风格不同，需要从项目已有脚本中提取代码风格（通过 AI Search 检索），注入 prompt 要求一致。

💡 亮点

  • 冒烟验证 + 自修复循环：生成后自动在 sandbox 跑一次，失败则让 AI 自己修 1-2 轮，仍失败才标记人工介入。这能自动修复约 60% 的简单问题。
  • Page Object 自动维护：当 UI 变更导致脚本失败时，失败分析模块触发 POM 更新建议，AI 生成新的定位策略。

🕳️ 可能踩的坑

  • GPT-4o-mini 对复杂业务逻辑的代码生成能力不足，生成的脚本逻辑有 bug 但语法正确（冒烟通过 ≠ 逻辑正确）。
  • ElementMap 表维护成本高：每个页面每个元素都要手动录入，初期工作量巨大。

测试执行模块

Power Automate 调度 → 容器化 Playwright 执行 → 实时回传
▼

🎯 为什么这样设计

执行模块的架构选择是Azure Functions + 容器化 Playwright，而不是传统的 VM 上跑 Jenkins Agent。原因：Functions 按需付费，没任务时不花钱；容器化保证每次执行环境一致；支持水平扩展（50+ 并行实例）。

执行队列与并行控制
执行任务写入 Dataverse 队列 → Power Automate 轮询 → 按优先级和环境分组调度 → Azure Functions 拉取执行。关键设计：同一环境下的脚本串行（避免数据冲突），不同环境间并行。通过 Functions 的 concurrency 控制 + 队列分区实现。

⚠️ 难点

  • Playwright 浏览器在 Functions 上的内存消耗：一个 Chromium 实例约 500MB，Functions 内存上限可能不够，需要 Premium Plan 或 Container Apps。
  • 执行超时：Azure Functions 默认 5 分钟超时（消耗计划），长测试需要 Premium Plan（无限制）或 Durable Functions。
  • 实时状态推送：Power Apps 需要实时看到执行进度，但 Functions 是无状态的。方案是 SignalR Service 推送，或用定时写 Dataverse 状态字段 + 前端轮询。

💡 亮点

  • 失败自动重试一次：配置化重试策略，第一次失败自动重跑（排除环境问题导致的 flaky）。重试仍失败才进入失败分析。
  • Playwright Trace 保留：失败时自动保留完整的 Playwright Trace（含 DOM 快照、网络请求、控制台输出），供失败分析模块使用。

🕳️ 可能踩的坑

  • Functions 冷启动 + 下载浏览器二进制，首次执行可能耗时 2-3 分钟。需要预热或使用 Always Ready 实例。
  • 并行执行时，测试数据互相污染（比如两个脚本同时操作同一个测试账号）。需要环境隔离 + 数据隔离策略。

失败分析模块

失败分类 → AI 根因推理 → 自修复 → 自动提单
▼

🎯 为什么这样设计

这是整个平台 AI 最核心的环节。传统自动化测试最大的痛点是：跑完 1000 条，失败 50 条，3 个人花一整天排查。AI 能做到的是：自动分类 + 归因 + 历史匹配 + 自修复尝试 + 自动提单。五步流水线，每一步都在降低人的工作量。

五类失败分类（关键设计）
类别说明自动修复
SCRIPT_BUG脚本问题：selector 失效、等待不足高
ENV_ISSUE环境问题：服务不可用、数据被清理低
PRODUCT_BUG业务逻辑缺陷：预期与实际不符低（需人工）
FLAKY偶发失败：上次成功，本次失败中（重试）
DATA_ISSUE测试数据问题：被污染、未初始化中

⚠️ 难点

  • 多模态分析：失败原因可能在截图里（按钮没渲染）、trace 里（网络请求超时）、日志里（异常堆栈）。GPT-4o 需要同时消化这三种输入，但截图 + trace 的 token 消耗巨大。
  • Flaky 检测：判断一个失败是 flaky 还是稳定缺陷，需要对比历史执行记录。同一用例最近 5 次执行中 3 次成功 2 次失败 → flaky。但阈值设置是门学问。
  • 历史匹配的冷启动：初期没有足够的历史失败记录，向量检索什么都找不到。

💡 亮点

  • 关键字预分类 + LLM 兜底：先用正则匹配错误信息（如 "TimeoutError" → SCRIPT_BUG），命中率 70%。未命中才调 GPT-4o，节省 Token。
  • 自修复仅限 SCRIPT_BUG：AI 尝试修改脚本（更新 selector 或等待条件），重新执行一次。成功则标记「自动修复」，不产生告警。失败则标记人工。
  • 自动创建 Bug 草稿：确认是 PRODUCT_BUG 后，AI 生成包含失败步骤、截图、日志片段、根因分析的 Bug 描述，推送到 Azure DevOps，由人工确认后提交。

🕳️ 可能踩的坑

  • AI 分类错误：把 PRODUCT_BUG 误判为 SCRIPT_BUG，然后「自修复」改了脚本，结果把真正的缺陷掩盖了。
  • Flaky 判定阈值设太高，真正的间歇性缺陷被当作 flaky 忽略。
  • 自动提单的 Bug 描述太长，开发人员不读。

报告生成模块

数据聚合 → AI 摘要 → 多格式导出 → Teams/Outlook 分发
▼

🎯 为什么这样设计

测试报告不是「一堆数字堆砌」，而是给不同角色看不同内容。测试经理要趋势和风险，开发要具体失败信息，PM 要覆盖度。所以设计了四种报告类型（执行报告/回归报告/需求覆盖报告/质量报告），每种有不同的数据源和 AI 摘要策略。

AI 摘要生成
GPT-4o 基于执行数据和趋势，生成自然语言摘要：「本次回归测试通过率 92.3%，较上周下降 3.1%，主要失败集中在订单模块...」「建议优先修复的 3 个高风险缺陷：...」「长期未覆盖的高风险需求：...」。这比人手动写摘要准且快。

⚠️ 难点

  • 数据聚合的性能：一次回归测试可能有 1000+ 条结果，跨 Dataverse 和 Azure SQL 聚合，需要优化查询。
  • 报告格式一致性：HTML 在线查看和 PDF 导出的渲染效果要一致，用同一套模板引擎。

💡 亮点

  • GPT-4o-mini 降本：报告摘要用 mini 模型（图表数据摘要），成本低但效果够用。
  • 定时推送：每天早上 9 点自动生成昨日报告，推送到 Teams 频道和邮件。

🕳️ 可能踩的坑

  • AI 摘要过于乐观：全部通过时说「一切正常」，但忽略了通过率下降的趋势。
  • PDF 导出中文乱码，需要配置中文字体。

智能体交互模块

Copilot Studio → 自然语言 → 全平台操作入口
▼

🎯 为什么这样设计

用户不需要学 Power Apps 的操作路径。打开 Teams 就能控制整个测试平台——「给 RQ-001 生成用例」「执行回归测试」「上周的报告出了没」。这不是锦上添花，是降低使用门槛的核心手段。

Agent 拓扑
主 Agent（Copilot Studio）→ 9 个 Topic（对应 8 个模块 + 通用问答）→ 每个 Topic 内部通过 Power Automate Flow 调用后端 API 或查询 Dataverse → 复杂任务（如失败分析）走 Azure Function 多步分析。Fallback 走 Generative AI 兜底。

⚠️ 难点

  • 意图识别准确率：Copilot Studio 的 NLU 对中文测试术语的识别有限，需要大量训练语料。
  • 多轮对话上下文：用户说「再生成一次」，Agent 需要知道「再」指的是哪条需求、什么用例类型。
  • 权限传递：Agent 的身份是「当前用户」，操作权限必须与其 Azure AD 角色一致。

💡 亮点

  • Proactive Messaging：测试完成、失败率超阈值、报告就绪等事件，主动推送 Teams 卡片消息，而不是等用户来问。
  • 自然语言查询：「上周订单模块的失败率是多少」→ Agent 自动查询 Dataverse + Azure SQL，汇总后返回自然语言答案。

🕳️ 可能踩的坑

  • Copilot Studio 的 Token 消耗不可控，复杂查询可能触发多次 API 调用，费用飙升。
  • Teams 消息频率太高，用户会关通知。
Architecture

五层架构

表现层 → 应用层 → 服务层 → 数据层 → 集成层。微软生态原生串联，每一层都有明确的技术选型理由。

架构核心逻辑

Power Apps 触发 → Power Automate 协调 → Azure Functions 执行 AI 逻辑 → 结果写回 Dataverse / SQL → Power Automate 推送通知。关键分层原则：Power Automate 只做线性编排，复杂 AI 逻辑（多轮对话、循环、条件分支）全部下沉到 Azure Functions，因为 Flow 写复杂逻辑既难维护又难调试。

Design Decisions

关键设计决策

这些决策是整个平台架构的骨架，每一个都经过「为什么不用替代方案」的推敲。

🏗️ Power Platform 而非定制前端

项目深度依赖 Dataverse、Power Automate、Copilot Studio，这些在 Power Platform 内是原生集成。定制 React 前端反而要额外 API 网关层。代价：复杂交互需 PCF 组件扩展，版本管理依赖 Power Platform 发布机制。

🔍 AI Search 做 RAG 知识库

测试领域有大量历史数据（相似用例、历史失败），向量搜索 + 关键词混合检索能精准召回，搭配 Azure OpenAI 实现 RAG。代价：需设计索引 Schema，初始化时批量向量化存量数据。

🎭 Playwright 为主执行引擎

Playwright 现代化 API、自动等待、多浏览器支持、网络拦截能力全面优于 Selenium。代价：需构建 Playwright 执行器服务，旧 Selenium 脚本逐步迁移。

⚡ Azure Functions 而非 Logic Apps

Power Automate 适合线性流程，但 AI 调用涉及多轮对话、循环、条件分支，Functions 的代码灵活性更适合。代价：需维护 Functions 代码仓库，部署流水线不能完全低代码化。

🗄️ Dataverse + Azure SQL 双存储

Dataverse 与 Power Platform 原生集成（安全、审计、角色），但复杂查询性能有限。Azure SQL 承载高吞吐执行结果写入和聚合查询。代价：两个存储交叉查询需 Function 或 API 桥接。

💰 GPT-4o + mini 分级降本

分析类任务（需求解析、失败分析、评审）用 GPT-4o 保证质量；生成类任务（脚本生成、报告摘要）用 GPT-4o-mini 降本 90%。原则：成本敏感的场景用 mini，质量敏感的场景用 4o。

数据流转
