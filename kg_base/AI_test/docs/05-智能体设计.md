# 05 智能体设计

> 基于 Microsoft Copilot Studio + Azure OpenAI 的智能测试 Agent 架构设计

---

## 1. Agent 架构设计

### 1.1 整体架构

采用 **主 Agent + 子技能** 的单层编排模式，不引入多级嵌套 Agent。

```
┌─────────────────────────────────────────────────┐
│                   Teams / Web                   │  用户入口
└──────────────────────┬──────────────────────────┘
                       │
┌──────────────────────▼──────────────────────────┐
│              TestMaster（主 Agent）              │
│   ┌──────────────────────────────────────────┐  │
│   │  System Prompt + 意图路由                  │  │
│   │  → 接收自然语言 → 识别意图 → 分发技能      │  │
│   └──────────────────────────────────────────┘  │
└──┬─────┬─────┬─────┬─────┬─────┬─────┬─────┬───┘
   │     │     │     │     │     │     │     │
   ▼     ▼     ▼     ▼     ▼     ▼     ▼     ▼
 需求  用例   用例   脚本   执行   结果   失败   报告   知识
 分析  生成   评审   生成   调度   查询   分析   生成   问答
 技能   技能   技能   技能   技能   技能   技能   技能   技能
   │     │     │     │     │     │     │     │     │
   ▼     ▼     ▼     ▼     ▼     ▼     ▼     ▼     ▼
┌──────────────────────────────────────────────────┐
│           Azure OpenAI (GPT-4o / o3-mini)        │
├──────────────────────────────────────────────────┤
│        Azure AI Search   |   Azure Functions      │
│        Power Automate    |   Azure SQL / APIM      │
└──────────────────────────────────────────────────┘
```

**为什么不用多级子 Agent？**

Copilot Studio 的 Topic 机制天然适合单层路由。每个 Topic 就是一个独立技能，主 Agent 负责匹配意图并跳转。引入多层 Agent 会增加对话延迟和错误传递风险，对测试平台场景没有额外收益。

### 1.2 TestMaster 主 Agent

| 属性 | 说明 |
|------|------|
| **名称** | TestMaster |
| **定位** | 测试平台的统一 AI 交互入口，接收用户自然语言请求，路由到对应技能，聚合结果返回 |
| **对话入口** | Teams / Web Chat / Power Apps 嵌入 |
| **职责** | 意图识别、技能分发、上下文管理、结果整合、兜底回复 |

**主 Agent 不做的事：**
- 不直接调用 Azure Functions 或外部 API
- 不存储执行状态（状态由各技能对应的后端管理）
- 不处理文件解析（文件解析下沉到技能或 Power Automate）

### 1.3 技能列表概览

| 编号 | 技能名称 | 触发场景 | 后端依赖 |
|------|---------|---------|---------|
| S1 | 需求分析 | 用户上传需求文档 | Power Automate → Azure OpenAI + Azure AI Search |
| S2 | 用例生成 | 用户基于需求生成用例 | Azure Functions → Azure OpenAI |
| S3 | 用例评审 | 用户请求评审已生成的用例 | Azure Functions → Azure OpenAI |
| S4 | 脚本生成 | 用户请求生成自动化脚本 | Azure Functions → Azure OpenAI |
| S5 | 执行调度 | 用户触发测试执行 | Power Automate → Jenkins/ADO |
| S6 | 结果查询 | 用户查询执行状态 | Azure Functions → Database |
| S7 | 失败分析 | 用户请求分析失败原因 | Azure Functions → Azure OpenAI + Logs |
| S8 | 报告生成 | 用户请求生成测试报告 | Azure Functions → Azure OpenAI |
| S9 | 知识问答 | 用户提问测试相关知识 | Azure Functions → Azure AI Search (RAG) |

## 2. 技能配置（Topics）

每个技能的配置遵循相同的结构：

- **Trigger Phrases**：触发短语，每条 3-8 个词，覆盖用户常见问法
- **Dialog Flow**：对话流程，用 Copilot Studio Topic 节点描述
- **Backend Call**：调用的后端服务及参数
- **Input / Output**：技能级输入输出定义

### S1 需求分析技能

**目标**：用户上传需求文档，Agent 解析并提取测试点。

**Trigger Phrases**：
- 分析这份需求
- 帮我解析需求文档
- 提取测试点
- 需求分析
- analyze this requirement
- extract test points

**对话流程**：

```
用户发送消息（含文件附件或文本）
  → TestMaster 匹配 Topic
  → 要求用户上传需求文档（如未提供）
  → 调用 Power Automate Flow
      → Flow 解析附件 / 接收文本
      → 调用 Azure OpenAI，Prompt：需求分析模板
      → 返回结构化测试点列表
  → 格式化输出结果
  → 询问是否需要生成测试用例
```

**后端服务**：Power Automate Cloud Flow

**Power Automate 流程**：

| 步骤 | 操作 |
|------|------|
| 1 | 接收 Copilot Studio 传过来的文本或文件 URL |
| 2 | 如为文件，读取文件内容（支持 .docx/.pdf/.txt） |
| 3 | 调用 Azure OpenAI（GPT-4o），传入需求分析 Prompt |
| 4 | 解析返回的 JSON，传回 Copilot Studio |

**Input**：

```json
{
  "content": "string",          // 需求文本内容
  "fileUrl": "string (optional)" // 附件 URL
}
```

**Output**：

```json
{
  "requirementName": "string",
  "testPoints": [
    {
      "id": "TP-001",
      "category": "功能测试|性能测试|安全测试|兼容性测试",
      "summary": "string",
      "priority": "P0|P1|P2|P3"
    }
  ]
}
```

### S2 用例生成技能

**目标**：基于需求或测试点，生成标准格式的测试用例。

**Trigger Phrases**：
- 生成测试用例
- 创建测试用例
- 为需求生成用例
- 写测试用例
- generate test case
- create test cases for requirement

**对话流程**：

```
用户指定需求或测试点
  → Agent 确认生成范围（全部/指定分类）
  → 调用 Azure Functions
      → 请求 OpenAI，Prompt：用例生成模板
      → 返回用例列表
  → 展示用例摘要
  → 询问是否导出（Excel/Test Case 管理工具）
```

**后端服务**：Azure Functions（HTTP Trigger）

**Input**：

```json
{
  "requirementId": "string (optional)",
  "testPoints": ["TP-001", "TP-002"],
  "count": "number (optional, 默认每个测试点 3 条)",
  "format": "standard|detailed|minimal"
}
```

**Output**：

```json
{
  "testCases": [
    {
      "id": "TC-001",
      "title": "string",
      "precondition": "string",
      "steps": ["step1", "step2"],
      "expectedResult": "string",
      "priority": "P0|P1|P2|P3",
      "relatedTP": "TP-001",
      "type": "positive|negative|boundary|exception"
    }
  ]
}
```

### S3 用例评审技能

**目标**：对已有测试用例进行 AI 评审，给出改进建议。

**Trigger Phrases**：
- 评审这些用例
- 帮我审核测试用例
- 用例评审
- review test cases
- check test case quality

**对话流程**：

```
用户提供或选择要评审的用例
  → Agent 展示用例列表让用户确认
  → 调用 Azure Functions
      → 请求 OpenAI，Prompt：用例评审模板
      → 返回评审结果
  → 展示评审意见（覆盖率、可执行性、冗余、遗漏）
  → 询问是否自动修正
```

**后端服务**：Azure Functions（HTTP Trigger）

**Input**：

```json
{
  "testCases": [ /* S2 输出的用例结构 */ ],
  "requirement": "string (optional, 关联需求作为评审参考)"
}
```

**Output**：

```json
{
  "overallScore": 85,
  "issues": [
    {
      "testCaseId": "TC-001",
      "type": "missing_step|ambiguous_result|redundant|missing_coverage",
      "severity": "high|medium|low",
      "description": "string",
      "suggestion": "string"
    }
  ],
  "summary": "string"
}
```

### S4 脚本生成技能

**目标**：根据测试用例生成自动化脚本（Playwright / Selenium 或自定义框架）。

**Trigger Phrases**：
- 生成自动化脚本
- 写测试脚本
- 生成脚本代码
- generate test script
- create automation script
- 转成脚本

**对话流程**：

```
用户选择测试用例
  → Agent 确认脚本框架类型（Playwright / Selenium / 自定义）
  → Agent 确认目标语言（TypeScript / Python / Java）
  → 调用 Azure Functions
      → 请求 OpenAI（使用 o3-mini 以优化代码质量）
      → 返回脚本代码
  → 展示代码并提供复制或下载
  → 询问是否需要添加到仓库
```

**后端服务**：Azure Functions（HTTP Trigger）

**Input**：

```json
{
  "testCases": [ /* 用例结构 */ ],
  "framework": "playwright|selenium|custom",
  "language": "typescript|python|java",
  "codeStyle": "pageObject|simple"

```

**Output**：

```json
{
  "scripts": [
```

### S9 知识问答技能

**目标**：回答测试相关知识、规范、流程等问题，基于 RAG 方案。

**Trigger Phrases**：
- 什么是 ...
- 怎么做 ...
- 查询测试规范
- 测试流程是啥
- how to ...
- 问一下 ...
- 知识查询
- help

**对话流程**：

```
用户提问
  → Agent 接收问题
  → 调用 Azure Functions
      → 对问题进行向量化（Azure OpenAI Embedding）

      → 请求 Azure OpenAI 生成回答
```

**后端服务**：Azure Functions（HTTP Trigger）

**Input**：

```json
{

  "filterCategory": "string (optional, 限定检索范围)"
}
```

**Output**：

```json
  "answer": "string",
  "sources": [
    {
      "title": "string",
```

## 3. 多 Agent 协作模式

Copilot Studio 本身是单 Agent 运行时，所谓的"多 Agent 协作"通过 Topic 路由 + 后端编排来实现。

### 3.1 协作流程

```
用户输入
  ↓
TestMaster 意图识别（Copilot Studio NLU）
  ↓
匹配 Topic → 进入对应技能对话流程
  ↓
技能内部可能再调用其他技能：
  ┌──────────┐     ┌──────────┐
  │ 需求分析  │ ──→ │ 用例生成  │  (需求分析完成后，用户可选生成用例)
  └──────────┘     └──────────┘
  ┌──────────┐     ┌──────────┐     ┌──────────┐
  │ 用例评审  │ ──→ │ 脚本生成  │ ──→ │ 执行调度  │  (评审通过后直接生成脚本并执行)
  └──────────┘     └──────────┘     └──────────┘
  ┌──────────┐     ┌──────────┐
  │ 执行调度  │ ──→ │ 结果查询  │  (执行后自动触发结果推送)
  └──────────┘     └──────────┘
  ┌──────────┐     ┌──────────┐
  │ 失败分析  │ ──→ │ 报告生成  │  (分析完结果后生成报告)
  └──────────┘     └──────────┘
```

### 3.2 典型协作场景

**场景：从需求到执行的完整链路**
```
用户："分析这份需求文档"
  → S1 需求分析（返回测试点）
  → 用户："为这些测试点生成用例"
  → S2 用例生成（返回用例）
  → 用户："帮我评审一下"
  → S3 用例评审（返回评审意见）
  → 用户："没问题了，生成脚本"
  → S4 脚本生成（返回脚本代码）
  → 用户："跑一下"
  → S5 执行调度（触发执行）
  → 自动回调 → S6 结果查询（推送结果）
  → 用户："分析下失败的原因"
  → S7 失败分析（返回分析报告）
  → 用户："出一份完整报告"
  → S8 报告生成（返回报告链接）
```

每个 Topic 结束后，都会问用户"下一步想做什么"，保持对话的连续性。这不需要额外的 Agent 协调逻辑，是 Copilot Studio Topic 跳转的原生能力。

## 4. 集成设计

### 4.1 Teams 集成

Copilot Studio 原生支持发布为 Teams 应用，这是最主要的用户入口。

**配置项**：

| 项目 | 配置 |
|------|------|
| Application Type | Microsoft Teams |
| App Name | TestMaster |
| Capabilities | Chat Bot, Messaging Extension |
| Auth | SSO with Microsoft Entra ID |

**在 Teams 中的使用方式**：

```
1. 在 Teams App Store 搜索 "TestMaster" 并安装
2. 在聊天中 @TestMaster 或直接对话
3. 支持在频道中 @TestMaster 并提及具体测试任务
4. Messaging Extension 方式：在消息 Action 里直接调 TestMaster
```

**Messaging Extension 场景**：

用户在 Teams 中收到一条测试失败报告消息，点击「分析失败原因」→ 直接触发 S7 失败分析技能，无需切换到聊天窗口。

### 4.2 Outlook 集成

通过 Power Automate 实现邮件触发的 Agent 交互。

**场景 1：邮件触发执行**
```
用户给测试平台邮箱发送邮件
  → Power Automate 监听特定格式的邮件
  → 调用 TestMaster API（通过 Copilot Studio REST API）
  → 触发对应技能（如执行调度）
  → 执行完成后，回复邮件或发送结果摘要
```

**场景 2：定时报告推送**
```
Power Automate Scheduled Trigger
  → 调用 S8 报告生成
  → 生成报告后通过 Outlook 发送给指定收件人
  → 邮件正文包含摘要，附件包含完整报告
```

**场景 3：执行完成通知**
```
Power Automate 监听执行完成事件
  → 构造摘要文本
  → 发送 Outlook 邮件给用户
  → 邮件中提供 TestMaster 链接（Copilot Studio 的 Teams 入口）
```

### 4.3 Power Apps 集成

通过 Copilot Studio 的 Power Apps 嵌入能力，在已有 Power Apps 界面中嵌入 Agent。

**方式 1：嵌入聊天控件**
```
在 Power Apps 的测试管理页面中
  → 添加 Copilot Studio chat control
  → 用户选中某个测试任务后，点击「AI 分析」
  → Chat control 自动携带上下文打开，执行对应技能
```

**方式 2：按钮触发技能**
```
Power Apps 按钮 → Run Copilot Studio Topic → 传递参数
示例：
  - 「自动生成此需求的测试用例」按钮
  - → 调用 TestMaster 的 S2 Topic
  - → 传递 RequirementId 作为 Context Variable
  - → Topic 直接执行返回结果，不经过意图匹配
```

**集成架构**：

```
┌─────────────┐     ┌──────────────────┐     ┌──────────────┐
│  Power Apps  │ ──→ │  Copilot Studio  │ ──→ │  Backend API │
│  (界面嵌入)  │     │  (Topic 调用)    │     │  (业务逻辑)   │

```

## 5. AI 提示词设计

### 5.1 System Prompt（主 Agent）

```text
你是一个名为 TestMaster 的测试专家助手，运行在基于微软技术的测试平台上。
你的用户主要是测试工程师和开发工程师。

核心职责：
1. 理解用户在软件测试全流程中的需求
2. 根据用户意图引导到合适的测试能力
3. 提供清晰、结构化的测试分析结果
4. 对测试相关专业知识进行答疑

行为准则：
- 始终用用户使用的语言回复（如果用户用中文，你也用中文）
- 输出结构化内容时优先使用表格和列表
- 不确定的信息不要编造，引导用户查询知识库
- 对于需要后端操作的功能（执行、生成等），不做承诺，只说明已经提交

能力边界：
- 你可以分析需求、生成和评审测试用例、生成自动化脚本、查询执行结果、分析失败原因、生成报告
- 你不具备实际的测试执行能力，测试执行通过后端调度系统完成
- 你的知识截止于当前对话，超出范围的测试知识通过知识库检索获取

交互风格：
- 专业、简洁、结果导向
- 复杂分析结果先给结论，再给详情
- 主动引导下一步操作
```

### 5.3 RAG 检索策略

**数据源**：

| 类型 | 存储位置 | 索引策略 |
|------|---------|---------|
| 测试规范文档 | Azure Blob Storage → Azure AI Search | 全文 + 向量 |
| 测试流程文档 | Azure Blob Storage → Azure AI Search | 全文 + 向量 |
| FAQ 库 | Azure SQL → Azure AI Search | 全文 |
| 历史问题记录 | Azure SQL → Azure AI Search | 全文 + 向量 |

**检索配置**：

| 参数 | 值 | 说明 |
|------|----|------|
| 检索模式 | Hybrid（全文 + 向量） | 兼顾关键词匹配和语义匹配 |
| Top K | 5 | 返回最相关的 5 个片段 |
| 相似度阈值 | ≥ 0.75 | 低于此阈值的结果不返回 |
| 向量模型 | text-embedding-3-large | Azure OpenAI Embedding 模型 |
| 分段策略 | 按章节分块，每块不超过 1500 token，重叠 200 token | 避免切断语义 |

**检索流程**：

```
用户提问
  → 判断是否需要检索（简单问候/闲聊不检索，直接回复）
  → 需要检索：
      1. 对用户问题进行向量化
      2. 在 Azure AI Search 中执行 Hybrid 检索
      3. 过滤排序后取 Top 5
      4. 过滤掉相似度低于 0.75 的结果
      5. 将检索结果作为上下文注入 Prompt
  → 不需要检索：直接使用对话上下文回复
```

### 6.1 Topic 结构示例

以 S2 用例生成为例，Topic 在 Copilot Studio 中的节点配置：

```
┌──────────────────────────────────────────────────┐
│ Trigger: "生成测试用例", "写测试用例", ...         │
├──────────────────────────────────────────────────┤
│ Condition: 用户是否提供了测试点或需求 ID？         │
│  ├─ No:  提问 "请选择需要生成用例的测试点或需求"    │
│  └─ Yes: 跳转下一步                                │
├──────────────────────────────────────────────────┤
│ Question: "需要生成多少条用例？(默认每点 3 条)"    │
├──────────────────────────────────────────────────┤
│ Call an action: Azure Functions (S2 API)         │
│  - Input:  testPoints, count, format             │
│  - Output: testCases (JSON)                      │
├──────────────────────────────────────────────────┤
│ Condition: 调用成功？                             │
│  ├─ No:  显示错误信息，建议重试                     │
│  └─ Yes: 格式化并展示用例列表                      │
├──────────────────────────────────────────────────┤
│ Adaptive Card: 展示用例摘要                        │
│  - 按钮: "导出 Excel" → 触发 Power Automate      │
│  - 按钮: "生成脚本"  → 跳转 S4 Topic              │
│  - 按钮: "返回"     → 返回主菜单                  │
└──────────────────────────────────────────────────┘
```

### 6.2 上下文变量

| `CurrentRequirementId` | string | 全局 | 当前会话关联的需求 ID |
| `CurrentTestPoints` | array | 全局 | 当前会话的测试点列表 |

## 7. 注意事项与限制

1. **Copilot Studio 的 NLU 精度问题**：Trigger Phrases 需要持续优化。初期上线后收集用户真实输入，补充高频短语，移除不触发或误触发的短语。

2. **Token 消耗控制**：需求分析和报告生成场景容易消耗大量 Token。建议：
   - 长文档分块处理，不在一次 Prompt 中塞完整文档
   - 为 o3-mini 和 GPT-4o 分配不同场景（代码生成用 o3-mini，分析类用 GPT-4o）

3. **对话上下文窗口**：Copilot Studio 单个 Topic 的执行上下文有限。复杂的多步操作（如分析→生成→评审→执行）建议每步独立调用 API，不要试图在一次 Topic 执行中完成。

4. **Power Automate 超时**：Copilot Studio 调用 Power Automate 有超时限制（约 2 分钟）。耗时较长的操作（如执行调度）建议采用异步模式：立即返回任务 ID，然后通过 Webhook 回调通知结果。

5. **Auth 与权限**：所有后端 API 需要通过 Microsoft Entra ID 认证。Copilot Studio 已发布的应用需要通过 SSO 集成统一身份认证。
