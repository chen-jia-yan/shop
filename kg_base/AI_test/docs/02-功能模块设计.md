## 1. 需求分析模块

### 功能描述

AI 自动解析需求文档（PRD、设计稿、用户故事等），提取结构化测试需求。支持多格式文档输入，输出可被下游模块直接消费的测试点清单。

核心目标：让测试人员从逐字阅读需求文档中解放出来，AI 完成初步分析，人工仅做确认和补充。

### 输入 / 输出

| 项 | 说明 |
|------|------|
| **输入** | PRD 文档（Word/PDF/Markdown）、用户故事（Azure DevOps）、原型图描述、会议纪要 |
| **输出** | 结构化测试需求清单（Dataverse 表）、需求-测试点映射矩阵、需求质量评分（完整性/一致性/可测试性） |

### AI 能力运用

- **Azure OpenAI GPT-4o**：解析长文本需求，提取功能点、业务规则、边界条件
- **Azure AI Search**：对历史需求做相似度匹配，辅助判断新需求是否有覆盖盲区
- **Azure AI Document Intelligence**（原 Form Recognizer）：从 PDF/Word 中抽取文档结构和段落

### 关键实现方式

1. **文档预处理**：用户通过 Power Pages 上传文档，Power Automate 调用 Azure AI Document Intelligence 提取文本。
2. **AI 解析**：文本送入 Azure OpenAI，按预设 prompt 模板提取：功能描述、前置条件、业务规则、异常场景、数据要求、UI 要求。
3. **结构化存储**：解析结果写入 Dataverse 表 `requirement_analysis`，字段包括：原文片段、抽取结果、置信度、人工确认状态。
4. **需求质量评分**：GPT-4o 基于完整性、无歧义性、可测试性三个维度打分，低于阈值时通过 Teams 通知需求方补充。
5. **人工确认流程**：测试人员在 Power Apps 中逐条确认 AI 分析结果，可编辑、驳回、新增。确认后状态变为"已确认"，下游模块才可取用。

### 与其他模块的交互

```
需求分析 → 测试用例生成：传递结构化测试需求清单
需求分析 ⇄ 智能体交互：用户可通过自然语言查询需求分析结果，或触发重新分析
需求分析 → 报告生成：需求覆盖度数据供报告模块使用
需求分析 ⇄ Azure DevOps：拉取用户故事，写回分析结果作为附件
```

## 2. 测试用例生成模块

### 功能描述

基于需求分析模块输出的结构化需求，智能生成测试用例。支持多种用例模板（功能测试、边界测试、组合测试、异常测试），自动覆盖正向/反向场景。

核心目标：让 AI 完成 80% 的用例编写工作，测试人员只需调整而非从零创建。

### 输入 / 输出

| 项 | 说明 |
|------|------|
| **输入** | 结构化测试需求清单、用户指定的用例模板类型（边界/等价类/场景法/正交等）、历史用例库 |
| **输出** | 测试用例（Dataverse `test_case` 表）、用例-需求关联记录、用例质量预评分 |

### AI 能力运用

- **Azure OpenAI GPT-4o**：根据需求自动推导测试场景，生成用例步骤、预期结果、测试数据建议
- **Azure AI Search + Vector Search**：基于语义相似度检索历史用例库，推荐可复用的用例模式
- **Prompt 模板体系**：不同测试方法对应不同 prompt 模板（边界值分析、等价类划分、判定表、场景法）

### 关键实现方式

1. **用例策略选择器**：Azure Function 根据需求的特征（如是否涉及数值范围 → 边界值；多条件组合 → 判定表）自动推荐最优测试策略，测试人员可在 Power Apps 中切换策略。
2. **AI 生成流水线**：Power Automate 编排流程：输入需求 → 检索相似历史用例（AI Search）→ 组装 prompt → 调 Azure OpenAI → 解析响应 → 写 Dataverse。
3. **批量生成**：支持一次选择多条需求，批量生成用例。AI 自动去重，合并重复场景。
4. **用例模板**：预置功能测试、API 测试、UI 测试、性能测试、安全测试 5 类模板，各有不同的字段结构和 prompt。
5. **人工编辑**：生成后在 Power Apps 中展示，测试人员可增删改步骤、调整优先级、补充测试数据。修改直接存回 Dataverse。

### 与其他模块的交互

```
测试用例生成 ← 需求分析：消费结构化需求
测试用例生成 → 用例评审：待评审用例
测试用例生成 ⇄ 自动化脚本生成：用例结构决定了脚本生成策略
测试用例生成 ⇄ 智能体交互：用户可通过"给需求 RQ-001 生成功能测试用例"触发
```

## 3. 用例评审模块

### 功能描述

AI 辅助评审测试用例质量，从完整性、正确性、可执行性、冗余度四个维度给出评分和改进建议。

核心目标：在人工评审前，AI 先筛一遍低级问题，节省评审时间。人工评审只关注业务逻辑层面的判断。

### 输入 / 输出

| 项 | 说明 |
|------|------|
| **输入** | 待评审的测试用例（Dataverse `test_case`）、关联的需求记录、历史评审记录 |
| **输出** | 用例质量评分（四维度）、改进建议列表、严重问题标记、评审报告 |

### AI 能力运用

- **Azure OpenAI GPT-4o**：逐条评审用例，判断步骤是否完整、预期结果是否明确、是否冗余、与需求是否一致
- **Azure AI Search**：检索历史评审记录中同类问题的处理方式，辅助给出修复建议

### 关键实现方式

1. **自动评审触发器**：用例状态变更为"待评审"时，Power Automate 自动触发 AI 评审。评审结果写回 `test_case_review` 表。
2. **评审维度**：
   - **完整性**：步骤是否完整、预期结果是否明确、前置条件是否完备
   - **正确性**：用例逻辑是否自洽、实际结果是否可验证、与需求是否一致
   - **可执行性**：是否有明确的执行条件、是否需要不可获取的测试数据
   - **冗余度**：与本模块其他用例是否重复、与历史用例是否重复
3. **严重问题拦截**：评分低于阈值（如完整性 < 60 分）的用例标记为"建议修改"，直接退回生成阶段，不进入人工评审队列。
4. **人工评审界面**：Power Apps 展示 AI 评审结果 + 建议。评审人可逐条确认或驳回 AI 建议，最终给出总体结论（通过 / 需修改 / 废弃）。
5. **评审反馈闭环**：评审人的修改和驳回记录写入 Dataverse，作为后续 AI 模型 fine-tuning 或 prompt 优化的训练数据。

### 与其他模块的交互

```
用例评审 ← 测试用例生成：接收待评审用例
用例评审 → 测试用例生成：退回不合格用例，附 AI + 人工修改意见
用例评审 → 自动化脚本生成：通过的用例进入脚本生成队列
用例评审 ⇄ 智能体交互：用户可查询评审状态，请求 AI 给出更详细的评审说明
```

## 4. 自动化脚本生成模块

### 功能描述

将评审通过的测试用例自动转换为可执行的 Playwright（优先）或 Selenium 自动化测试脚本。

核心目标：让 AI 完成脚本编码，测试人员只需做脚本级别的人工走查和调试。

### 输入 / 输出

| 项 | 说明 |
|------|------|
| **输入** | 评审通过的测试用例、被测应用 URL/API 端点、页面元素定位信息或录制会话 |
| **输出** | 自动化测试脚本（TypeScript + Playwright / Java + Selenium）、脚本元数据（依赖、环境要求、标签）、脚本执行配置 |

### AI 能力运用

- **Azure OpenAI GPT-4o + Code Interpreter-like prompt**：根据用例步骤生成可直接运行的测试代码
- **AI Search 代码库检索**：检索项目中已有的脚本片段、Page Object Model 模式代码，确保生成风格一致

### 关键实现方式

1. **代码生成策略**：
   - **UI 测试**：Playwright 优先。AI 根据用例步骤生成脚本，对于页面元素定位，支持三种方式：先录后改（用户先用 Playwright Codegen 录制动作为起点）、AI 根据页面截图 + 描述推断选择器、手动补充 selector。
   - **API 测试**：直接生成 Playwright `APIRequestContext` 或 axios 请求代码。
   - **数据验证**：生成 SQL 查询或 API 断言代码。
2. **代码存储**：Azure Function 或 GitHub Actions 生成脚本文件，提交到 Azure Repos（或 GitHub）的 `tests/` 目录下。脚本元数据写回 Dataverse `test_script` 表。
3. **代码质量保障**：
   - AI 生成的代码自动通过 ESLint + TypeScript 编译检查。
   - 生成后自动在 sandbox 环境执行一次冒烟验证，验证脚本可运行而非逻辑正确。
   - 失败则让 AI 自行修复 1-2 轮，仍失败则标记为"需人工介入"。
4. **Page Object 维护**：AI 辅助维护 POM 文件。当 UI 变更导致脚本失败时，失败分析模块（模块 6）触发 POM 更新建议。

### 与其他模块的交互

```
自动化脚本生成 ← 用例评审：接收通过用例
自动化脚本生成 → 测试执行：生成的脚本写入执行队列
自动化脚本生成 ⇄ 失败分析：脚本执行失败时，失败分析结果反馈此处以改进生成质量
自动化脚本生成 ⇄ 智能体交互：用户可通过"为这条用例生成脚本"触发单个用例的脚本生成
```

## 5. 测试执行模块

### 功能描述

调度和执行自动化测试脚本，实时监控执行状态，管理测试环境。支持并行执行、定时执行、CI/CD 触发执行。

核心目标：提供可靠、可观察的自动化测试执行平台，执行状态和数据全链路可追踪。

### 输入 / 输出

| 项 | 说明 |
|------|------|
| **输入** | 待执行的脚本清单（Dataverse `test_execution_queue`）、执行环境配置、执行参数（并行数/重试策略/超时时间） |
| **输出** | 执行结果（通过/失败/跳过/超时）、执行日志、截图/视频（失败 case）、执行耗时、性能指标 |

### AI 能力运用

- **Azure OpenAI**（轻量模型 GPT-4o-mini）：执行失败时实时截取错误信息，辅助初步分类（脚本问题 vs 环境问题 vs 业务逻辑问题）
- **不用于执行调度**：调度由 Power Automate + Azure Functions 完成，保证确定性

### 关键实现方式

1. **执行队列管理**：执行任务写入 Dataverse `test_execution_queue`，Power Automate 轮询队列，按优先级和环境分组调度到 Azure Functions。
2. **执行引擎（Azure Functions + Playwright）**：
   - Azure Functions（Linux Consumption Plan）上预装 Playwright + 浏览器。
   - Function 拉取执行任务 → clone 脚本仓库 → 安装依赖 → 执行脚本 → 上传结果/日志/截图到 Blob Storage → 回写执行状态到 Dataverse。
3. **并行控制**：通过 Azure Functions 的 concurrency 控制 + 队列分区保证同一环境下的脚本串行执行，不同环境间的脚本可并行。
4. **环境管理**：每个测试环境（dev/staging/qa）在 Dataverse 中注册。执行时自动选择对应环境的 base URL 和凭据（Azure Key Vault 管理）。
5. **实时状态推送**：
   - Azure Functions 执行过程中通过 SignalR Service 或定时写 Dataverse 状态字段。
   - Power Apps 前端通过定时刷新或 Dataverse WebSocket 展示实时状态。
6. **重试机制**：失败用例自动重试 1 次（配置化）。重试仍失败进入失败分析模块。

### 与其他模块的交互

```
测试执行 ← 自动化脚本生成：拉取待执行队列
测试执行 → 失败分析：失败的执行进入分析流水线
测试执行 → 报告生成：执行结果数据供报告模块消费
测试执行 ⇄ Azure DevOps：CI/CD Pipeline 触发执行，回传结果到 PR 状态
测试执行 ⇄ 智能体交互：用户可通过"执行回归测试"、"查看执行进度"控制执行
```

## 6. 失败分析模块

### 功能描述

AI 自动分析测试失败原因，进行分类、归因和根因建议。降低人工排查成本，缩短问题定位时间。

核心目标：让 AI 完成 90% 的失败分类和初步归因，测试人员只需确认结果和推动修复。

### 输入 / 输出

| 项 | 说明 |
|------|------|
| **输入** | 失败脚本、错误日志（Blob Storage）、执行截图/视频（Blob Storage）、控制台输出、网络请求记录（Playwright trace）、历史失败记录 |
| **输出** | 失败分类标签、根因分析报告、修复建议、关联 Bug（Azure DevOps/Jira）草稿 |

### AI 能力运用

- **Azure OpenAI GPT-4o**：多模态分析——截图 + 日志 + trace 文件，综合判断失败原因
- **Azure AI Search 向量检索**：匹配历史失败记录，判断是否为已知问题（回归缺陷 vs 新缺陷 vs flaky test）
- **Azure OpenAI Embeddings**：对错误信息做语义向量化，聚类同类失败，辅助归因

### 关键实现方式

1. **失败触发分析**：测试执行标记失败后，Power Automate 调用 Azure Function 启动分析。
2. **输入聚合**：Function 从 Blob Storage 拉取截图、日志、Playwright trace，从 Dataverse 拉取脚本信息和历史失败记录。
3. **AI 分析流水线**：
   - **Step 1 - 分类**：GPT-4o 判断失败类型：
     - `SCRIPT_BUG`：脚本本身问题（selector 失效、等待逻辑错误等）
     - `ENV_ISSUE`：环境问题（服务不可用、数据被清理、依赖服务超时）
     - `PRODUCT_BUG`：业务逻辑 bug（预期结果与实际不符）
     - `FLAKY`：不稳定的测试（偶发失败，上次成功）
     - `DATA_ISSUE`：测试数据问题（数据被污染、未初始化）
   - **Step 2 - 归因**：对 PRODUCT_BUG 类型，提取具体错误位置、输入条件、预期 vs 实际，辅助开发定位。
   - **Step 3 - 历史匹配**：向量检索历史失败记录，标注"已知问题 #TICKET-1234"或"新发现问题"。
4. **自修复尝试**（仅限 SCRIPT_BUG 类型）：AI 尝试修改脚本（如更新 CSS selector 或等待条件），重新执行 1 次。成功则标记"自动修复"，不产生告警。
5. **Bug 自动提单**：确认是 PRODUCT_BUG 后，AI 生成 Bug 描述草稿（含失败步骤、截图、日志片段），推送至 Azure DevOps/Jira，由人工确认后正式提交。

### 与其他模块的交互

```
失败分析 ← 测试执行：接收失败执行数据
失败分析 ⇄ 自动化脚本生成：SCRIPT_BUG 类型触发脚本自修复流程
失败分析 → 报告生成：失败分析统计数据供报告模块使用
失败分析 ⇄ Azure DevOps/Jira：自动创建 Bug 草稿
失败分析 ⇄ 智能体交互：用户可查询失败分析结果，请求更详细的根因说明
```

## 7. 报告生成模块

### 功能描述

基于执行结果和需求覆盖数据，自动生成多维度测试报告。支持定时生成和按需生成，支持多种导出格式。

核心目标：让报告从"测试人员需要花半天整理"变为"一键生成，AI 帮写摘要和分析"。

### 输入 / 输出

| 项 | 说明 |
|------|------|
| **输入** | 执行结果集（Dataverse `test_execution_result`）、需求覆盖数据、失败分析结果、历史执行趋势 |
| **输出** | 测试报告（HTML/PDF/Word/Excel）、报告摘要（AI 生成）、趋势图、需求覆盖矩阵、PDF 附件通过邮件/Teams 分发 |

### AI 能力运用

- **Azure OpenAI GPT-4o**：从测试数据中提取趋势，用自然语言撰写执行摘要、风险提示、改进建议
- **GPT-4o-mini**：生成报告中的图表数据摘要，以较低成本处理数据量较大的部分

### 关键实现方式

1. **报告类型**：
   - **执行报告**：单次测试执行的结果汇总，通过/失败/跳过分布，失败详情
   - **回归报告**：多次执行趋势对比，回归缺陷列表，新增/修复缺陷统计
   - **需求覆盖报告**：需求与测试用例的映射矩阵，未覆盖需求清单，覆盖度趋势
   - **质量报告**：综合质量评分，失败率趋势，问题分类分布，修复时效
2. **报告生成流水线**：
   - Power Automate（Scheduled 或 Instant）触发 → Power BI Embedded（或 D3.js 图表）生成图表 → Azure OpenAI 生成文字摘要 → 拼装 HTML/PDF → 上传 Blob Storage → Dataverse 记录报告元数据 → 通过 Teams/邮件推送。
3. **AI 摘要生成**：GPT-4o 基于执行数据和趋势，生成：
   - "本次回归测试通过率 92.3%，较上周下降 3.1%，主要失败集中在订单模块..."
   - "建议优先修复的 3 个高风险缺陷：..."
   - "长期未覆盖的高风险需求：..."
4. **导出格式**：支持 HTML（在线查看，Power Pages 展示）、PDF（存档/邮件）、Excel（数据分析）、Word（正式交付物）。

### 与其他模块的交互

```
报告生成 ← 需求分析：需求覆盖数据
报告生成 ← 测试执行：执行结果集
报告生成 ← 失败分析：失败分类统计
报告生成 ⇄ 智能体交互：用户可通过"生成上周回归报告"触发，或查询报告内容
报告生成 → Teams/Outlook：推送报告链接或附件
```

## 8. 智能体交互模块

### 功能描述

Copilot Studio Agent 作为平台的统一交互入口，用户通过自然语言完成所有操作——查询状态、触发任务、获取分析结果。

核心目标：用户不需要学习 Power Apps 的操作路径，打开 Teams 或网页就能用自然语言控制整个测试平台。

### 输入 / 输出

| 项 | 说明 |
|------|------|
| **输入** | 自然语言查询或指令（Teams/Web/移动端） |
| **输出** | 自然语言回答（文字/卡片）、触发后台操作（生成用例/执行测试/生成报告）、主动推送通知（失败告警/报告就绪） |

### AI 能力运用

- **Copilot Studio**：对话管理、意图识别、多轮对话、上下文维护
- **Azure OpenAI**（通过 Copilot Studio 的 Generative AI 能力）：复杂推理、非标准意图的兜底处理
- **Azure AI Search**：检索历史数据辅助回答

### 关键实现方式

1. **Agent 拓扑**：
   - **主 Agent**（Copilot Studio）：入口 Agent，负责对话管理、用户意图识别、路由到子系统。
   - **Topic 设计**：每个模块对应一组 Topic，如"查询测试结果"、"生成用例"、"执行测试"、"查看报告"。
     - 每个 Topic 内部通过 Power Automate Flow 调用后端 API 或查询 Dataverse。
     - 对于复杂任务（如"分析这个失败并给我建议"），Topic 调用 Azure Function 执行多步分析。
   - **Fallback Topic**：无法匹配时，使用 Generative AI 能力通过 Azure OpenAI 兜底。

2. **主要交互场景**：

   | 用户指令 | Agent 动作 |
   |----------|-----------|
   | "帮我看看这个需求 RQ-001 的用例覆盖情况" | 查询 Dataverse 需求-用例映射，返回覆盖度和缺失场景 |
   | "给需求 RQ-002 生成功能测试用例" | 触发 Power Automate→测试用例生成模块，完成后推送结果 |
   | "执行回归测试" | 查询最后一次通过的用例集，触发执行队列，返回执行 ID |
   | "上周的测试报告出来了没" | 查询报告状态，返回链接或摘要 |
   | "这个失败为什么是 SCRIPT_BUG？" | 调用失败分析模块，展示详细的 AI 分析过程 |
   | "通知我测试跑完" | 创建通知订阅，执行完成后通过 Teams 主动推送 |

3. **通知推送**（Proactive Messaging）：
   - 测试完成、失败率达到阈值、报告就绪等事件，通过 Power Automate 调用 Teams/Outlook API 或 Copilot Studio 的 outgoing webhook 主动推送卡片消息到用户或频道。
   - 卡片包含：状态摘要 + 关键数据 + "查看详情"按钮（链接到 Power Pages 对应页面）。

4. **权限集成**：Copilot Studio 认证对接 Azure AD，用户的操作范围和可查看数据受其 Azure AD 角色和 Dataverse 权限控制。

### 与其他模块的交互

```
智能体交互 → 所有模块：作为用户操作入口
智能体交互 ← 所有模块：查询各模块数据
智能体交互 ← 测试执行/失败分析/报告生成：接收事件推送，主动通知用户
```

## 9. 模块交互总览

### 核心数据流

```
[用户] ↔ [智能体交互模块] ──→ [需求分析] ──→ [用例生成] ──→ [用例评审]
                                                          ↓
                                                     [脚本生成] ──→ [测试执行] ──→ [失败分析]
                                                                        ↓
                                                                   [报告生成]
```

### 数据流向汇总

| 数据 | 来源 | 去向 | 存储 |
|------|------|------|------|
| 需求分析结果 | 需求分析模块 | 用例生成、报告生成 | Dataverse `requirement_analysis` |
| 测试用例 | 用例生成模块 | 用例评审、报告生成 | Dataverse `test_case` |
| 评审结果 | 用例评审模块 | 用例生成（反馈）、脚本生成（通过） | Dataverse `test_case_review` |
| 测试脚本 | 脚本生成模块 | 测试执行 | Dataverse `test_script` + Azure Repos |
| 执行结果 | 测试执行模块 | 失败分析、报告生成 | Dataverse `test_execution_result` + Blob Storage（日志/截图） |
| 失败分析 | 失败分析模块 | 脚本生成（反馈）、报告生成 | Dataverse `failure_analysis` |
| 报告元数据 | 报告生成模块 | 所有模块 | Dataverse `test_report` + Blob Storage（PDF/HTML） |

### 触发关系

| 触发事件 | 动作 | 目标模块 |
|----------|------|---------|
| 用户上传新需求文档 | 触发需求分析 | 需求分析模块 |
| 需求状态变为"已确认" | 建议（非强制）触发用例生成 | 用例生成模块 |
| 用例状态变为"待评审" | 触发 AI 自动评审 | 用例评审模块 |
| 用例状态变为"已通过" | 触发脚本生成 | 脚本生成模块 |
| 用户/CI 触发测试执行 | 调度执行队列 | 测试执行模块 |
| 用例执行失败 | 触发失败分析 | 失败分析模块 |
| 定时/手动触发 | 生成报告 | 报告生成模块 |
| 所有模块的关键事件 | 更新智能体上下文，按需推送通知 | 智能体交互模块 |
