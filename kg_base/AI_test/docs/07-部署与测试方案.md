## 一、部署方案

### 1.1 环境规划

| 环境 | 用途 | Power Platform 环境类型 | Azure 资源 | 数据源 |
|------|------|------------------------|-----------|--------|
| 开发 (DEV) | 开发者自测、功能联调 | 开发者沙箱 | 低配 SKU，按量计费 | 脱敏测试数据 |
| 测试 (TEST) | 集成测试、性能测试 | 测试环境 | 标准配置，手动扩缩 | 合成测试数据集 |
| 预生产 (STAGING) | UAT、AI 质量验收、发布候选验证 | 生产类沙箱 | 预生产配置（接近生产） | 脱敏生产副本 |
| 生产 (PROD) | 正式上线运营 | 生产环境 | 高可用配置，自动扩缩 | 真实业务数据 |

**环境隔离原则：**

- 四套环境物理隔离，数据不互通
- DEV/TEST 共享同一个 Azure AD 测试租户
- STAGING/PROD 使用正式租户
- STAGING 的 Azure 资源配置与 PROD 保持一致，SKU 按需降级
- 连接器、API 密钥、环境变量在不同环境使用独立值

### 1.2 Power Platform 部署

#### 1.2.1 Solution 管理

所有定制组件打包为 **受管 Solution** 在环境间流转：

```
解决方案结构：
└── AITestSolution (发布者: AI_Test_Platform)
    ├── Canvas Apps: AITestDashboard, TestCaseManager, ReportViewer
    ├── Tables: ai_test_run, ai_test_case, ai_test_result, ai_defect_log
    ├── Flows: OrchestrateTestRun, CollectResults, NotifyReviewer
    ├── Connection References: AzureOpenAI, SharePoint, Teams
    ├── Environment Variables: AI_Search_Endpoint, OpenAIModelVersion
    └── Sets: SecurityRole_AITester, SecurityRole_Reviewer
```

**部署流程：**

1. 开发环境以非受管 Solution 开发
2. 开发完成 → 导出为受管 Solution（含所有组件）
3. 导入 TEST → 运行集成测试
4. 测试通过 → 导入 STAGING → UAT
5. UAT 通过 → 导入 PROD

**版本管理：** Solution 版本号遵循 `主版本.次版本.修订号`，与 Git Tag 对齐。

#### 1.2.2 环境变量

| 变量名 | DEV | TEST | STAGING | PROD |
|--------|-----|------|---------|------|
| AzureOpenAI_Endpoint | `https://ai-dev.cognitiveservices...` | `https://ai-test...` | `https://ai-staging...` | `https://ai-prod...` |
| AzureOpenAI_DeploymentName | `gpt-4o-dev` | `gpt-4o-test` | `gpt-4o` | `gpt-4o` |
| Storage_ConnectionString | Key Vault 引用 | Key Vault 引用 | Key Vault 引用 | Key Vault 引用 |
| DevOps_OrgUrl | `https://dev.azure.com/org-dev` | `https://dev.azure.com/org-test` | `https://dev.azure.com/org` | `https://dev.azure.com/org` |
| AISearch_IndexName | `testcases-dev` | `testcases-test` | `testcases` | `testcases` |

环境变量在打包时设为**空值**，导入环境后由管理员在 `Power Platform Admin Center` 中配置实际值，避免密钥泄露。

#### 1.2.3 连接器配置

| 连接器 | 认证方式 | 备注 |
|--------|---------|------|
| Azure OpenAI | API Key（Key Vault 引用） | 每个环境独立 Key |
| SharePoint | OAuth（当前用户） | 自动继承 |
| Teams | OAuth（当前用户） | 自动继承 |
| Azure DevOps | PAT（Key Vault 引用） | 服务账号 PAT |
| SQL Server | Azure AD 托管标识 | 无需密钥轮换 |
| Outlook / Exchange | OAuth（当前用户） | 自动继承 |

**关键点：** 所有手动密钥统一使用 Key Vault 引用。Power Automate 流部署后，首次运行会自动提示确认连接引用，无需手动配置每个连接。

#### 1.3.2 部署脚本示例

```bash
#!/bin/bash
# deploy.sh — Azure 资源部署

RESOURCE_GROUP="rg-ai-test-$ENV"
LOCATION="eastus2"

az deployment group create \
  --resource-group $RESOURCE_GROUP \
  --template-file infrastructure/main.bicep \
  --parameters infrastructure/parameters/$ENV.parameters.json \
  --name "deploy-$ENV-$(date +%Y%m%d%H%M)"
```

#### 1.3.3 CI/CD Pipeline 资源部署

```yaml
# azure-pipelines-infra.yml
trigger:
  branches:
    include:
      - main
  paths:
    include:
      - infrastructure/*

variables:
  - group: AI-Test-Platform-${{ parameters.environmentName }}

stages:
  - stage: Validate
    jobs:
      - job: lint_and_validate
        steps:
          - script: az bicep build --file infrastructure/main.bicep

  - stage: Deploy
    jobs:
      - deployment: DeployInfra
        environment: ${{ parameters.environmentName }}
        strategy:
          runOnce:
            deploy:
              steps:
                - script: |
                    az deployment group create \
                      --resource-group rg-ai-test-$(Environment.Name) \
                      --template-file infrastructure/main.bicep
```

### 1.5 AI 服务部署

#### 1.5.1 模型部署矩阵

| 模型 | 用途 | 部署方式 | 版本策略 |
|------|------|---------|---------|
| GPT-4o | 测试用例生成、自然语言分析 | Azure OpenAI 全局部署 | 指向最新稳定版，季度评估升级 |
| GPT-4o-mini | 分类、标注、简单输出解析 | Azure OpenAI 全局部署 | 同上 |
| text-embedding-3-large | 语义搜索向量化 | Azure OpenAI 全局部署 | 固定版本，确认兼容后升级 |
| GPT-4o (STAGING) | UAT AI 质量评估 | Azure OpenAI 独立部署 | 仅用于验证，与新模型 A/B 对比 |

#### 1.5.2 Prompt 管理

- Prompt 模板使用 **环境变量 + 配置表** 管理，不硬编码在流或函数中
- 每条 Prompt 带版本号，修改 Prompt = 新建版本
- 重要提示变更需先经过 STAGING A/B 测试
- Prompt 与模型版本绑定：换模型时同步回归所有关联 Prompt

#### 1.5.3 AI 模型推送流程

```
DEV 调试 Prompt     →     TEST 自动化回归     →     STAGING A/B 评估     →     PROD 全量上线
    ↓                       ↓                          ↓
新模型/Prompt 在       验证准确率达标            业务方确认输出质量
开发环境试跑           (≥ 预设阈值)               + 与当前版本对比
```

### 2.1 单元测试

#### 2.1.1 Azure Functions（Python）

```python
# tests/test_orchestrator.py
import pytest
from unittest.mock import patch, MagicMock
from orchestrator import generate_test_cases

@pytest.fixture
def mock_openai():
    with patch("openai.ChatCompletion.create") as mock:
        mock.return_value = {
            "choices": [{"message": {"content": '[{"title": "登录测试", "steps": ["打开页面"]}]'}}]
        }
        yield mock

class TestCaseGenerator:
    """AI 用例生成器单元测试"""

    def test_generate_from_prd(self, mock_openai):
        """PRD → AI 用例生成逻辑"""
        result = generate_test_cases("用户登录功能")
        assert len(result) > 0
        assert result[0]["title"] == "登录测试"

    def test_empty_input_raises(self):
        """空输入应抛出异常"""
        with pytest.raises(ValueError):
            generate_test_cases("")

    def test_malformed_response(self, mock_openai):
        """AI 返回非 JSON 时的降级逻辑"""
        mock_openai.return_value["choices"][0]["message"]["content"] = "不是 JSON"
        result = generate_test_cases("登录")
        assert result == []  # 降级返回空列表
```

### 2.2 集成测试

#### 2.2.1 Power Automate 工作流测试

Power Automate 原生不支持自动化测试脚本，采用以下策略：

- **测试流映射：** 每条正式 Flow 配一个对应的测试流，测试流以特定触发器启动（如手动 HTTP 请求）
- **输入样本：** 预置 10-20 组典型输入 JSON（正常流程 + 边界场景）
- **预期验证：** 测试流末尾将结果写入 SharePoint List，测试脚本通过检查列表记录判断通过/失败
- **频率：** DEV 环境每次部署后手动触发一轮，TEST 环境纳入 Pipeline 定期触发

**典型场景清单：**

| 测试场景 | 输入样本数 | 覆盖要点 |
|---------|-----------|---------|
| 发起测试执行 → 接收结果 | 5 | 全链路数据流转 |
| AI 超时降级 | 3 | 捕获超时 → 返回兜底结果 |
| Teams 通知失败重试 | 3 | 通知发送失败 → 自动重试 3 次 |
| 并发流冲突 | 2 | 同一时间触发多条流的隔离性 |

### 2.3 AI 质量测试

这是本项目的重点测试领域，AI 输出的不可确定性需要专门的质量评估机制。

#### 2.3.1 评估指标

| 指标 | 定义 | 目标值 |
|------|------|-------|
| 用例可用率 | AI 生成的测试用例可直接使用（无需人工修正）的比例 | ≥ 80% |
| 用例覆盖率 | 生成的用例覆盖 PRD 需求点的比例 | ≥ 90% |
| 步骤正确率 | 生成的测试步骤无逻辑错误的比例 | ≥ 85% |
| 输出格式合规率 | JSON 格式严格合规的比例 | ≥ 99% |
| 幻觉率 | 出现不存在的功能或组件的比例 | ≤ 3% |
| 回归稳定性 | 相同输入连续 5 次输出的相似度 | ≥ 70% |

#### 2.3.2 评估数据集

建立 **人工标注金标准集**：

| 数据集 | 样例数 | 来源 | 用途 |
|--------|-------|------|------|
| 回归测试集 | 100 | 从真实项目 PRD 提取 | 每次模型变更后回归 |
| 多样性测试集 | 300 | 覆盖不同业务域 | 季度全面评估 |
| 边界测试集 | 50 | 复杂/模糊/空输入 | 稳定性验证 |

金标准集由 QA 团队人工标注，每个样例包含：输入 PRD / 期望输出用例列表。

#### 2.3.3 评估流水线

```python
# scripts/eval_ai_quality.py
"""
用法: python eval_ai_quality.py --dataset regression --model gpt-4o --version v1.2.3
输出: JSON 评估报告，含各项指标 + 差异用例明细
"""

def evaluate(dataset: str, model: str, version: str) -> dict:
    golden = load_golden_set(dataset)         # 加载金标准
    generated = batch_generate(golden.inputs)  # AI 批量生成
    report = compute_metrics(golden, generated)
    diff = find_mismatches(golden, generated)  # 找出差异用例供人工审查
    save_report(dataset, model, version, report)
    return report
```

流水线集成到 CI/CD 中，每次模型/Prompt 变更自动触发。

- **性能：** 90% 的常规操作响应时间满足 SLAs

#### 2.5.3 UAT 流程

| 角色级访问控制 | 按 AITester / Reviewer / Admin 角色逐项测试 | 低角色不能执行高角色操作 |
| 跨租户隔离 | 尝试从 A 环境调用 B 环境 API | 返回 401/403 |
| 未认证访问 | 未登录状态下尝试访问所有页面和 API | 全部重定向到登录或被拒绝 |
| Power Platform DLP 策略 | 验证 DLP 策略是否阻止未授权的连接器 | 违规连接被阻止 |

#### 2.6.2 数据隔离测试

| 测试项 | 方法 | 验证点 |
|--------|------|-------|
| 项目间数据隔离 | 用户 A 登录后是否能查看用户 B 的项目 | 看不到 |
| AI 生成数据隐私 | AI 调用中是否泄露了其他用户的上下文 | 无交叉 |
| 敏感数据脱敏 | 日志和 AI 调用记录中是否有明文密码/Token | 已脱敏或无 |
| SharePoint 权限继承 | 文档库权限是否与用户角色一致 | 一致 |

#### 2.6.3 API 安全测试

| 测试项 | 方法 | 验证点 |
|--------|------|-------|
| 认证绕过 | 移除认证头请求 API | 返回 401 |
| 注入攻击 | 参数中携带 SQL/XSS/NoSQL 注入 | 参数被转义或拒绝 |
| 参数篡改 | 修改请求中的用户 ID 参数 | 服务端校验操作权限 |
| 请求频率限制 | 短时间内高频请求 | 触发频率限制，返回 429 |
| JWT 令牌测试 | 篡改/重放/过期 JWT | 全部被拒绝 |

#### 2.6.4 安全测试工具

```
API 安全测试：OWASP ZAP / Burp Suite
权限验证：手动测试矩阵 + Playwright 自动化
依赖扫描：GitHub Dependabot / Azure DevOps Dependency Scanning
秘密扫描：GitHub Secret Scanning / GitLeaks
```

### 3.2 代码审查流程

```
[开发者提交 PR]
    │
    ▼
[自动化检查]
  ├── Lint 通过?
  ├── 单元测试通过?
  ├── AI 质量评估通过?
  └── 构建成功?
    │
    ▼ 全部通过
[Code Review]
  ├── 至少 1 名 Senior 开发者
  └── 涉及 AI 逻辑的变更 → 额外 QA Review
    │
    ▼ 批准
[合并到目标分支]
    │
    ▼
[自动触发对应环境 Pipeline]
```

**审查重点：**

| 变更类型 | 审查重点 |
|---------|---------|
| AI Prompt 修改 | 输出格式、回退逻辑、安全性 |
| Power Automate 流 | 错误处理、重试策略、并发控制 |
| Azure Functions | 异常处理、日志、资源释放 |
| Bicep/ARM 模板 | 安全配置、密钥管理、网络隔离 |
| Dataverse 表结构 | 索引设计、关系完整性、列类型 |

### 3.3 自动化测试集成

Pipeline 中各阶段的测试执行时机：

```
PR 创建时         → CodeQuality + AIQuality（快速回退）
合并到 feature/*  → CodeQuality + AIQuality + Build
PR → main         → 全量 Pipeline（以上全部）
Scheduled 每日     → 全量 Pipeline + 性能测试（夜间执行）
```

**测试门禁阈值：**

| 门禁 | 阈值 | 阻隔阶段 | 失败处理 |
|------|------|---------|---------|
| 单元测试覆盖率 | ≥ 80% | CodeQuality | 阻断 Pipeline |
| Lint 错误 | 0 | CodeQuality | 阻断 Pipeline |
| AI 用例可用率 | ≥ 80% | AIQuality | 阻断 Pipeline（可手动跳过） |
| 集成测试通过率 | 100% | IntegrationTest | 阻断 Pipeline |
| E2E 测试通过率 | 100% | IntegrationTest | 阻断 Pipeline |
| 性能测试 | 不超过基线 20% | 夜间执行 | 告警，不阻断 |

### 3.4 发布策略

#### 3.4.1 Power Platform

Power Platform 本身支持**直接导入 Solution**覆盖更新，回退策略：

- **正常发布：** 受管 Solution 导入覆盖
- **回退方案：** 导入上一版受管 Solution，恢复上一版环境变量值
- **注意：** Dataverse 表的删除操作不可逆。需要删除表结构的变更，必须先在 DEV 确认无数据依赖，导出时排除数据

#### 3.4.2 Azure Functions

使用 Azure 部署槽（Deployment Slots）：

| 环境 | 策略 | 交换方式 |
|------|------|---------|
| TEST | 直接部署 | 不涉及槽交换 |
| STAGING | 部署到 Slot → 预热 → 交换 | 自动交换 |
| PROD | 金丝雀发布 → 灰度 10% → 全量 | 手动确认后全量切换 |

**回退步骤（生产故障场景）：**

```
1. 触发回退开关
2. Slot 交换回旧版本
3. 确认功能恢复
4. 排查根因
```

#### 3.4.3 AI 模型更新策略

| 变更类型 | 策略 | 回退 |
|---------|------|------|
| 模型版本升级 | STAGING A/B 测试 3-7 天 | 环境变量指向旧模型 |
| Prompt 优化 | 版本化管理，先 STAGING 验证 | 环境变量指向旧 Prompt 版本 |
| 新模型替换 | 并行部署 → 流量切换 → 观察 → 下线旧模型 | 重新切换回旧模型 |
