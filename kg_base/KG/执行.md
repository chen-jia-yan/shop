## 2. 数据模型（目标形态）
### 节点新增字段
```json
{"id":"System:SFDC","type":"System","label":"SFDC","source_docs":["doc::ab12...","doc::cd34..."]}
```
Chunk 节点保留原 metadata，额外加 `source_docs`（通常只含 1 个 doc）。

### 边新增字段
边的身份键 = `(source, type, target)`。加字段：
```json
{"source":"...","target":"...","type":"包含","source_docs":["doc::..."],"provenance_inferred":false}
```
`provenance_inferred=true` 表示该边的来源是回填时推断的（见阶段 1），非精确。

### 文档索引 `kg_versions/doc_index.json`
```json
{
  "doc::ab12...": {"source_file":"#15_SFDC.pptx","chunk_ids":["74ba..."],"node_ids":["System:SFDC",...],"edge_keys":["System:SFDC|使用|Data:Account_T",...]},
  ...
}
```
以及 `file_to_doc.json`：`{"#15_SFDC.pptx":"doc::ab12..."}`（当前每个文件对应的最新 doc 内容哈希）。

### 版本管理
- `kg_versions/v1.json`、`v2.json` …：每个版本是一张完整图谱快照。
- `kg_versions/manifest.json`：`{"active":"v2","history":[{"version":"v2","parent":"v1","ts":"...","ops":[...],"note":"..."}]}`
- `kg_versions/changelog/delta_<ts>.json`：每次 dry-run/apply 的变更明细。
- 原始 `business_kg_enriched.json` 始终不动；v1 = 它 + 回填的 provenance。

## 阶段 2 —— 增量引擎（add / update / delete + dry-run + 版本化 apply + rollback）
写**新模块** `kb_poc/kg/kg_incremental.py`。核心是基于 `source_docs` 的**引用计数**。

### 2.1 子图构建
`build_subgraph_for_document(doc_id) -> {nodes, edges}`：复用阶段 0 找到的抽取逻辑，只跑这一个文档的 chunk，产出该文档贡献的节点和边（含 Chunk 层 + 实体/语义层）。如果阶段 0 结论是"抽取无法按单文档跑"，则：Chunk 层按文档精确构建；实体/语义层退化为"对该文档 chunk 单独跑抽取后合并"，并在注释里写明限制。

### 2.2 计算变更计划（不写盘）
`plan_delta(ops) -> DeltaPlan`，`ops` 是一组 `{action: add|update|delete, file 或 doc_id}`：
- **add(D)**：算 `new_doc_id`；若已在图中（同内容）→ no-op。否则 build 子图，对每个节点/边：已存在 → 往 `source_docs` 加 `new_doc_id`（记为 touched）；不存在 → 新增（记为 added）。
- **delete(D)**：解析 doc_id；对每个 `source_docs` 含该 doc 的节点/边 → 移除该 doc；移除后 `source_docs` 为空 → 标记 removed。再清理：任一端点被 removed 的边一并 removed。
- **update(D)**：= delete(old_doc_id) + add(new_doc_id)，old/new 由 `file_to_doc` 与新内容哈希得到；两边合并成一个计划（净增净删）。
- 全程只在内存算，产出 `DeltaPlan{nodes_added, nodes_removed, nodes_touched, edges_added, edges_removed, edges_touched}`。

### 2.3 dry-run
`plan_delta` 后打印**人类可读报告**（+N 节点 / −M 节点 / ~K 边…，并列出被删节点的 label 和它们归零的原因），把计划写到 `kg_versions/changelog/delta_<ts>.json` 和预览图 `kg_versions/_dryrun/preview.json`。**不动 active、不写新版本**。

### 2.4 apply（我手动跑）
`apply_delta(plan)`：读 active 版本 → 应用计划 → 写 `kg_versions/v{N+1}.json`（原子写）→ 更新 `manifest.active=v{N+1}` 并追加 history（含 parent、ops、delta 文件名）→ **绝不改旧版本文件**。

### 2.5 rollback（我手动跑）
`rollback()`：把 `manifest.active` 指回 `history` 里的上一个版本。旧版本文件都在，纯指针回退，秒级可逆。

### 2.6 loader 接入（开关，默认关）
改 `get_default_kg()`：新增环境变量开关 `KB_KG_USE_VERSIONS`（默认关）。开关**开**且 `manifest.json` 存在时，加载 `manifest.active` 指向的版本；否则**完全保持现在的行为**（读 `business_kg_enriched.json`）。给我看这段 diff。

## 必须覆盖的边界情况（设计时就要处理，别留到后面补）
1. **共享实体**：被多文档引用的节点/边，删一个文档不能删它（引用计数 > 0 就保留）。
2. **更新 = 删旧+加新**，不要原地改。
3. **重复新增**：同一文档内容哈希已存在 → no-op，不重复加。
4. **孤儿清理**：`source_docs` 归零的节点删除；任一端点被删的边删除；不能留悬空边。
5. **Chunk 层与文档 1:1**：Chunk 节点和 mentioned_in 边随文档精确增删。
6. **inferred provenance 边**：删除时保守处理——只有当两端实体的 `source_docs` 都空了才删这条推断边，避免误删。
7. **原子写**：临时文件 + rename，中途崩溃不损坏 active。
8. **首次运行前**：先把 `business_kg_enriched.json` 复制一份备份。
