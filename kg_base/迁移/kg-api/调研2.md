【一、响应格式（修正，照 TAP 实际规范）】
1. 成功：直接返回业务对象，不包 {code, data}。列表返回 {items, total, page, page_size}；详情直接返回对象
2. 业务错误（找不到等）：HTTP 200，响应体 {"code": "CCB001", "message": "..."}
3. 参数不合法：HTTP 422（使用 FastAPI 默认的校验，不改成 200）
4. 未捕获的异常：HTTP 500，响应体 {"code": "CCB500", "message": "服务内部错误"}，不返回异常信息
5. 分页：page 默认 1，最小 1；page_size 默认 20，范围 1–100。照 TAP 的 ListConversationsRequest 写法
6. 列表类的返回模型，照 TAP 的 XxxListData 写法，每个资源单独定义

【二、Chunk 节点的处理（新增规则）】
- "实体节点"指 type != "Chunk" 的节点；"实体关系"指两端都是实体节点的关系
- stats：节点、关系分两组统计（实体 / 切片），并给出各类型的数量
- graph/overview：只返回实体节点和实体关系，不返回 Chunk 节点、mentioned_in、related_chunk。limit 默认 300，最大 500
- nodes/search：默认只搜实体节点；请求加 include_chunks（默认 false）。返回 items 时加上 degree（只统计实体关系的数量）
- nodes/expand：请求加 include_chunks（默认 false），默认只展开实体邻居
- 新增接口 POST /tap/ai/kg/nodes/chunks/list：请求 node_id、page、page_size；
  返回这个实体出现在哪些切片：chunk_id、source_file、page_or_sheet、label。mentioned_in 两个方向都要查，并说明实际是哪个方向

【三、字段对应】
- 节点：id = node_id，name = label，type = type，properties = metadata_json 解析后的对象（为空时给 {}）
- 节点的 source_files：
  - Chunk 节点：取 metadata_json.source_file
  - 实体节点：通过 kg_node_sources 的 doc_id，找到同一 doc_id 下 Chunk 节点的 source_file，去重
  - doc_id → source_file 的对应关系，在程序启动时算一次，缓存起来
- 关系：id = edge_id，source = source_id，target = target_id，type = type，properties 中包含 inferred（provenance_inferred 转成 true/false）、bridge_reason，以及 metadata_json 解析后的内容
- files/list：每个文件一行：doc_id、source_file、切片数、实体数（kg_node_sources 中这个 doc_id 下的实体节点数）、实体关系数（kg_edge_sources 中这个 doc_id 下的实体关系数）。按 source_file 升序排列
- graph/overview 按文件过滤：请求 doc_id（可选）。返回 kg_node_sources 中属于这个 doc_id 的实体节点，以及两端都在这些节点里、并且 kg_edge_sources 中属于这个 doc_id 的实体关系
