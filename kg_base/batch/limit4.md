# 任务:找回批处理里 OCR "解析慢" 的原因并提速(配置档 + 重复解析)

## 背景
同样的文件,原始 `python -m kb_poc ingest`(单进程循环)每个文件秒过;新批处理系统即使 OCR 引擎已初始化成功,单个文件的解析/OCR 仍要几分钟。既然原始做同样的 OCR 却很快,说明新系统在"解析/OCR 推理"这一步做得更慢或更重。请定位并修复。

## 需要排查与修复的点

### 1. 对比新旧 OCR 引擎配置(重点)
- 找到原始 `kb_poc ingest` 初始化 PaddleOCR / OCR 引擎时用的参数,和新系统 `LocalPaddleProvider`(kb_poc/parsing/ppt_ocr.py 等)用的参数,逐项对比:
  - `cpu_threads`(新系统很可能被设成了 1,单线程会让推理慢数倍)
  - `enable_mkldnn`(是否被关掉)
  - `use_angle_cls` / 方向分类
  - det / rec 模型、图像 resize / limit_side_len 等影响推理量的参数
- 输出一份明确对比:新旧各是什么值、哪些被调慢了。

### 2. 在"安全范围"内恢复 OCR 快档
- 之前为治崩溃把 OCR 掐成保守档(单线程等)。现在重文件已走独立可杀子进程隔离,崩溃已被兜住,不必再靠单线程保命。
- 把 OCR 推理配置调回快档:`cpu_threads` 提到合理的多线程值(可配置,如 4)、`enable_mkldnn=True`(若可用)。
- 所有速度相关参数做成**可配置**,方便按机器调优;默认给一个明显快于单线程的值。

### 3. 消除两阶段的重复解析
- 检查两阶段(text / full)是否把同一个文件**打开并完整解析了两遍**。
- 目标:文件只解析一次。text 阶段抽文本;full 阶段**只对图片做 OCR**,不要重新解析/重新抽取整份文档的文本内容。若当前实现是两阶段各自完整重解析,请改为单次解析 + 阶段性产出,或让 full 阶段复用 text 阶段已解析的结构。

### 4. 确认 OCR 工作量与原始一致
- 对同一个文件,确认新系统 OCR 的图片数量、分辨率与原始一致,没有多 OCR 小图/装饰图,也没有用比原始更高的分辨率。
- 如有,增加"跳过过小图片 / 限制最大边长"的可配置阈值,和原始行为对齐。

## 约束
- 只用标准库 + 已安装包,不新增需下载依赖;不改动/不删除 PaddleOCR 本地模型缓存;Windows spawn;索引仍用 Azure AI Search。
- OCR 快档配置的改动不得破坏"重文件隔离子进程"这一崩溃兜底。

## 验收标准
- 单个含图文件的 OCR 推理耗时明显下降,接近原始 `kb_poc ingest` 在同文件上的水平。
- 耗时日志中 `parse_ms`(含 OCR 推理)大幅下降;同一文件不再被解析两遍。
- 新旧 OCR 配置对比清单产出,且新系统不再是单线程慢档。
- 重文件隔离与崩溃恢复行为保持不变。
