# 任务:解决 embedding 持续被 429 限流、批量比单文件还慢的问题

## 背景
本地批处理系统,多进程(ProcessPoolExecutor,MAX_WORKERS=4)处理文件,每个文件切片后调 embedding API(Azure),再写 Azure AI Search。现象:embedding 持续 429,已经 honor 了 Retry-After 仍然一直被限;并发越高越慢,79 个文件今天只跑成功 17 个。**配额数字未知,无法查看。**

## 根因判断
1. 每个进程各自调 embedding、各自限流 → 汇总速率超配额,形成"羊群效应"。
2. honor Retry-After 后所有请求同步复活、再次同时冲 → 锯齿式反复 429。
3. 可能是逐条发 embedding 请求,请求数(RPM)过高。

## 要实现的改造

### 1. 全局单通道 + 自适应限速(AIMD)
- 所有 embedding 调用必须经过**同一个限速器**(集中到父进程统一发,或用 SQLite/文件锁做跨进程令牌桶),不允许每个进程各自限流。
- 限速器采用自适应速率(AIMD),**无需知道配额数字**:
  - 每成功 N 批,发送速率(或每分钟令牌数)**加法小步增加**;
  - 一旦收到 429,速率**乘法减半**,并进入冷却;
  - 长期自动收敛到配额线以下的最优速率。
- in-flight 的 embedding 请求并发数控制在很小(1~3 可配置)。

### 2. 退避加随机抖动
- 收到 429 时,等待 = Retry-After(若有)+ 随机抖动(如 0~2 秒);无 Retry-After 时用指数退避 + 抖动。
- 目的:避免多请求同步复活后再次同时撞墙。

### 3. 请求内批量(降请求数,关键)
- 把多条 chunk 合并到**一次** embedding API 调用里,在不超单请求 token 上限的前提下尽量多塞(可配置 batch 大小)。
- 确认当前不是在循环里逐条发送;若是,改为真正的批量输入调用。

### 4. 阶段解耦
- CPU 密集阶段(解析、OCR)保持多进程并行;
- embedding 阶段全部汇集到上面的单一限速通道,不再每进程独立发。

### 5. 幂等,避免重复嵌入
- 按 chunk 内容哈希缓存/跳过已嵌入内容;文件级用整文件哈希跳过未变更文件。
- 不要因为重跑就清空已入库数据。

## 约束
- 只用 Python 标准库 + 已安装包,不新增需下载的依赖。
- 全部本地运行,索引仍用 Azure AI Search。
- Windows,多进程 spawn,入口需 `if __name__ == "__main__"`。

## 验收标准
- 连续运行时 429 频率显著下降,且不再出现"等待→全速→立刻再 429"的锯齿。
- 相同一批文件,总完成时间明显短于当前;并发调到 1 与调到 4 时,吞吐不出现"越并发越慢"。
- 日志能打印:当前自适应速率、每次 429 的降速动作、每个 embedding 请求打包了多少条 chunk。
- 提供把 MAX_WORKERS 和 embedding 并发数、batch 大小外部可配置的入口。
