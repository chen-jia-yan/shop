### 3. 這條鏈路的檢索—用的是 HybridRetriever，不是 Answerer

`search_kb` 工具直接调用 `self.answerer.retriever.search()` ——即 `HybridRetriever.search()`：
- `kb_poc/skills/kb_retrieval/runtime.py:108`：
```python
hits = self.answerer.retriever.search(
    query=query,
    top_k=top_k,
    alternate_queries=alternate_queries,
    query_intent=query_intent,
)
```
`Answerer.answer()` 本身没有被生产链路调用（见下方第8题对比）。生产链路走的是 Agent 调用 `search_kb` 工具 → 直接调用 HybridRetriever。

`HybridRetriever.search()` 的检索流程：

- `retrieval/retriever.py:73` —入口
- 先精确匹配（`_exact_match_hits`）
- 收集 lexical candidates（`_collect_lexical_candidates`，含 BM25 + 可选向量）
- 向量检索（如果 embedding client 可用，`_merge_candidates` 中合并）
- 重排序（`_reranker.rerank`，支持 heuristic / cross-encoder）
- 门禁过滤（`score >= min_score`，`coverage >= min_coverage`，或 RRF 模式直接信任排名）

### 4. 除了检索到的 chunk，还读了哪些额外来源？

| 邻近 chunk | `expand_evidence` 工具展开前后相邻 chunk | `skills/kb_retrieval/runtime.py:202-275` | LLM 可主动调用 |

### 5. 最终返回什么？

返回结构：`FinalGroundedAnswer`（`agent/models.py:23`）：
```python
class FinalGroundedAnswer(BaseModel):
    answer: str                  # 最终回答文本（含 结论 / 详细说明 / 出处 三栏）
    status: Literal["grounded", "insufficient_evidence"]
    work_logs: list[WorkLogItem] # 可阅的工作步骤记录 (decision/tool_call/tool_result/final_answer)
    raw_output: str | None       # LLM 原始输出
```

返回的是纯文本（Markdown 格式的三栏式答案：结论 + 详细说明 + 出处表格），但不直接返回流程图图形——流程图资讯以文字描述形式嵌入答案（泳道、主流路径、分支/汇合点等）。

### 6. 这条链路能不能被程序单独调用？
可以。签名如下：

```python

    user_query="你的问题",
    allow_ingestion=False,
    max_rounds=10,

# 方式 2: 流式 (SSE)

    messages=[{"role": "user", "content": "你的问题"}],
    allow_ingestion=False,
    max_rounds=10,
):
    # event 是 {"type": "phase", ...} 或 {"type": "result", "payload": {...}}
    ...

# 方式 3: 带到对话历史
answer, updated_messages = orchestrator.run_chat_turn(
    messages=[...],
    allow_ingestion=False,
    max_rounds=10,
    on_phase=None,
)
```

- `kb_poc/agent/orchestrator.py:47` — `run_chat_turn()`

### 8. 对每道 gold 题的检索与答案生成
#### a. 用哪个函数做检索？
`RagEvalSkillRuntime._search()` —调用的是 `Answerer.search()`（不是直接调 HybridRetriever）

- `kb_poc/skills/rag_eval/runtime.py:186`：
```python
def _search(self, question: str, top_k: int) -> list[dict[str, Any]]:
    if self._answerer is None:
        raise RuntimeError("检索器未初始化")
    hits = self._answerer.search(question, top_k=top_k) # ← 道行
```

而 `Answerer.search()` 内部：

- `kb_poc/qa/answerer.py:51`：
```python
def search(self, query: str, top_k: int | None = None) -> list[SearchHit]:
    expanded_query = expand_query(query)
    ...
    hits = self.retriever.search(...) # self.retriever 是 BM25Retriever? 不是, 是 HybridRetriever --- 等等, 看下面
```

关键发现：`Answerer.__init__()` 用的是 `BM25Retriever`，不是 `HybridRetriever`

- `kb_poc/qa/answerer.py:34`：
```python
self.retriever = BM25Retriever(index_path=self.index_path, settings=settings)
```

这意味着评估链路用的是 **BM25Retriever（纯BM25，不含向量检索、不含 RRF、不含 cross-encoder reranker）**，与生产链路的 HybridRetriever 是不同的检索器。

#### b. 用哪个函数/哪个模型生成被评测的答案？
`RagEvalSkillRuntime._generate_answer()` —它调用的是 `OpenAICompatibleClient`（与生产链路同一个 LLM provider），但用独立的 prompt，不是走 Agent 链路：

- `kb_poc/skills/rag_eval/runtime.py:210`：
```python
def _generate_answer(self, question: str, context_docs: list[dict[str, Any]], client: Any) -> str:
    from ..kb_advanced_qa.runtime import AdvancedQASkillRuntime
    from ...tool_schemas import CitationItem
    ...
    material = AdvancedQASkillRuntime._build_answer_text(
        user_query=question,
        deduped_hits=deduped,
        citations=citations,
    )
    messages = [
        {"role": "system", "content": "あなたは日本の保険システムに関する知識アシスタントです。..."},
        {"role": "user", "content": f"【質問】\n{question}\n\n【素材】\n{material}"},
    ]
    response = client.create_chat_completion(messages=messages, tools=None) # ← 道行
```

结论：评估链路走的是【纯RAG】——直接用检索结果拼接成 prompt 让 LLM 一次生成答案，不走 AgentOrchestrator 的工具调用循环。这与生产链路（Agent + search_kb + query_business_graph 多轮编排）完全不同。

评估链路的特点：
- 单次 LLM 调用生成答案（`tools=None`，不允许工具调用）
- 没有多轮检索、没有知识图谱查询、没有流程图验证、没有 evidence expansion
- 复用了 `AdvancedQASkillRuntime._build_answer_text()` 和 `_deduplicate_hits()` 做素材拼接

# 10. 检索诊断指标
## Toehold召回
- 计算位置：`kb_poc/skills/rag_eval/runtime.py:270` — `_score_toehold()`
- 计算方式：纯规则，不经LLM：
  - 优先用 `expected_file`（gold set中的纯文件名）做 casefold 子串匹配
  - 兜底用 `expected_source`（正则）
  - 命中 → score=5，未命中 → score=1

## 上下文相关性（context_relevance）
- 计算方式：LLM裁判（在 `_judge()` 的prompt中与4个答案维度一起打分）
- 裁判prompt中定义：`"context_relevance: 检索上下文与问题是否相关，噪音是否可接受"`（runtime.py:407）
- 打分也是1-5分制

# 两条链路的关键差异总结
| 维度 | 生产链路（Agent） | 评估链路（rag_eval） |
| ---- | ---- | ---- |
| 检索器 | HybridRetriever（BM25 + 向量 + RRF + reranker） | BM25Retriever（纯BM25） |
| 检索调用 | `RetrievalSkillRuntime.search_kb()` → `answerer.retriever.search()` | `Answerer.search()` → `self.retriever.search()` |
| 答案生成 | Agent多轮编排（rewrite_query → search_kb → expand_evidence → query_business_graph → LLM整合） | 单次LLM调用（检索结果拼接成prompt，无工具） |
| 知识图谱 | ✅ 可用 `query_business_graph` + `search_kb` 自动注入KG | ❌ 不使用 |
| 额外扩展 | ✅ `expand_evidence`（邻近chunk） | ❌ 不使用 |
| 流程图处理 | ✅ `validate_flowchart_edges` + LLM自行分析 | ❌ 没有（只有原始chunk内容） |
| 返回格式 | FinalGroundedAnswer（三栏式：结论/详细说明/出处） | 纯日文本（一次性生成） |
