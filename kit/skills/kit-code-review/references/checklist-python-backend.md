# 清单：Python 后端（FastAPI + SQLAlchemy + 插件化项目）

## 分层
- [ ] 路由函数只做：参数解析、调用服务、转换响应；没有直接写 SQL 或业务判断。
- [ ] 服务层不依赖 FastAPI 的 Request/Response 对象。
- [ ] 仓储层只负责数据库读写，返回模型或简单数据，不抛 HTTP 异常。

## 接口
- [ ] 请求、响应都有 Pydantic 模型；字段名与同模块其他接口风格一致。
- [ ] 错误用项目统一的异常类型/错误码，而不是随手 `raise HTTPException(500)`。
- [ ] 分页、排序参数和已有列表接口一致。

## 数据库
- [ ] ORM 模型类定义在模块顶层（**绝对不能嵌套在另一个类里**——曾导致表没注册、迁移缺表）。
- [ ] 状态更新用“条件更新”（`UPDATE ... WHERE id=? AND status=?`）防止并发覆盖，并检查影响行数。
- [ ] 事务边界清楚：一次业务操作要么全部成功，要么全部回滚；没有在循环里每条都 commit。
- [ ] 查询带索引字段过滤，没有全表扫描后在 Python 里过滤。
- [ ] 数据库驱动在当前环境确实可用（曾出现测试环境没有对应驱动导致导入失败）。

## 配置
- [ ] 配置项在 settings 类里声明了类型和默认值；代码直接用 `settings.xxx`，**不要** `getattr(settings, "xxx", 默认值)`（会掩盖拼写错误）。
- [ ] 新功能开关的默认值是否合理？默认开启时缺少必要配置要能安全降级或明确报错。
- [ ] 测试里通过参数或 fixture 注入配置，不读取真实 .env。

## 插件 / 模块边界
- [ ] 插件之间通过约定的接口（contracts）交互，没有直接导入别的插件的内部模块。
- [ ] 要求“隔离”的模块（例如 schema 定义文件）没有导入项目里的重依赖。
- [ ] 没有修改别人负责的模块（例如同事的问答插件）。

## 日志与可观测
- [ ] 关键步骤有日志（开始、成功、失败原因），日志里带业务 ID，便于排查。
- [ ] 失败信息足够定位问题，但不包含密钥和完整用户数据。
