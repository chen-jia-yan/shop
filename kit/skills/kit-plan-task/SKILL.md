# 任务规划（只读）

## 什么时候用
- 用户给了一个新需求、一个迁移任务、一份验收问题清单。
- 需求里有“然后/还有/另外”，一次包含好几件事。
- 上一轮执行出现了“只做了一部分”“改到了不该改的地方”。

## 绝对禁止
1. 绝对禁止在规划阶段修改任何文件（包括“顺手”修个小问题）。
2. 绝对禁止读取 .env、.env.example、providers.json 等可能含密钥的文件。
3. 绝对禁止凭印象写文件路径和函数名：每一个都要先用 grep / glob / view 确认存在，并写出 `文件:行号`。
4. 绝对禁止把多个不相关的改动塞进同一步。

## 步骤
1. **复述目标**：用 1～3 句话写出“做完以后，用户能看到什么变化”。如果说不清，列出要问用户的问题，停下来等回答。
2. **摸清现状**：
   - 用 grep / glob 找到相关入口（接口、服务、仓储、测试），每个写 `文件:行号` 和一句话作用。
   - 找一个项目里“同类功能”的现成写法当参照（例如已有的另一个接口），写出路径。
   - 如果项目有风格包（技能名 style- 开头），先加载它，按卡片对照。
3. **列出受保护区域**：配置里标为受保护的目录、同事负责的模块、锁定文件（pyproject.toml、uv.lock 等）。计划里任何一步都不能碰它们。
4. **拆步骤**：每一步满足——
   - 只改 1～4 个文件，写出完整路径；
   - 有明确的完成标准（可以被一条命令或一个断言证明）；
   - 有验证命令（具体到测试文件或 `-k` 关键字）；
   - 能单独提交（每步做完都可以 commit，出问题好回退）。
5. **标风险**：每步写一个“最可能出错的地方”，以及怎么提前发现（例如：改了模型类要确认没有嵌套定义；改了导入要确认没有循环导入）。
6. **写范围文件建议**：给出第一步的 `scope` 命令，方便用户锁定修改范围：
   `{{PYTHON}} {{KIT_ROOT}}/tools/scope.py set --project <项目名> --task "<步骤标题>" --files <文件1> <文件2>`
   （这条命令由用户自己运行；规划阶段你只负责写出来。）

## 输出格式
```
【目标】……
【现状】（文件:行号 — 作用）
【参照写法】……
【受保护区域】……
【步骤】
步骤 1：标题
  - 修改文件：……
  - 完成标准：……
  - 验证命令：……
  - 风险与提前发现办法：……
步骤 2：……
【需要用户决定的问题】（没有就写“无”）
【核对表】
- [ ] 每个路径都用工具确认过存在
- [ ] 每步不超过 4 个文件
- [ ] 每步都有验证命令
- [ ] 没有任何一步涉及受保护区域
- [ ] 没有修改任何文件
```

## 不要做
- 不要写“优化相关代码”“完善测试”这类说不清改什么的步骤。
- 不要在计划里写实现代码的完整内容（那是下一阶段的事，写了会浪费额度）。
- 不要假设依赖已经安装；不确定就写成“需要用户确认”的问题。
