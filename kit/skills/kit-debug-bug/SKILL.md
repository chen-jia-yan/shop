# 定位并修复问题

## 什么时候用
- 有错误信息、失败的测试、异常行为。
- 上一次的“修复”没有效果，或者修好一个又冒出一个。

## 绝对禁止
1. 绝对禁止没复现就改代码。
2. 绝对禁止只凭错误信息的最后一行下结论（例如看到 `ModuleNotFoundError` 就说“装个包”）——先读完整堆栈。
3. 绝对禁止通过删除、跳过、弱化测试来“修好”问题。
4. 绝对禁止安装依赖、改 pyproject、执行 git 写操作；需要时写进报告由用户决定。
5. 绝对禁止读取 .env；需要知道配置时问用户“某个配置项是否设置”，不要读值。
6. 绝对禁止对共享资源做写操作来“试一下”（共享数据库、只读索引、别的团队的数据）。

## 步骤
1. **复现**：写出最小复现命令（具体到测试文件和 `-k`），运行，贴原始输出。复现不了就停下，列出需要用户提供的信息（完整日志、输入文件类型、配置开关状态）。
2. **读完整证据**：
   - 堆栈从下往上读，找到**第一个属于本项目代码**的帧，写 `文件:行号`。
   - 区分“收集阶段报错”（ERROR collecting，通常是导入问题）和“执行阶段失败”（FAILED，通常是逻辑问题）。
   - 批量失败时先分类：按错误类型统计数量（例如：路径问题 N 个、超时 N 个、加密文件 N 个、数据库连接 N 个），先处理数量最多或影响最大的一类。
3. **提出假设**：至少写 2 个可能原因，每个写“如果是这个原因，还应该能看到什么现象”。
4. **验证假设**：用只读手段逐个排除（view 代码、grep 引用、加一条临时打印再删掉、单独运行一个小命令）。写出每个假设“成立/排除”和证据。
   - 典型陷阱：`ImportError: cannot import name` 很可能是循环导入，不是缺包；在 Python 里单独 `import 那个模块` 看看第一个报错在哪。
   - 依赖“缺失”时，先确认是不是当前虚拟环境里根本不该有它（例如 SDK 只在另一个项目的环境里）。
5. **根因深度检查**：问三次“为什么会这样”，直到落到一个可以改的具体代码或配置上。
6. **最小修复**：只改导致问题的地方；改动不超过修改范围。
7. **回归测试**：补一条“修之前失败、修之后通过”的测试；运行它和相关测试，贴原始输出。
8. **记录教训**：如果这个问题以后可能再发生，建议用户用 `/kit-memory` 记一条教训（写出建议的 subject 和 fact）。

## 输出格式
```
【现象】……
【复现命令与原始输出】……
【第一个项目内的堆栈位置】文件:行号
【假设与验证】
1. 假设：…… 预期现象：…… 验证：…… 结论：成立/排除
2. ……
【根因】（追问三次后的结论）
【修复】文件 — 改动
【回归测试】命令 + 原始输出
【建议记住的教训】（没有写“无”）
【核对表】
- [ ] 先复现再修改
- [ ] 至少两个假设并逐个验证
- [ ] 没有删除/跳过/弱化测试
- [ ] 补了回归测试且通过
- [ ] 没有越界修改、没有装依赖、没有 git 写操作
```
