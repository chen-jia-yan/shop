## 需求描述
详细读取这个项目的切片索引的流程以及参数设置，存储情况的细节。
然后将切块的内容变成可视化的形式，不仅仅是存储在json里，结构化分层放在ui页面，并且可以通过调参的形式对于切的不好或者不满意的切块可以进行调整，可以通过参数来控制切片内容。搜集符合想法以及想实现的功能的高质量工程化的对应工程或者已实现落地方案，要求可验证可复用，高价值不是豆腐渣工程半成品，是取得成果的项目，输出本项目的实现思路，以及改动范围的大致评估。

## 初步方案
【Miya的專屬小col】先给结论：**你这个想法是靠谱的，而且和当前项目很贴；难点在于要把现在“面向入库的切片结果”补成“面向人看的调参工作台”**。

已确认的是，这个项目本身已经有切片、结构化 artifact、Web UI、管理接口这些基础；
判断：先做**切片可视化 + 参数试切 + 人工对比确认**这一层，改动范围**中等**，不是小改，但也没到要推翻 ingestion 主链路的程度。

### 已确认的事实
1. 当前切片主流程在 `kb_poc\ingestion\ingestor.py`，按文档先 parse 成 `ParsedDocument.segments`，再 `_chunk_document()` 按 segment 切块；
2. 切块参数来自 `kb_poc\config.py` 的环境变量，例如：
    - `KB_CHUNK_SIZE=520`
    - `KB_CHUNK_OVERLAP=80`
    - `KB_PPT_CHUNK_SIZE=900`
    - `KB_OCR_CHUNK_SIZE=260`
    - `KB_PDF_CHUNK_SIZE=420`
3. 切块规则：**按行累积**，不是按 token 精准切；而且 **chunk 不跨 locator**，也就是不会跨 slide / sheet。PPT、流程图页会尽量整页保留；
4. Excel/PPT 解析时还会把 structured / semantic / ocr artifact 写到 `data\artifacts\...`，路径会挂在 chunk 的 `metadata.artifact_path`上；
5. 本地索引落在 `data\index.json`，管理侧批处理 JSONL 落在 `data\kb_admin\jsonl\file‑*.jsonl`，Azure Search 里则把 metadata 基本都转成字符串字段存进去。

> 这说明 “结构化展示切片来源和层级”天然有抓手，不需要硬猜原文结构。

### 落地思路
**不要一上来改正式入库链路，而是先单独做一个「切片调试工作台」**。

后端新增一组只读/试运行接口：
1. 读取某文件已有 structured artifact 和 chunks；
2. 用一组临时参数对单文件重新 parse/chunk，但**不写正式索引**；
3. 返回「原始结构树 + 分段 + chunk 列表 + chunk 命中边界说明」；
4. 用户在 UI 上修改 `chunk_size` / `overlap` / `content_type profile` / 是否保留整页 / OCR块合并策略 后重新预览。

前端放在现有 `kb_poc\ui\modern_chat_page.html/js` 体系里新增一个 tab，不必重做 UI 框架。先解决“看得见、调得动、能对比”，再决定是否把参数固化进正式批处理。

## 当前项目切片/存储关键点
|模块|路径|现在在做什么|对你的需求有什么价值|
|---|---|---|---|
|切片入口|`kb_poc\ingestion\ingestor.py`|`_chunk_document()` 遍历 segment，按 content_type 选 chunk profile，再`_split_text()`按行切|这是“调参试切”的核心函数，最适合做预览接口|
|参数来源|`kb_poc\config.py`|用环境变量定义 text/ppt/ocr/pdf 的 size & overlap|现在是全局静态参数，后面可扩展为“UI临时参数覆盖”|
|PPT解析|`kb_poc\parsing\pptx_parser.py`|每页一个 segment，抽标题、段落、表格、备注、OCR、流程图，并写 structured/ocr/semantic artifact|想做“结构化分层显示”，这里的信息最完整|
|Excel解析|`kb_poc\parsing\excel_parser.py`|每 sheet 一个 segment，保留 cell_range、shape、OCR、flowchart，并写 artifact|很适合在 UI 上做 sheet → block → chunk 的层级树|
|元数据模型|`kb_poc\models.py`|`DocumentChunk` + `ChunkMetadata`，含 `page_or_sheet`、`title_path`、`block_type`、`artifact_path`、`ocr_blocks`等|UI展示不需要重新发明 schema|
|本地存储|`kb_poc\indexing\store.py`|`data\index.json`保存 content、metadata、tokens、embedding|适合做“已入库 chunk 查看”|
|Azure存储|`kb_poc\indexing\azure_search_store.py`|metadata大多被转成字符串写入Azure Search|能检索，但不适合作为UI精细调试，调试更应读本地artifact|
|管理批处理|`kb_admin\ingestion.py`|生成单文件chunk JSONL、分text/ocr phase、写入`data\kb_admin\jsonl`|适合做“批次级切片结果回放”|
|UI入口|`kb_poc\ui\api_admin.py` + `modern_chat_page.*`|已有多页签和管理接口|可以直接扩展，不必新开一个前端项目|

## 改动评估

## 外部高质量工程参考清单
> 目标：借鉴设计思想，而非直接整体替换框架。

|项目|适合拿来借鉴什么|为什么值钱|不适合直接照搬的点|
|---|---|---|---|
|**Docling**|文档结构树、lossless JSON、复杂文档解析思路|对表格、版面、扫描件、结构保留很强，特别适合保险资料|它不是现成 chunk 调参UI，接入成本也不低|
|**Unstructured**|chunking策略设计、元素级traceability、参数模型|`by_title`、`max_characters`、`overlap`这套非常适合做试切面板|你现在已有自己的parser，直接替换会比较重|
|**Langfuse**|记录“哪组切参导致了什么检索效果”|很适合后面做线上观察、失败样本回溯|不是文档结构可视化工具|
|**Haystack**|流水线编排、A/B实验框架思路|适合以后把 ingestion 管线做得更模块化|现在引入会偏重，不是第一步|
|**LlamaIndex**|多种chunker实验层|适合拿来做对比试验|对于当前Excel/PPT结构可视化帮助没那么直接|
|**Argilla**|人工标注“这个切块不好”|适合后续业务员/标注员反馈闭环|不是核心架构，只能做辅助层|
|**Ragas / TruLens**|评估不同切参对问答效果的影响|有助于避免“看着顺眼但问答变差”|不能替代chunk可视化|

> 核心结论：**不建议直接替换现有解析框架，参考理念，在现有代码上开发自定义 chunk‑debug UI**。项目已经实现本地OCR、Excel/PPT结构提取、artifact落盘、Azure Search入库，硬切换框架风险更高。

## 分阶段落地实现思路
### 第一阶段（优先实施，最小工程化版本，不改动正式入库链路）
目标：**单文件切片调试工作台**
1. 后端复用现有解析逻辑：`kb_poc\parsing\pptx_parser.py`、`kb_poc\parsing\excel_parser.py`、`kb_poc\ingestion\ingestor.py`
2. 新增只读预览接口：读取结构化artifact、读取现有chunk、使用临时参数调用`_chunk_document()`重新切片，返回新旧切片对比diff。
3. 前端扩展现有页面 `kb_poc\ui\modern_chat_page.html/js`，新增独立Tab页面：
    - 左侧：文档结构树（sheet/slide → block层级）
    - 中间：参数控制面板
    - 右侧：Chunk卡片列表
4. 交互：点击Chunk卡片，溯源对应的`page_or_sheet` / `title_path` / `block_type` / `artifact_path`，解释切片边界来源。
5. 本阶段**不写入正式索引**，仅用于预览调参。

### 第二阶段（后续迭代）
将调试完成的参数方案持久化为可发布配置：支持全局默认、按文档类型、单文件覆盖的参数策略；将配置接入 `kb_admin\services.py`、`kb_admin\worker.py` 的正式批处理入库链路。
> ⚠️ 该阶段需要重点考虑worker稳定性、增量更新、批量处理一致性、参数优先级、版本回退机制。

## 最小可行版本（MVP）清单
1. 新增「切片调试页」Tab；
2. 支持选择单个文档文件；
3. 展示 `structured artifact` 结构树 + 当前已生成 chunk 列表；
4. 支持调整 `chunk_size` / `overlap` / 内容类型profile，执行重新预览；
5. 提供修改前后切片对比（before/after diff）；
6. MVP阶段不写入正式索引，纯调试预览。

> 该方案收益最大、风险最低，贴合项目现状。下一步可继续细化接口定义、页面布局、数据结构、待修改文件清单的详细设计。
