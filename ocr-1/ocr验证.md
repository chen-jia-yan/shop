# OCR 改动验证步骤

## 改动前(准备)
1. 备份数据库:复制一份 `ingest.db`(改坏了能回退)。
2. 准备一小批测试文件:2–3 个即可,其中**至少 1 个重文件**(会走独立子进程隔离那条路),覆盖 PPT 和 Excel 两类。

## 验证一:OCR 是否"每进程只建一次"(提速核心)
1. 确认代码里已加日志:每次真正创建 OCR 实例打印 `OCR engine created pid=... count=N`。
2. 跑这一小批文件(建议在 VS Code 里跑 worker)。
3. 看日志里 `OCR engine created` 出现的次数:
   - **正确**:次数 ≈ 进程数(MAX_WORKERS,如 4),不随文件数量增长。
   - **错误**:文件越多、打印越多(说明还在每文件新建,没改到位)。

## 验证二:速度是否明显下降
- 对比改动前后处理同一批文件的单文件平均耗时;应明显下降,接近单进程 ingest(`python -m kb_poc ingest`)的水平。

## 验证三:配置是否真的生效
- 改一项配置(如 `KB_LOCAL_OCR_CPU_THREADS` 或 `enable_mkldnn`),重跑,确认 OCR 行为/日志能体现出变化;而不是像以前那样改了没反应。

## 验证四:只剩一条 OCR 路径
- 全局搜索代码,确认只有一个 OCR 创建入口在被真正调用;`ocr_provider.py::LocalPaddleProvider` 要么已删、要么已归并成同一实例(不再是独立的预热实例)。

## 验证五:该保住的东西没坏(回归)
逐项确认没有回退:
- 重文件仍走独立子进程,处理完能正常回收。
- 子进程解释器仍是 `sys.executable`(.venv312),没跑到系统 Python。
- 日文识别结果正常(抽查 1–2 个文件的解析文本)。
- 失败重试 / 崩溃计数 / 断点续跑 / 按文件哈希的增量幂等,仍照常工作。
- embedding 限速与批量没被破坏(没有重新出现大量 429)。

## 判定
以上五项全部通过 = 改动成功。任一项异常,先看日志定位是哪一步,必要时用备份的 `ingest.db` 回退。
