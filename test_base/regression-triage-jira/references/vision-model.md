# 模型识图（可选）

> 目前没有启用。启用前要重新实现截图打码（发到外部模型的截图必须先涂黑个人信息），下面的“页面上复制识图指令”也需要重新做。

Windows 文字识别只能读出截图上的文字。勾选状态、按钮是否灰色、页面是否空白、截图里的图形这些，要靠视觉模型来看。本文说明怎么接入模型、怎么问、怎么使用结果。接口和指令写在 `config/vision.yaml` 里（从 `config/vision.example.yaml` 复制）。

## 1. 原则

1. **模型只描述看到了什么，不做分类。** 分类仍由现有规则完成，模型的回答只是一条证据，标为“模型看图描述”。
2. **只发需要看的截图。** 默认只发“待复核”和“需人工判断”的用例，不全量发送。
3. **先打码再发送。** 证件号、手机号、邮箱、卡号、人名清单先涂黑；没有文字识别结果的截图不能自动打码，所以不发送。
4. **结果必须人确认。** 依据模型得出的结论一律是“待复核”，人点“采用”后才算确认；日志已经能确定的结论不会被模型改变。
5. **密钥不进页面、不进文件。** 只放在电脑的环境变量里，或者由公司网关统一管理。

## 2. 三种使用方式（在 `vision.mode` 里选）

| 方式 | 适合 | 怎么做 |
|---|---|---|
| `off` 不用模型 | 默认 | 只用 Windows 文字识别和人工“截图观察” |
| `manual` 手动 | 没有接口权限，但公司批准了某个对话工具 | 页面上复制这条用例的“识图指令”，在对话工具里粘贴截图（已打码）和指令，把模型的 JSON 回答粘贴回页面 |
| `api` 接口 | 拿到公司的模型接口和密钥 | 本机脚本按 `vision.yaml` 批量调用，生成结果文件，再在页面导入 |

三种方式产生的结果格式相同（见第 5 节），页面上的显示和核对方式也相同。

## 3. 接口怎么调用（`mode: api`）

用的是常见的“对话补全”接口，图片以 base64 放在消息里。

**Azure OpenAI**

```
POST {endpoint}/openai/deployments/{deployment}/chat/completions?api-version={api_version}
请求头：api-key: <环境变量 VISION_API_KEY 的值>
```

**公司网关或兼容 OpenAI 格式的接口**

```
POST {endpoint}/chat/completions
请求头：Authorization: Bearer <环境变量 VISION_API_KEY 的值>
```

**请求内容（两种接口相同）**

```json
{
  "model": "<model，Azure 可省略>",
  "temperature": 0,
  "response_format": {"type": "json_object"},
  "messages": [
    {"role": "system", "content": "<system_prompt>"},
    {"role": "user", "content": [
      {"type": "text", "text": "<user_prompt，已填入用例编号、失败步骤、报错>"},
      {"type": "image_url", "image_url": {"url": "data:image/png;base64,<打码后的截图>"}}
    ]}
  ]
}
```

- 地址、版本号、模型名以公司提供的为准。部分网关不支持 `response_format`，去掉即可，指令里已经要求只用 JSON 回答。
- 超时、限流（返回 429）时等待后重试 1 次；仍失败就记为“识图失败”，不影响其他截图。

## 4. 指令

写在 `vision.yaml` 的 `system_prompt` 和 `user_prompt` 里。要点：

- 带上日志里的**失败步骤和报错原文**，模型才知道该看哪里。
- 要求**逐字照抄**，看不清写 `unknown`，**不推测原因**。
- 固定的 JSON 格式，便于程序核对。
- 改指令后把 `prompt_version` 加 1，结果里会记录用的是哪一版，方便比较效果。

## 5. 结果文件

接口方式生成 `模型识图结果.vision.json`，和报告放在一起；手动方式由页面直接保存。

```json
{
  "tool": "ta-vision", "v": 1, "created": "2026-11-20 10:30:00",
  "model": "<模型名或部署名>", "prompt_version": 1,
  "images": [
    {
      "sha256": "<截图指纹，和文字识别结果用同一种，页面靠它对应截图>",
      "case_id": "test_27_TC_LAS_PaidToDateAdvance_01",
      "answer": { "screen": "popup", "popup_text": "Contract is currently used by other user", "...": "..." },
      "error": null
    }
  ]
}
```

## 6. 页面怎么使用结果（核对规则）

1. **按指纹对应截图**，和文字识别结果一样，与文件名无关。
2. **弹窗文字要能核对上**：`popup_text` 和 `other_messages` 必须能在这张图的文字识别结果里找到（允许 l/I、0/O 等常见识别差异）。找不到的标为“模型给出的文字未能核对”，不参与判断。
3. **unknown 不参与判断。** `confidence: low` 的整条只做提示。
4. **对应到“截图观察”**：`screen` 对应现有的观察选项（normal → 正常，popup → 弹窗，blank → 空白，locked_or_black → 锁屏/黑屏，other_window → 其他窗口）。`target_control.enabled = no` 对应“按钮灰色/不可用”，然后交给现有规则重新分析。
5. **标出位置**：在截图上用框标出 `region`，人一眼就能核对模型说的对不对。
6. **结论标“待复核”**：显示为“依据模型看图，待确认”，人点“采用”后才算确认。

## 7. 准不准：上线前先评估

挑 30–50 张已经人工判断过的截图，人工先记下正确答案（屏幕状态、弹窗原文、勾选或按钮状态、最终分类）。然后用模型跑一遍，分别统计：

| 项目 | 达标线（建议） |
|---|---|
| 弹窗原文逐字正确 | ≥ 95% |
| 屏幕状态正确 | ≥ 90% |
| 勾选 / 按钮状态正确 | ≥ 90%，不达标就这一项继续交给人 |
| 依据模型得出的分类与人工一致 | ≥ 90% |

把评估结果和用的 `prompt_version` 一起记下来。换模型或改指令后重新评估一次。
