# 证据的强弱与截图判读

本文件回答三个问题：
1. 截图怎么识别？用什么工具？准不准？
2. 报错和截图说法不一致时，信哪个？
3. 怎样让证据本身更可靠（需要改测试框架的地方）？

---

## 1. 证据等级

| 等级 | 证据 | 为什么可靠 / 不可靠 | 用法 |
|---|---|---|---|
| A | 异常类型 + 项目代码里的出错位置 | 程序自动产生，不需要解读 | 判断“在哪一步、哪种操作失败” |
| A | 控件/窗口清单（窗口标题、类名、是否可见、是否可用、勾选状态） | 直接读自操作系统，精确到每个控件 | 判断“当时屏幕上有什么” |
| A | 数据库/交易日志核查结果（人工或批准的只读脚本） | 直接查询事实 | 判断数据问题 vs 系统问题 |
| B | 被测系统给出的原话：弹窗文字、`Validation Error`、Life/Asia Message | 系统自己说明了原因；但要读全，空文字无效 | 判断原因的方向 |
| B | 同批次其他用例的记录（断崖、通过用例里的同样报错、同功能对比） | 多个独立记录互相印证 | 提升或降低结论强度 |
| C | 截图 | 现场画面，但需要解读；可能不是失败那一刻；小细节容易看错 | 补充 A/B 没有的信息：前台是什么窗口、有没有意外的对话框 |
| D | 包装后的笼统报错：`job cannot submit successfully`、`xxx Error!`、`SystemExit: 0` | 只说明“失败了” | 不作为分类依据 |

**规则：**
- 结论以最高等级的证据为准；低等级证据只能补充，不能推翻高等级证据。
- 截图是 C 级：截图里看到的东西可以**提出**新的可能（例如“前台有一个未知对话框”），但要用 A/B 级证据确认后才能 `confirmed`。
- 两条同等级证据矛盾 → `NEEDS_HUMAN`（`conflicting_evidence`）。

## 2. 截图怎么识别

### 2.1 三类工具对比

| 方式 | 擅长 | 不擅长 | 适合用在 |
|---|---|---|---|
| **多模态大模型看图**（公司批准的 Azure OpenAI 等） | 理解整体：前台是哪个窗口、有没有对话框、对话框大意、页面是否异常 | 小目标（勾选框、单选框、小图标）、高分辨率整屏截图里的细节、密集表格里的具体数字；可能“看到”不存在的内容 | 给出“看什么、哪里可疑”的方向 |
| **OCR**（PaddleOCR、Windows 自带 OCR、Azure AI Vision Read） | 把截图里的文字准确读出来，带位置和置信度 | 不理解含义；勾选框、灰色按钮这类非文字状态读不出来 | 读对话框文字、窗口标题、表格里的状态和编号 |
| **直接读控件状态**（pywinauto 读窗口和控件树） | 精确：每个窗口的标题、类名，每个控件是否可见/可用/已勾选，对话框里的全部文字 | 需要在失败那一刻由测试框架采集（改造框架） | **最准确，应作为主要证据** |

### 2.2 大模型看截图准不准：公开评测的结论

- ScreenSpot-Pro 是在 23 个专业桌面软件（含 Windows 程序）的**高分辨率整屏截图**上评测模型定位界面元素的基准。论文报告：已有模型表现很差，最好的模型准确率只有 **18.9%**；用分区域逐步放大的方法后提升到 **48.1%**。
- 同一评测中，目标元素平均只占截图面积的 **0.07%**；带文字的目标比纯图标容易得多（例如 OS-Atlas-7B 平均：文字 28.1%，图标 4.0%）。
- 这个评测测的是“找到某个元素在哪里”，不是“读出文字”，但它说明了一个对我们很重要的事实：**在整屏、高分辨率、元素很小的截图上，模型对小图标、小控件的判断不可靠**。LAS 这种传统 Windows 程序界面密集、控件小，正是这种情况。

来源：Li et al., *ScreenSpot-Pro: GUI Grounding for Professional High-Resolution Computer Use*（arXiv 2504.07981）。

### 2.3 因此的做法

1. **对话框文字、窗口标题**：优先用控件读取的文字（A 级）；没有时用 OCR；最后才让模型读。
2. **勾选框、单选框、按钮是否可用**：不要让模型从截图判断。写“截图中无法确认”，并用控件状态核对。
3. **让模型看截图时，先裁剪再看**：只给它对话框或相关区域，不要整屏。公开评测也显示缩小范围能明显提高准确率。
4. **模型只描述，不下结论**：输出“看到了什么、在哪里”，由规则和人来分类。
5. **“图中图”**（主窗口里又开了子窗口、对话框）：先确定**前台窗口**是哪个（有焦点的标题栏、最上层的对话框），只有前台窗口的内容与当前操作相关；后面的窗口只能说明“还开着”。

## 3. 截图有效性检查（先做这一步）

| 检查 | 怎么查 | 不通过时 |
|---|---|---|
| 截图是否真的拍成功了 | 日志里截图函数有没有报 `screen grab failed` | 这个用例**没有**有效截图；报告里显示的图片不能作为证据 |
| 时间是否对得上 | 截图里任务栏时钟、系统日期 vs 用例执行时间 | 可能是其他用例的截图 |
| 窗口是否对得上 | 截图前台窗口标题 vs 用例要操作的功能 | 用例停在别的界面，或截图属于别的用例 |
| 数据是否对得上 | 截图里的保单号 vs 用例测试数据 | 截图属于别的用例 |
| 是否黑屏/锁屏/空白 | 画面内容 | 截图时桌面不可用 |
| 是否与上一个用例的截图完全相同 | 比较图片 | 可能没刷新，或拍的是旧画面 |
| 截图时机 | 截图是在弹窗处理**之后**拍的 | 截图里没有弹窗 ≠ 当时没有弹窗 |

> 实例：No.25～No.51 的截图函数都报了 `screen grab failed`，这 27 个用例没有任何有效截图；报告里如果显示了图片，不能用来判断这些用例。

## 4. 截图与日志对照

| 情况 | 处理 |
|---|---|
| 一致 | 例如日志 `trans_status:COMPLETED`，截图里交易日志表格 Trans Status 也是 COMPLETED → 互相印证，写进依据 |
| 截图补充了日志没有的信息 | 例如日志只有 `ElementNotEnabled`，截图显示表单上有一行红字提示 → 把提示文字作为新线索，用 OCR 或控件读取确认后再定 |
| 矛盾 | 先做有效性检查；有效且仍矛盾 → `NEEDS_HUMAN`（`conflicting_evidence`），写明“E2 说 …，E4 显示 …” |

## 5. 让证据更可靠：建议测试框架补充的采集

现在每个失败用例只有日志和一张截图，很多结论只能停在 `suspected`。在失败处理函数里（**弹窗处理之前**）多采集以下内容，大部分 `suspected` 可以变成 `confirmed`。参考实现：`scripts/desktop_evidence.py`。

| 采集项 | 解决的问题 |
|---|---|
| 当前时间、执行机名、桌面是否可交互 | 截图时间核对；直接判断桌面问题 |
| 所有顶层窗口：标题、类名、是否可见、是否可用、所属进程 | 前台是什么、有没有残留窗口、有没有意外对话框 |
| 所有对话框（类名 `#32770`）里的全部文字 | 弹窗文字为空、读不全的问题 |
| 前台窗口内控件清单：类型、文字、是否可见、是否可用、勾选状态 | 按钮为什么灰、勾选框是否勾上——不再靠截图猜 |
| 脚本当时要找的控件/窗口名称、要输入的值、要设置的日期 | `ElementNotFound`、`Failed to set time` 一类问题直接定位 |
| 下拉框的全部选项 | `'Reversal' is not in list` 一类问题直接定位 |
| 截图（与上面同一时刻） | 现场画面 |

**两项框架改进可以避免大面积失败：**
1. **用例开始前检查桌面是否可交互**（例如尝试移动一次鼠标，失败即视为桌面不可用）。不可用时直接停止本次运行并报警，而不是让后面几十个用例逐个失败。本次 No.26 起的 26 个用例就是这种情况。
2. **失败后清理窗口**：每个用例结束时关闭它打开的窗口、释放保单。本次 No.31 的残留窗口、No.5 的多个同名控件、No.23 的保单被占用，都可能与此有关。
