2. 报错信息不一定对得上原因，证据编号怎么写

你说得对。弹窗类问题的报错往往只是“等待超时”，这只是现象，不是原因。证据不只有报错信息，还包括截图、弹窗文字、整屏截图、重跑结果、数据核查记录，每条都有编号。引用时要分清“现象证据”和“原因证据”，写法像这样：

分类：弹窗干扰
原因证据：E3（弹框文字 “System Notice: SIT2 maintenance tonight”）、E2（截图中该弹框遮挡了 Submit 按钮）
现象证据：E1（TimeoutException，等待 #nextStep 可点击超时。这只说明超时了，不能单独说明原因）

SKILL.md 现在写的是“引用证据原文：异常类型、报错行……”，没有区分这两种，需要改。

3. 规则不够灵活、不全面，不一定是真实根因

这个担心是对的，规则本来也不是用来找根因的。它们做的是初步分类：判断这个失败该谁处理、要不要建单。所以规则写得很保守，只在证据非常明确时才给结论（confirmed），拿不准的都标成“疑似”或“需人工判断”。

真实根因要靠人结合 AI 去看证据，规则覆盖不到的情况会进入“需人工判断”。规则靠两样东西逐步完善：

- 审核人每次改了分类，系统都会记下来（corrections.jsonl）；

- 用历史数据跑评测，算出准确率。

我建议把文档里的“根因”改成“初步分类”，避免让人误以为脚本给的就是最终结论。上线初期，“需人工判断”占比偏高是正常的。

4. 重跑前要列出依据，等用户确认

同意，这一处需要改。现在的流程是把所有失败用例都直接重跑，这不对。应该改成：

1. 先不带重跑结果做一次预分类，生成“重跑计划”，每个用例写明“建议重跑 / 不建议重跑”和理由；

2. 用户确认后再重跑，可以增删用例；

3. 重跑完再做最终分类。

默认不建议重跑的情况：

- 有业务报错的：重跑解决不了，还会消耗测试数据；

- 会产生真实业务数据的：比如支付、出单；

- 疑似整体环境故障的：应该等环境恢复后再跑；

- 定位表达式本身写错的：重跑肯定还会失败。

5. guess_error_type 只看报错信息不准确

这个函数只做一件事：从报错文字里提取出异常的类名，比如 TimeoutException。它只是解析文字，不做判断。

分类时用的是几项证据的组合：异常类型、弹窗证据、页面业务报错、重跑结果、数据核查。异常类型只是其中一项，单靠它，规则只会给出“疑似”（比如 SCR1 脚本问题就只能是 suspected）。

但你指出的缺口是真的：怎么看截图，现在没有写清楚，AI 复核截图时缺少统一标准。需要补一份截图判读指南（references/screenshot-guide.md），列出看什么、看到什么说明什么：

6. 是否要写清楚怎么识别页面、弹窗、截图

load_results.py 里那段代码读取的是插件在失败那一刻自动抓下来的信息，比如弹框文字、网址，没有任何主观判断。“怎么判断”的规则分散在三个地方：

- 弹窗识别：popup-catalog.md，加上 popup_evidence.py 里查找弹框的选择器；

- 分类依据：taxonomy.md；

- 截图判读：目前缺失，就是第 5 条要补的那份指南。

所以答案是：要写，而且要单独成一份文件，不应该写在代码注释里。

7. 递归能定位到具体挂点吗？核心问题怎么判断？

能定位到挂点，但挂点不等于根因。

Allure 的步骤是嵌套的，大步骤里套着小步骤。递归会找到最深一层失败的那一步，也就是“在哪一步断的”。但问题可能出在更早的地方。比如在“点击 Submit”这一步失败了，原因却可能是前面输错了 agent code，或者前面就弹过框。

这个挂点（failed_step）只用在两处：合并分组时作为参考维度之一，以及在 Jira 描述里写“失败步骤”。核心问题由分类规则和证据决定，不由挂点决定。

另外有个前提：测试脚本里要用 allure.step 标记了步骤，否则这一项是空的。

8. 为什么必须是目录？附件这样处理有没有问题？

- 必须是目录：Allure 的输出本来就是一个文件夹（allure-results/），里面每个用例一个 JSON，外加一堆附件。JUnit 格式则文件和目录都能读。

- 附件的处理方式确实太粗糙，需要改。现在凡是图片都当失败截图、凡是名字带 evidence 的 JSON 都当弹窗证据，有两个风险：

  - 测试过程中的其他图片（比如对比用的期望图、过程截图）会被误当成失败截图；

  - 其他工具生成的同名 JSON 可能被误读。

改法是只认插件自己写入的固定名称（failure screenshot、fullscreen screenshot、evidence），名称可以在配置里修改；其他附件单独列为“其他附件”，不参与判断。

9. 那段代码里的“环境”是什么

这里的“环境”不是要你去搭的东西，而是这次测试是在什么条件下跑的，最后会填进 Jira 的 Environment 字段：

字段 意思 例子

env_name 被测系统部署在哪套测试环境 NBS-SIT2、UAT

browser / browser_version 跑测试用的浏览器和版本 Edge 142

数据来源有三处：

- Allure 结果目录里的 environment.properties 文件，由测试框架写入；

- 弹窗插件从浏览器读取的信息；

- 测试平台本身显示的信息。

二、rerun_failed.py

怎么运行、怎么连到平台

这是现在最大的未知数。脚本目前假设测试是在本机用 pytest 跑的。如果测试是在 BLN 平台或 Jenkins 上跑的，重跑就得通过那个平台来触发。需要做成可以切换的三种方式：

- local：本机命令行执行（现在的写法）；

- platform：调用平台的接口，或者触发 Jenkins 带参数的任务，传入要重跑的用例列表；

- manual：在平台上手动点“重跑失败用例”，再把重跑结果导入进来。

最省事的是 manual，不需要任何接口权限。需要问同事B：测试是在哪里跑的，平台有没有“重跑失败用例”的按钮或接口。

先解析还是先重跑

其实已经是先解析的：第 1 步 load_results 解析了第一次的结果，生成 failures.json，重跑读的就是它。你发现的真正问题是：解析完之后没有先判断哪些该重跑，而是全部都重跑。这就是第 4 条要改的地方：先预分类，再生成重跑计划，用户确认后才重跑。

为什么默认串行，串行有没有问题

默认串行，是因为共用测试环境时并行重跑容易出问题：

- 争抢同一份测试数据：两个用例同时用同一个 agent 或同一张保单，互相影响；

- 同一个账号被挤下线：同一账号同时登录，先登录的会话被踢掉；

- 把环境压慢：并发一高，环境变慢，造成新的超时，干扰判断。

串行的问题是慢：40 个用例、每个 2 分钟，就要 80 分钟。折中办法：

- 不同测试账号、不同测试数据的用例可以并行，配置里的 parallel 可以调大；

- 如果平台自己支持并行重跑，交给平台去做；

- 先通过重跑计划减少要重跑的数量。

为什么用 shell 执行

你的怀疑有道理，这一处应该改。用 shell 执行时，用例名里如果有引号、& 之类的特殊字符，命令可能被拆错，存在注入风险。更稳妥的做法是在配置里把命令写成列表，逐项替换后直接执行，不经过 shell，Windows 和 Mac 都能兼容。

三、classify_rules.py：弹窗干扰不一定是这些报错

对，这是规则的一个漏洞。现在网页弹框的规则（POP2）只在“点击被挡住、找不到元素、等待超时”这几种异常下才会触发。实际上弹窗还可能导致：

- 断言失败（读到的是弹框上的文字）；

- 元素过期（StaleElementReferenceException）；

- 页面跳转到了别处；

- 甚至用例通过了，但流程不对。

还有一点要注意：失败时页面上有弹框，不代表就是弹框导致的失败，弹框也可能是失败之后才出现的。所以我建议这样改：

情况 分类

有直接证据证明弹窗挡住了操作（原生对话框异常；被遮挡的元素就是这个弹框） 弹窗干扰，confirmed

失败时页面上有干扰弹框，但异常类型对不上 弹窗干扰，疑似，需要看截图确认

弹框文字不在清单里 需人工判断（未知弹窗）
