# 一、首先理解：IT 行业为什么需要测试？

假设富卫保险正在开发一个新的保险业务系统。

客户可以通过系统：

- 查询保险产品。
- 提交投保申请。
- 上传身份证、健康告知等资料。
- 查询保单状态。
- 申请理赔。
- 查询理赔进度。

开发团队完成了系统开发，领导问：

这个系统可以上线了吗？

开发人员说：代码写好了，可以运行。

但这并不代表系统可以上线。

因为可能出现：

- 用户提交投保申请，系统没有生成保单。
- 客户上传身份证，系统识别错误。
- 用户已经缴费，系统却显示未缴费。
- 理赔金额计算错误。
- 修改了投保模块，结果原本正常的保单查询功能坏了。
- 100个人同时访问没有问题，但10000个人访问时系统崩溃。

这些问题都会造成业务损失、客户投诉，甚至合规风险。

所以，软件测试的核心目的就是：

在软件正式交付或上线之前，尽可能发现问题，验证系统是否满足业务要求，并确保修改不会破坏原有功能。

企业 IT 软件交付的基本闭环

业务需求

要开发什么功能？解决什么问题？

系统设计与开发

开发人员编写代码、配置系统

软件测试 QA

功能、接口、数据、性能、安全等验证

缺陷修复与回归测试

发现 Bug → 开发修复 → 重新验证

验收与上线

业务确认、QA 评估、发布审批

这是通用企业软件交付模型，实际项目可能存在并行测试、持续集成和多轮验收。

这里你需要先记住一个概念：

测试不是开发结束以后才开始的工作。

在成熟的软件研发团队中，测试往往从需求分析阶段就开始介入。

# 二、IT 行业主要有哪些测试类型？

先给你建立一个完整的知识地图。

测试类型很多，但不能把它们理解成完全平级的东西。

例如：

- 功能测试：测试系统功能是否正确。
- 自动化测试：测试执行方式的一种自动化手段。
- 回归测试：测试目的之一，检查修改是否造成旧功能异常。
- A/B 测试：通过不同版本的对照实验，验证哪种方案效果更好。

它们回答的问题不同，因此一个测试项目可能同时使用多种测试方式。

## 2.1 企业常见测试类型总览

| 测试类型       | 核心目的        | 主要解决的问题         |
| ---------- | ----------- | --------------- |
| 功能测试       | 验证功能是否符合需求  | 功能能不能正常使用？      |
| 自动化测试      | 自动执行测试任务    | 能不能减少人工重复操作？    |
| 回归测试       | 验证修改没有破坏旧功能 | 修改后原来的功能还正常吗？   |
| A/B 测试     | 比较不同方案的实际效果 | 哪个版本更好？         |
| 接口测试       | 验证系统接口交互    | 系统之间的数据传输正确吗？   |
| 性能测试       | 验证系统承载能力    | 系统能承受多少用户？      |
| 压力测试       | 寻找系统性能极限    | 系统什么时候会崩溃？      |
| 安全测试       | 发现安全漏洞      | 数据和系统安全吗？       |
| 兼容性测试      | 验证不同环境下的表现  | 不同浏览器、设备能正常运行吗？ |
| 集成测试       | 验证多个模块协作    | 不同系统连接后能正常工作吗？  |
| 单元测试       | 验证最小代码单元    | 某段代码的逻辑正确吗？     |
| UAT 用户验收测试 | 让业务用户验证系统   | 业务部门认可这个系统吗？    |
| 冒烟测试       | 快速检查核心功能    | 这次构建版本是否值得继续测试？ |
| 探索性测试      | 通过灵活操作寻找问题  | 有没有预料之外的异常？     |
| 数据测试       | 验证数据准确性和完整性 | 数据有没有丢失、错误或重复？  |

下面重点讲解，并且每一种都用保险公司的实际业务场景帮助你理解。

## 2.2 功能测试（Functional Testing）

最基础、最常见

它是什么？

检查软件的每一项功能，是否按照产品需求正常运行。

例如，富卫保险开发一个线上投保系统，客户填写资料后点击「提交投保」。

测试人员需要验证：

- 是否能够正常提交？
- 必填字段是否有校验？
- 身份证号码格式错误时，是否提示？
- 缺少健康告知信息时，是否阻止提交？
- 提交成功后，是否生成正确的申请编号？
- 重复点击提交，会不会产生两笔申请？

应用场景

几乎所有软件开发项目都需要功能测试：

- 保险投保系统。
- 保单管理系统。
- 理赔系统。
- 内部员工管理系统。
- Power Apps 业务应用。
- 企业知识库、审批系统。

怎么做？

假设需求是：

> 用户可以通过系统提交保险投保申请，必须填写姓名、身份证号码、联系方式和保险产品。

QA 会把这个需求拆成多个测试场景。

| 测试用例  | 操作        | 预期结果     |
| ----- | --------- | -------- |
| TC001 | 填写完整资料并提交 | 成功提交     |
| TC002 | 姓名为空      | 提示必填     |
| TC003 | 身份证格式错误   | 提示格式错误   |
| TC004 | 手机号码格式错误  | 提示格式错误   |
| TC005 | 未选择保险产品   | 阻止提交     |
| TC006 | 重复点击提交    | 不产生重复申请  |
| TC007 | 提交后刷新页面   | 申请记录仍然存在 |

这里有一个重要概念：

Test Case（测试用例）

测试用例不是简单地写「检查投保功能」，而是明确规定：

1. 测试什么功能？
2. 测试前需要什么条件？
3. 输入什么数据？
4. 执行什么操作？
5. 预期出现什么结果？
6. 实际结果是什么？
7. 最终通过还是失败？

这也是你以后开发测试智能体最需要掌握的基础，因为 AI 生成测试用例，本质上就是将业务需求转换成可执行、可验证的测试步骤。

## 2.3 自动化测试（Automation Testing）

与你当前工作最相关

它是什么？

通过代码、工具或者自动化平台，让计算机代替测试人员执行重复性的测试操作，并自动判断结果。

传统人工测试

| 多浏览器测试   | 自动检查兼容性    |
| API 接口测试 | 批量验证数据交互   |
| 移动端测试    | 自动操作 App   |

| JMeter       | 性能及压力测试             |

这里需要特别理解：

自动化测试不等于 AI 测试。

两者可以结合，但不是同一回事。

## 2.4 回归测试（Regression Testing）

保险系统非常重要

它是什么？

当开发人员修改了软件代码、修复了 Bug 或增加了新功能之后，重新测试原本已经正常的功能，确保它们没有因为这次修改而受到影响。

我用一个真实工作逻辑来解释。

假设富卫保险的投保系统原本有三个功能：

- A：客户投保。
- B：客户查询保单。
- C：客户申请理赔。

现在业务部门提出新需求：

增加一个新功能：投保时自动识别客户上传的身份证。

开发人员修改了投保模块，开发完成后测试人员发现：

- 身份证识别正常。
- 投保提交正常。
- 但是保单查询功能出现异常。
- 原本可以查询的保单，现在显示为空。

这就是典型的修改引发旧功能问题。

如果只测试新功能，就很可能漏掉这个问题。

因此需要进行回归测试。

回归测试的核心逻辑

原有系统

投保正常｜保单查询正常｜理赔正常

开发人员修改投保模块

新版本系统

增加身份证自动识别功能

重新测试新功能和受影响的旧功能

投保正常

新功能通过

保单查询异常

发现回归缺陷

回归测试什么时候使用？

- 系统增加新功能。
- 系统修改已有功能。
- 修复 Bug 之后。
- 数据库结构发生变化。
- API 接口发生变化。
- 系统版本升级。
- 正式上线之前。

回归测试怎么做？

通常需要：

1. 确认本次代码修改涉及哪些模块。
2. 分析哪些原有功能可能受到影响。
3. 从历史测试用例中筛选相关用例。
4. 执行回归测试。
5. 记录通过和失败的结果。
6. 对失败项创建缺陷。
7. 修复后再次执行测试。

这里有个重点：

不是每次回归测试都必须把所有历史用例全部重新执行。

企业通常会结合代码变更范围、业务影响、风险等级和历史缺陷，选择：

- 全量回归（Full Regression）。
- 定向回归（Targeted Regression）。
- 风险驱动回归（Risk-based Regression）。

这也是 AI 测试智能体可以发挥价值的地方：根据本次需求变更，分析影响范围，推荐应该执行哪些历史用例。

## 2.5 A/B 测试（A/B Testing）

业务效果验证

这个和上面的测试有明显区别。

它是什么？

将用户随机分配到两个或多个实验组，让不同组体验不同版本的产品，再通过数据指标判断哪种方案效果更好。

它的目的不是单纯检查系统有没有 Bug，而是验证：

哪种产品设计、业务策略或者用户体验更好？

举个保险业务案例。

富卫保险想优化线上保险产品购买页面。

目前有两个设计方案：

A 版本

[Simplifying Insurance Purchasing: HDFC life insurance redesigned case study | by Navedahmed | Medium](https://images.openai.com/static-rsc-4/p39aX2nun7N7jDEpuA-_pyX7lzxaw5olyaikYkpR9w1fEjDBV9WXvPEcZGDSMyEYByGDEpC2J4WcjxZSvqRKK2dFgO9SvZon7Y-ifUy4860G3TlUS-BWmkgWcVkz_OT3hEZP-vNLBywRJIKJIj5jEnNwb8JNZpJhEpdNX2Bjy5Q?purpose=inline)

传统投保页面

填写较多信息，多个页面逐步完成。

B 版本

[Website Forms For Lead Generation | Tapform](https://images.openai.com/static-rsc-4/g3b5UqGUoHrHViQXVvA95c8_f_mSDfK3BO4JVycAAQVHQvS17t9yFCoPPSX8WNY0kI4Kgpd_BW955L3bm13X3qqWozLn0w05ScW4Ex5qli11fMWlYBA29GspnBrewncip8FHcDd62zVkwCsF0XuVUuHB3BLHL9OcynlnYbe1bDY?purpose=inline)

简化投保页面

优化信息布局，减少不必要的操作步骤。

公司希望知道哪个版本更好。

于是开展 A/B 测试：

- 10000名符合实验条件的用户。
- 5000人进入A版本。
- 5000人进入B版本。
- 两组用户使用不同页面。
- 统计投保完成率、页面退出率、平均操作时间等指标。

假设得到以下结果：

| 指标     | A版本  | B版本  |
| ------ | ---- | ---- |
| 进入页面人数 | 5000 | 5000 |
| 完成投保人数 | 500  | 650  |
| 投保完成率  | 10%  | 13%  |
| 退出率    | 30%  | 24%  |

B版本的投保完成率高出3个百分点，相对提升30%。

但是注意：这只是模拟数据，不代表B版本一定更好。还要检查样本量、统计显著性、实验分组是否公平，以及后续保单质量、客户投诉和合规指标。

A/B 测试的工作流

1. 提出业务假设

   例如：简化投保页面可以提高投保完成率。
2. 设计实验方案

   确定A/B版本、实验人群、流量分配和实验周期。
3. 开发不同版本

   开发人员完成两个版本的页面或功能。
4. 实验前质量测试

   验证两个版本的功能、数据采集、埋点、分流和权限。
5. 正式开展实验

   按照随机分组规则向用户提供不同版本。
6. 数据统计与分析

   比较转化率、退出率、操作时间等指标。
7. 业务决策

   判断是否扩大流量、继续实验或回退。

保险公司进行 A/B 测试需要特别注意：

保险产品涉及合同条款、保障责任、价格、适当性及监管要求。

不能为了提高转化率，就随意隐藏重要条款、弱化风险提示，或者给不同实验组提供不合规的保障内容。

所以 A/B 测试一般更适合用于页面布局、操作体验、信息呈现、合规范围内的服务流程优化等方面。

## 2.6 接口测试（API Testing）

它是什么？

验证不同系统之间的接口是否能够正确传递数据、处理请求和返回结果。

举例：

客户在保险 App 上提交投保申请，背后可能涉及多个系统：

- 前端 App。
- 投保业务系统。
- 客户信息系统。
- 身份验证系统。
- 支付系统。
- 保单管理系统。

这些系统之间需要通过 API 进行通信。

```
}
```

接口返回：

```
{
  "success": true,
  "applicationId": "APP00001",
  "status": "SUBMITTED"
}
```

接口测试需要检查：

- 请求参数是否正确。
- 返回数据是否正确。
- 数据类型是否正确。
- 缺少参数时如何处理。
- 重复请求会不会重复创建申请。
- 无权限用户是否能够调用接口。
- 接口异常时是否有合理错误提示。
- 数据是否真正写入数据库。

使用场景： 保险业务系统对接、支付、身份认证、保单管理、理赔系统、第三方服务等。

常见工具：Postman、REST Assured、Python Requests。

## 2.7 性能测试与压力测试（Performance / Load / Stress Testing）

这几个经常被放在一起，但含义有所不同。

| 类型    | 目的            | 保险业务案例        |
| ----- | ------------- | ------------- |
| 性能测试  | 综合评估系统响应能力    | 查询保单需要几秒？     |
| 负载测试  | 验证预期用户量下的表现   | 1000人同时查询保单   |
| 压力测试  | 超出预期负载，寻找系统极限 | 逐渐增加到10000人   |
| 稳定性测试 | 长时间运行是否稳定     | 连续运行24小时      |
| 峰值测试  | 突然出现流量高峰时的表现  | 营销活动开始时大量用户访问 |

例如保险公司开展线上营销活动。

平时系统每秒处理100个请求，活动期间可能突然达到每秒3000个请求。

测试人员需要验证：

- 页面响应是否变慢。
- API 是否超时。
- 数据库是否出现连接瓶颈。
- 是否发生请求丢失。
- 服务是否自动扩容。
- 流量恢复后系统能否正常工作。

常用工具：JMeter、LoadRunner、k6。

## 2.8 安全测试（Security Testing）

保险公司有大量客户个人信息和保单数据，因此安全测试特别重要。

例如：

- A客户能不能查询B客户的保单？
- 普通员工能不能访问管理员功能？
- 用户密码是否安全存储？
- API 是否存在越权访问？
- 身份证、手机号等信息是否被不当暴露？
- 文件上传是否存在恶意文件风险？
- 是否存在 SQL 注入、XSS 等漏洞？

常见测试方向：

| 方向   | 主要验证           |
| ---- | -------------- |
| 身份认证 | 登录机制是否可靠       |
| 权限控制 | 用户能否访问不属于自己的数据 |
| 数据保护 | 敏感信息是否得到保护     |
| 接口安全 | API 是否存在漏洞     |
| 漏洞扫描 | 是否存在已知安全风险     |
| 渗透测试 | 模拟攻击验证系统安全性    |

注意：渗透测试必须经过授权，在规定环境和范围内进行。

## 2.9 集成测试（Integration Testing）

它是什么？

检查多个独立模块或者系统组合起来之后，能否正确协同工作。

例如：

客户提交投保申请后：

1. 投保系统接收申请。
2. 身份认证系统验证客户身份。
3. 核保系统处理申请。
4. 支付系统处理缴费。
5. 保单系统生成保单。
6. 通知系统发送成功消息。

每个模块单独测试都通过，并不意味着组合后一定正常。

例如，支付系统显示成功，但是没有把结果正确传递给保单系统，最终客户付款了却没有生成保单。

这就是集成测试需要发现的问题。

## 2.10 单元测试、系统测试、UAT、冒烟测试

这四种也非常重要。

| 类型                  | 解释              | 主要执行者      |
| ------------------- | --------------- | ---------- |
| 单元测试 Unit Testing   | 对单个函数、方法、组件进行测试 | 开发人员       |
| 系统测试 System Testing | 对完整系统进行端到端验证    | QA         |
| UAT 用户验收测试          | 验证是否满足实际业务需求    | 业务用户、BA、QA |
| 冒烟测试 Smoke Testing  | 快速检查核心功能是否可用    | QA、开发人员    |

以保险投保系统为例：

- 单元测试：验证保费计算函数是否正确。
- 集成测试：验证投保系统能否正确调用支付系统。
- 系统测试：完整走一遍投保流程。
- UAT：业务部门确认投保流程是否符合实际业务要求。
- 冒烟测试：新版本部署后，快速检查登录、投保、保单查询等核心功能。

这里还有一个非常容易混淆的概念：

SIT 和 UAT 不是同一回事。

- SIT（System Integration Testing）：主要验证系统、模块、接口之间的集成是否正常。
- UAT（User Acceptance Testing）：主要由业务方验证系统是否符合业务需求、能否接受交付。

# 三、这些测试在企业里是如何配合工作的？

前面讲的是单项测试，现在要把它们放进真实的 IT 项目里。

因为实际工作中，并不是开发人员说做回归测试，QA 就只做回归测试。

企业会根据项目所处的阶段，安排不同的测试活动。

## 3.1 完整的软件测试工作流

以富卫保险开发一个新的线上理赔系统为例。

## 保险系统完整测试生命周期

1. 需求阶段（Requirement Analysis）

   BA / Product / QA

   业务部门提出需求：客户可以在线申请医疗理赔。

   QA 参与需求评审，理解业务规则，识别边界条件和潜在风险。

   产出：需求文档、业务规则、验收标准、风险清单。
2. 测试计划阶段（Test Planning）

   QA / Test Lead

   确定测试范围、测试类型、测试环境、测试人员、时间计划。

   产出：Test Plan、测试策略、测试资源计划。
3. 测试设计阶段（Test Design）

   QA / Test Analyst

   根据需求设计测试场景和测试用例。

   例如正常理赔、材料缺失、超出理赔期限、重复申请、金额异常等。

   产出：Test Scenario、Test Case、Test Data。
4. 开发与测试准备阶段

   Developer / QA

   开发人员完成系统功能，QA 准备测试账号、数据、环境和自动化脚本。

   产出：测试版本、测试环境、自动化脚本。
5. 测试执行阶段（Test Execution）

   QA

   先进行冒烟测试，再开展功能、接口、集成、自动化等测试。

   根据项目需要开展性能、安全和兼容性测试。

   产出：测试执行记录、Pass / Fail 结果。
6. 缺陷管理阶段（Defect Management）

   QA / Developer / BA

   QA 发现问题，提交 Bug，开发人员定位并修复，QA 重新验证。

   产出：Bug Report、修复记录、缺陷状态。
7. 回归测试阶段（Regression Testing）

   QA / Automation Engineer

   验证新功能，同时检查原有理赔、保单查询、支付等受影响功能。

   产出：回归测试报告。
8. UAT 与上线验收（Release Readiness）

   Business / QA / IT

   业务部门验收，QA 汇总测试质量、遗留缺陷和风险，相关负责人决定是否发布。

   产出：UAT Sign-off、测试总结、上线建议。
9. 生产验证与持续监控（Production Monitoring）

   IT / QA / Operations

   上线后检查关键业务流程、系统日志、错误率和异常数据。

   产出：生产验证记录、问题跟踪和优化任务。

这里有一个实际工作中很重要的事情：

测试并不是发现 Bug 就结束了，而是要跟踪到问题真正解决，并完成验证。

## 3.2 每个环节具体由谁负责？

| 角色                  | 工作内容               |
| ------------------- | ------------------ |
| BA（业务分析师）           | 收集需求、梳理业务规则、确认业务逻辑 |
| PM（项目经理）            | 负责项目计划、进度、资源协调     |
| Developer（开发）       | 编写代码、修复 Bug        |
| QA（测试工程师）           | 分析需求、设计用例、执行测试     |
| Automation Engineer | 搭建自动化框架、编写测试脚本     |
| Test Lead           | 制定测试策略、管理测试进度和质量   |
| Business User       | 进行 UAT、确认业务结果      |
| DevOps Engineer     | 管理构建、部署、CI/CD 和环境  |
| Security Engineer   | 安全评估、漏洞检测          |

你可以这样理解：

- BA 负责告诉团队业务要什么。
- 开发负责把业务需求做成软件。
- QA 负责验证软件是否符合要求。
- 自动化测试工程师负责让重复测试可以自动执行。
- 业务人员负责确认系统是否真正满足业务需要。

| Power Apps     | 表单字段、提交、校验、页面权限     |
| Power Automate | Flow 是否正常触发、审批是否正常  |
| SharePoint     | 文件是否成功保存、权限是否正确     |
| Dataverse      | 记录是否正确写入、状态是否同步     |
| Power BI       | 统计数据是否准确            |
| 集成测试           | 各模块之间是否正确传递数据       |
| 回归测试           | Flow 修改后，其他业务流程是否正常 |

注意，这里是一个典型的 Power Platform 企业应用架构示例，并非对富卫现有内部应用架构的确认。

# 五、如果在富卫实际做测试，一个项目的工作路径是什么？

现在把前面的内容转成一份可以拿去理解企业工作的流程。

假设 BA 给 QA 一份需求文档：

《保险理赔系统新增自动识别医疗发票功能》。

从接到需求到最终上线，QA 应该如何开展工作？

## 5.1 第一步：需求分析

QA 收到需求后，首先不能直接写测试用例。

应该先弄清楚：

- 为什么要开发这个功能？
- 用户是谁？
- 原有业务流程是什么？
- 新功能会改变哪些环节？
- 识别失败怎么办？
- 图片格式不支持怎么办？
- OCR 识别错误怎么办？
- 是否需要人工复核？
- 是否会影响现有理赔流程？

这里需要形成一份需求分析结果。

## 5.2 第二步：设计测试场景

根据需求，拆分不同场景。

| 场景编号  | 测试场景       | 优先级 |
| ----- | ---------- | --- |
| TS001 | 上传正常医疗发票   | 高   |
| TS002 | 上传模糊发票     | 高   |
| TS003 | 上传错误格式文件   | 中   |
| TS004 | 上传空白文件     | 中   |
| TS005 | OCR 识别金额错误 | 高   |
| TS006 | 上传重复发票     | 高   |
| TS007 | OCR 服务超时   | 高   |
| TS008 | 人工修正识别结果   | 高   |

## 5.3 第三步：编写测试用例

将每个场景继续拆成具体测试步骤。

例如：

| 字段              | 内容                  |
| --------------- | ------------------- |
| Case ID         | TC001               |
| Scenario        | 正常上传医疗发票            |
| Preconditions   | 用户已登录，拥有理赔申请权限      |
| Test Data       | 一张符合要求的测试发票         |
| Steps           | 选择文件 → 上传 → 等待识别    |
| Expected Result | 文件上传成功，OCR 正确识别相关字段 |
| Actual Result   | 实际执行后填写             |
| Status          | Pass / Fail         |

## 5.4 第四步：选择测试执行方式

不是所有测试用例都需要自动化。

需要判断：

| 测试任务     | 推荐方式     |
| -------- | -------- |
| 简单字段检查   | 自动化      |
| 高频重复操作   | 自动化      |
| API 参数校验 | 自动化      |
| 核心业务流程   | 自动化与人工结合 |
| 复杂业务判断   | 人工参与     |
| 新功能探索    | 人工探索性测试  |
| 用户体验评价   | 人工参与     |

例如 OCR 识别测试：

自动化可以检查识别结果是否符合预期；但对于复杂发票内容、业务合理性和异常场景，仍然需要人工审核。

## 5.5 第五步：执行测试和缺陷管理

执行测试之后，需要生成测试记录：

```
Test Execution Report

Project: Insurance Claims OCR

Total Cases: 100
Passed: 85
Failed: 10
Blocked: 5

Pass Rate: 85%

Critical Defects: 2
Major Defects: 3
Minor Defects: 5
```

以上是示意数据。

发现 Bug 后，提交缺陷：

```
Bug ID: BUG-001

Title:
OCR识别医疗发票金额错误

Environment:
UAT

Steps:
1. 登录测试系统
2. 上传测试发票
3. 等待OCR识别
4. 检查识别金额

Expected:
识别金额为 1200.00

Actual:
识别金额为 120.00

Severity:
Critical

Status:
Open
```

开发人员修复后，QA 重新执行：

- 缺陷验证（Retesting）。
- 相关功能回归测试（Regression Testing）。

两者不要混淆：

- Retesting：专门验证之前那个 Bug 是否已经修复。
- Regression Testing：检查修复过程中是否又影响了其他功能。

## 5.6 第六步：测试总结和上线建议

最后 QA 需要给出：

- 测试用例执行情况。
- 测试通过率。
- 缺陷数量和严重程度。
- 未解决问题。
- 回归测试结果。
- 上线风险。
- 是否满足验收标准。

最终交给项目负责人、QA 负责人及相关业务负责人进行上线决策。

# 六、最重要的部分：AI Agent 如何参与这些测试工作？

这部分才是你目前工作中最值得深入研究的内容。

你领导提出的目标是：

提质增效，提高测评效率，逐渐实现自动化。

这实际上不是单纯做一个聊天机器人，而是尝试让 AI 参与整个软件测试生命周期。

我建议把测试智能体设计成以下几个模块。

## 6.1 测试智能体的整体架构

## AI Test Automation Agent

输入层：需求和测试资料

BRD / PRD / User Story / API 文档 / 历史 Test Case

AI Agent 智能分析层

需求分析 Agent

识别业务规则

场景设计 Agent

生成测试场景

用例生成 Agent

生成 Test Case

用例审核 Agent

检查覆盖率

自动化开发 Agent

生成测试脚本

缺陷分析 Agent

分析失败原因

自动化执行层

Playwright / Selenium / Appium / API Testing / Pytest

测试结果与缺陷管理

Pass / Fail / Bug / Retest / Regression

测试报告与质量看板

测试覆盖率、通过率、缺陷趋势、质量风险

## 6.2 每个 Agent 具体负责什么？

| Agent             | 输入        | 输出            |
| ----------------- | --------- | ------------- |
| Requirement Agent | 需求文档      | 业务规则、需求分析     |
| Scenario Agent    | 需求分析结果    | 测试场景          |
| Test Case Agent   | 测试场景      | 测试用例          |
| Review Agent      | 测试用例      | 缺失项、重复项、覆盖率分析 |
| Automation Agent  | 测试用例、系统信息 | 自动化脚本         |
| Execution Agent   | 测试脚本      | 执行结果          |
| Defect Agent      | 失败记录、日志   | 缺陷描述、原因分析     |
| Report Agent      | 全部测试结果    | 测试报告          |

注意，Agent 不一定要全部独立部署成八个智能体。可以根据实际复杂度，把多个职责合并。

## 6.3 哪些测试工作可以交给 AI？

| 测试任务     | AI 自动化潜力 | 人工是否需要参与  |
| -------- | -------- | --------- |
| 需求文档分析   | 高        | 需要确认业务规则  |
| 测试场景生成   | 高        | 需要审核      |
| 测试用例生成   | 高        | 需要审核      |
| 测试用例去重   | 高        | 抽样检查      |
| 测试覆盖率分析  | 高        | 确认风险范围    |
| 自动化脚本生成  | 较高       | 需要代码审核    |
| 自动化执行    | 高        | 需要处理异常    |
| Bug 描述生成 | 高        | QA 确认     |
| Bug 根因分析 | 中高       | 开发人员最终判断  |
| 回归用例推荐   | 较高       | QA 确认执行范围 |
| A/B 实验设计 | 中高       | 业务及数据团队审核 |
| 上线决策     | 不建议全自动   | 必须由授权人员负责 |

这里有个很重要的设计原则：

AI 负责理解、分析、生成和辅助决策；确定性程序负责执行和校验；人负责业务判断、风险审批和最终决策。

尤其是保险行业，不能让 AI 自己决定某个理赔业务是否可以上线，或者擅自改变保险业务规则。

## 6.4 我建议你们的测试智能体分三个阶段落地

结合你目前已经规划过的测试智能体项目，我不建议一开始就追求全流程无人化。

第一阶段：AI 辅助测试设计

优先实施

先把人工测试准备工作提效

- 上传需求文档。
- 自动提取业务规则。
- 自动生成测试场景。
- 自动生成测试用例。
- 自动检查覆盖率。
- QA 人工审核并导出。

  核心价值：减少测试分析和用例编写时间。

第二阶段：自动化执行与回归测试

让 AI 从生成用例走向真正执行

- 自动生成部分 Playwright / API 测试脚本。
- 对接自动化测试框架。
- 自动执行测试。
- 解析 Pass / Fail。
- 根据需求变更推荐回归用例。
- 失败后生成缺陷报告。

  核心价值：减少重复测试执行和结果整理时间。

第三阶段：智能化测试闭环

逐渐形成企业级测试自动化体系

- 对接 Azure DevOps 等研发平台。
- 监听需求和代码变更。
- 自动分析影响范围。
- 自动选择测试集。
- 触发 CI/CD 测试流水线。
- 分析历史缺陷和失败规律。
- 生成质量趋势报告。

  核心价值：从人工驱动测试逐渐走向持续、风险驱动的测试。

## 6.5 怎么衡量测试智能体是否真正提效？

不能仅仅看 Agent 能不能生成测试用例。

建议从以下指标衡量：

| 指标                        | 衡量内容              |
| ------------------------- | ----------------- |
| Test Case Generation Time | 生成测试用例所需时间        |
| Test Case Acceptance Rate | AI 生成用例被 QA 接受的比例 |
| Requirement Coverage      | 需求覆盖率             |
| Automation Coverage       | 可自动化用例的覆盖程度       |
| Automation Pass Rate      | 自动化执行通过率          |
| Defect Detection Rate     | 测试发现缺陷的能力         |
| Regression Execution Time | 回归测试耗时            |
| Script Maintenance Cost   | 自动化脚本维护成本         |
| False Positive Rate       | 自动化误报率            |

注意几个指标的定义需要团队统一。例如，自动化执行通过率不等于系统质量通过率，因为测试本身也可能存在脚本错误、环境故障和测试数据问题。
