# 富卫测试部门 AI 提效与自动化测试平台：企业级建设方案

如果我是富卫的 AI 应用工程师，我不会把这个项目做成一个“能生成测试用例、能回答问题、能分析日志”的聊天机器人。

我会把它定位成一个真正服务于测试部门的 AI Testing Engineering Platform（AI 测试工程平台）：

- 让 AI 接手重复性高、规则相对明确的工作；
- 让自动化框架接手可确定、可重复的执行工作；
- 让 AI 帮助测试人员分析复杂失败、定位 Bad Case、沉淀经验；
- 让测试人员把精力集中在业务判断、风险判断、测试策略和质量决策上。

核心目标不是“尽可能多地使用 Agent”，而是让测试活动变得更快、更准、更可追溯、更容易复用，而且能持续维护。

先明确一个重要边界：我能结合富卫公开岗位职责、保险业务测试特点、行业标准和你此前提到的 Power Platform / AI Engineering 技术环境来设计；但目前没有证据证明富卫内部已经使用了哪些具体 Skills、测试框架、缺陷系统或自动化平台。因此，下面会把内容分成：

- 行业已有依据：标准、官方技术文档和成熟工程实践；
- 富卫候选方案：结合已知工作方向提出的设计；
- 需要内部验证：必须通过测试、开发、BA 访谈和系统盘点确认的事项。

这三者不能混为一谈。企业项目最忌讳把“方案假设”写成“现状事实”。

## 一、先确定：我们到底要建设什么？

我建议建设一个统一入口、多个专业能力模块、一个自动化执行底座的系统。

## AI Testing Engineering Platform

测试工程智能平台 · 目标架构

统一工作入口

Power Apps / Teams / Web Workbench

④ 测试资产与知识

历史用例、业务规则、缺陷库、脚本库、执行记录、经验沉淀

统一编排与治理层

QA 审核、业务确认、开发确认、发布审批

这个架构最重要的不是四个模块，而是四种职责必须分清：

| 技术                | 应该承担什么工作               |
| ----------------- | ---------------------- |
| Skill             | 封装一项可复用的专业工作方法         |
| Agent             | 理解任务、选择能力、处理不确定性、形成判断  |
| Workflow          | 控制流程、顺序、状态、重试、审批和异常    |
| Tool / API / Code | 访问系统、读写数据、运行脚本、执行确定性校验 |

不要把所有事情都做成 Agent。 例如，测试脚本是否执行成功，应当由测试框架根据断言结果决定；AI 可以解释失败原因，但不能仅凭语言判断就把失败改成通过。

## 二、Skill、Agent、Workflow 到底怎么设计？先把概念讲透

你提到目前可能已经有一些 Skill，但具体有哪些、怎么使用还不清楚。这是一个非常关键的切入点。

我建议不要先急着开发十几个 Agent，而是先做一份 Testing Capability Inventory（测试能力盘点表），把测试部门日常工作拆成可复用能力，再决定哪些做成 Skill、哪些做成 Agent、哪些必须写成代码。

### 1. Skill：不是一个小 Agent，而是一套可复用的专业工作规范

可以把 Skill 理解为：把一个测试工程师完成某项工作的知识、判断规则、步骤、模板和工具使用方法封装起来，让 AI 在需要时按照这套方法执行。

例如，测试部门经常需要根据 User Story 编写测试用例。

一个 `test-case-design` Skill 不应该只写一句：

> 根据需求生成测试用例。

它应该包含：

- 测试设计方法：等价类、边界值、决策表、状态迁移、错误推测；
- 业务规则识别方法；
- 测试用例字段和格式规范；
- 正向、反向、异常、权限、接口、数据一致性等覆盖要求；
- 历史用例检索方法；
- 输出 JSON Schema；
- 质量检查规则；
- 必要时调用的脚本和 API；
- 不能确定时必须提出澄清问题的规则。

这样它才是可复用、可维护、可测试的工程资产。

目前存在 Agent Skills 这样的开放格式，通常以 `SKILL.md` 为核心，并可附带脚本、参考资料和模板。它有利于跨工具复用，但不能把它误认为 ISTQB、ISO 等测试行业标准，也不能假设所有 Agent 平台都原生兼容。

### 2. 我会先规划这 12 个 Testing Skills

下面是我建议的第一版能力目录，不代表富卫已经存在这些 Skill。

| Skill 名称                        | 主要用途                | 输入                | 输出           |
| ------------------------------- | ------------------- | ----------------- | ------------ |
| `requirement-analysis`          | 解析需求、识别遗漏和歧义        | User Story、需求文档   | 结构化需求、待确认问题  |
| `business-rule-extraction`      | 提取业务规则和约束           | 需求、业务文档           | 规则清单、决策表     |
| `risk-based-testing`            | 识别高风险功能和测试优先级       | 需求、变更记录           | 风险清单、优先级     |
| `test-scenario-design`          | 设计测试场景              | 需求、业务规则           | 场景矩阵         |
| `test-case-design`              | 生成详细测试用例            | 场景、历史用例           | 标准化测试用例      |
| `test-case-review`              | 检查用例质量与覆盖率          | 用例、需求             | 缺失项、重复项、修改建议 |
| `test-data-design`              | 设计和准备测试数据           | 用例、数据规则           | 测试数据规格       |
| `automation-candidate-analysis` | 判断用例是否适合自动化         | 用例、执行频率、稳定性       | 自动化候选及理由     |
| `automation-script-generation`  | 生成自动化脚本             | 已审核用例、页面/API 规范   | 脚本、断言、运行配置   |
| `badcase-triage`                | 对失败进行初步分类           | 执行结果、错误信息         | 失败类型、证据      |
| `root-cause-analysis`           | 关联日志、接口、历史问题，提出根因假设 | 失败上下文、日志、Trace ID | 根因候选、证据链     |
| `regression-impact-analysis`    | 根据需求或代码变化推荐回归范围     | 变更记录、依赖关系、历史用例    | 回归测试集、风险说明   |

这 12 个不是 12 个独立 Agent。它们更像 12 项可被不同工作流调用的专业能力。

例如：

- `test-case-design` 可以被测试用例生成 Agent 调用；
- `test-case-review` 可以在用例生成后自动调用；
- `badcase-triage` 和 `root-cause-analysis` 可以由 Bad Case 分析 Agent 按阶段调用；
- `automation-script-generation` 可以由自动化工程 Agent 调用，但不能直接拿未经审核的用例就去执行生产操作。

每个 Skill 至少要具备六项工程属性：

1. 职责边界：什么任务适用，什么任务不适用。
2. 输入契约：需要哪些字段、文件和上下文。
3. 执行方法：采用哪些测试方法、判断规则和步骤。
4. 输出契约：固定结构，不能随意输出一篇自然语言长文。
5. 验证机制：如何判断输出合格。
6. 版本与责任人：谁维护、何时更新、如何回滚。

举个例子，`test-case-design` 的输出不能只是：

> 测试保单受益人修改功能，确保修改成功。

它必须给出可以落地执行的用例，例如：

```
{
  "case_id": "TC-BEN-001",
  "requirement_id": "REQ-BEN-001",
  "scenario": "修改有效保单的受益人比例",
  "preconditions": [
    "保单状态为有效",
    "当前用户具有受益人维护权限"
  ],
  "test_data": {
    "beneficiary_count": 2,
    "percentages": [60, 40]
  },
  "steps": [
    "进入保单受益人维护页面",
    "将第一位受益人比例修改为60%",
    "将第二位受益人比例修改为40%",
    "提交修改"
  ],
  "expected_results": [
    "系统接受修改",
    "两位受益人比例总和为100%",
    "修改记录被正确保存"
  ],
  "test_type": "functional",
  "priority": "high",
  "automation_candidate": true,
  "requirement_trace": "REQ-BEN-001"
}
```

这里的 100% 是示例业务规则，正式落地时必须由富卫对应产品和业务规则确认，不能让 AI 自己决定。

### 4. Agent 应该怎么拆？

我不建议“每个 Skill 一个 Agent”。Agent 数量过多，会带来上下文传递、重复调用、成本、权限和调试问题。

我会优先设置四个业务 Agent：

A. Test Design Agent

优先建设

职责：从需求到经过审核的测试用例

调用：`requirement-analysis` → `business-rule-extraction` → `risk-based-testing` → `test-scenario-design` → `test-case-design` → `test-case-review`

交付：需求结构化结果、业务规则、风险、测试场景、测试用例、覆盖率报告。

B. Automation Engineering Agent

第二阶段

职责：把审核通过的测试用例转成可靠的自动化资产

调用：`automation-candidate-analysis` → `automation-script-generation` → 脚本静态检查 → 测试环境执行 → 结果回传。

交付：脚本、断言、执行记录、失败证据、维护建议。

C. Bad Case Analysis Agent

优先建设

职责：把“测试失败了”变成“有证据、有分类、有下一步”的分析结果

调用：`badcase-triage` → 日志解析工具 → Trace 关联工具 → `root-cause-analysis` → 历史缺陷检索 → 缺陷报告生成。

交付：失败类型、证据链、根因候选、置信度、复现建议、缺陷草稿。

D. Regression Intelligence Agent

第三阶段

职责：判断一次变更可能影响哪些已有测试

调用：需求变更分析、代码/接口变更解析、依赖关系查询、历史缺陷检索、回归用例推荐。

交付：建议回归范围、优先级、变更关联证据、未覆盖风险。

四个 Agent 可以共享 Skill、知识库、工具服务和统一的权限体系。

它们也不一定需要彼此自由对话。多数情况下，用明确的 Workflow 串接会比让多个 Agent 自由协商更稳定。

## 三、真正能提速的地方：不是做一个 Agent，而是改造测试工作流

我会先把测试部门的工作拆成六个关键环节，再逐个寻找适合 AI 接手的任务。

这也与富卫广州公开招聘的自动化测试岗位职责存在较好的对应关系：岗位描述提到基于 User Story 设计自动化测试用例、开发和维护脚本、执行测试、分析结果、缺陷管理、回归测试，以及保险系统和业务数据流的端到端自动化。需要强调，这些是公开岗位要求，并不能证明富卫当前内部流程已经采用某种特定工具或存在某个具体痛点。

### 1. 需求分析：让 AI 先把需求理解清楚

高优先级

测试人员现在要做的工作：

拿到一份需求文档或 User Story，阅读业务描述、理解改动范围、找 BA 确认业务规则，再判断哪些功能需要测试。

常见问题：

- 需求文档很长，人工提取业务规则耗时；
- 需求描述不明确，测试人员需要反复找 BA；
- 新旧版本需求不一致；
- 需求没有明确的验收标准；
- 测试人员容易遗漏权限、异常、边界和状态变化；
- 历史类似需求没有被充分复用。

我会设计：Requirement Intelligence Skill。

它不只是总结文档，而是把需求转成结构化的测试输入。

实际工作流程

1. 上传需求

   Word、PDF、Excel、User Story、API 文档。
2. 解析与结构化

   提取功能、参与角色、业务条件、输入输出、业务规则、依赖系统。
3. 识别风险

   找出歧义、缺失条件、矛盾、未定义异常、验收标准缺失。
4. 检索历史知识

   查询类似需求、历史测试用例、相关缺陷和已确认业务规则。
5. 形成待确认清单

   把真正需要 BA 确认的问题整理出来，避免测试人员反复阅读和整理。
6. 生成结构化需求基线

   经过 QA/BA 确认后，作为后续测试设计的输入。

例如，需求写着：

> 允许客户在符合条件的情况下修改保单受益人。

AI 应该继续追问：

- 什么状态的保单允许修改？
- 是否需要特定角色权限？
- 多个受益人的比例总和有什么限制？
- 修改是否需要审批？
- 修改失败是否保留原数据？
- 是否需要保留修改历史？
- 是否允许并发修改？

最后生成一个结构化结果：

| 规则 ID  | 规则内容     | 当前状态  |
| ------ | -------- | ----- |
| BR-001 | 有效保单允许修改 | 待业务确认 |
| BR-002 | 受益人比例限制  | 待业务确认 |
| BR-003 | 是否需要审批   | 待业务确认 |
| BR-004 | 是否保留修改历史 | 待业务确认 |

这里最关键的设计是：AI 不能擅自把推测出来的规则当成正式业务规则。

每一条规则都必须带来源、版本、确认状态和责任人。

### 2. 测试场景和用例：让 AI 承担重复设计工作

最高优先级之一

这是我认为最容易产生实际价值的地方。

我会把它设计成一个完整的 Test Design Engine，而不是简单的 Prompt。

它至少要具备四个能力：

| 能力   | 具体工作                     |
| ---- | ------------------------ |
| 场景设计 | 从业务规则推导正常、异常、边界、权限、状态等场景 |
| 用例生成 | 把场景转为前置条件、步骤、数据、预期结果     |
| 历史复用 | 检索类似用例，避免重复造轮子           |
| 质量评审 | 检查遗漏、重复、逻辑错误和需求追溯关系      |

特别重要：测试设计必须采用成熟的测试设计技术，而不是让大模型自由发挥。

ISTQB CTFL v4.0.1 明确介绍了等价类划分、边界值分析、决策表、状态迁移等黑盒测试设计方法。它们是生成测试场景时应当落实的专业方法。

例如，保险业务中一个保单状态变更功能：

业务状态测试模型（示意）

Submitted

已提交

Underwriting

核保中

Approved

审核通过

Rejected

审核拒绝

示意状态，不代表富卫某个具体产品的实际状态机。

AI 不仅要测试正常流转，还应检查：

- 不允许的状态跳转；
- 重复提交；
- 并发操作；
- 操作失败后数据是否回滚；
- 状态变化后权限是否变化；
- 历史记录是否正确；
- 外部系统是否同步。

真正值得做的功能：自动生成覆盖矩阵。

比如：

| 业务规则   | 正常场景  | 异常场景  | 边界场景  | 权限场景  |
| ------ | ----- | ----- | ----- | ----- |
| BR-001 | 已满足条件 | 不满足条件 | 状态临界值 | 无权限操作 |
| BR-002 | 比例合法  | 比例不合法 | 边界比例  | 非授权修改 |
| BR-003 | 审批成功  | 审批拒绝  | 审批超时  | 无审批权限 |

每一个场景都能追溯到具体规则和需求。

这样做的价值不只是写得快，而是让测试覆盖更系统、更容易审计。

### 3. 自动化测试：AI 写脚本，工程框架执行脚本

核心工程建设

这里我会特别谨慎。

很多 AI 自动化测试项目会出现一个问题：

AI 可以根据自然语言生成一段 Playwright 脚本，但生成的脚本可能：

- 找不到正确的页面元素；
- 使用了错误的业务数据；
- 断言不充分；
- 页面还没有加载就开始操作；
- 没有清理测试数据；
- 表面执行成功，实际业务状态错误。

因此，我不会让 Agent 直接生成一段代码就自动运行。

我会设计一个完整的自动化工程流水线。

Automation Engineering Pipeline

1. Automation Suitability Analysis

   先分析哪些用例适合自动化：重复频率、稳定性、数据准备成本、业务价值、维护成本。
2. Script Generation

   使用已审核的用例、页面对象模型、API 契约、代码模板生成脚本。
3. Static Validation

   检查语法、依赖、命名、敏感信息、断言、测试数据和脚本规范。
4. Sandbox Execution

   在隔离的测试环境运行，禁止直接连接生产系统。
5. Result Verification

   检查 UI、API、数据库或业务状态，不能只看按钮是否点击成功。
6. QA Approval and Asset Registration

   人工确认后，将脚本纳入正式测试资产库。
7. CI/CD Execution

   在后续迭代或代码提交时按策略触发回归。

我会采用的技术组合：

| 测试类型   | 候选技术                               | 适用范围           |
| ------ | ---------------------------------- | -------------- |
| Web UI | Playwright + TypeScript            | 页面交互、端到端业务流程   |
| API    | Playwright API / Pytest / Requests | 接口功能、数据校验、接口契约 |
| 移动端    | Appium                             | iOS / Android  |
| 性能     | JMeter / k6                        | 并发、吞吐量、响应时间    |
| 数据验证   | SQL / Python                       | 数据一致性、批量校验     |
| 流水线    | Azure DevOps / Jenkins             | 持续集成、回归执行      |

具体选型需要看现有系统的技术栈和测试框架，不能为了引入新技术而推翻已经稳定运行的自动化平台。

### 4. Bad Case 分析：我认为这是整个项目最值得深挖的模块

重点建设

这部分不能做成一个“上传日志，AI 告诉你哪里错了”的工具。

因为测试失败不等于产品有 Bug。

我会先建立一个标准化的失败分类体系。

第一层：失败类型识别

| 一级分类              | 二级分类      | 示例          |
| ----------------- | --------- | ----------- |
| Product Defect    | 业务逻辑      | 计算结果不符合业务规则 |
| Product Defect    | 接口错误      | API 返回错误数据  |
| Product Defect    | 数据错误      | 数据未正确保存     |
| Product Defect    | 权限错误      | 无权用户成功执行操作  |
| Automation Defect | 定位器错误     | 页面元素定位失败    |
| Automation Defect | 脚本逻辑      | 脚本断言或流程错误   |
| Test Data Issue   | 数据不符合前置条件 | 测试保单已经失效    |
| Environment Issue | 环境异常      | 测试服务不可用     |
| Dependency Issue  | 外部服务异常    | 第三方接口超时     |
| Requirement Issue | 需求不明确     | 预期结果没有定义    |
| Test Design Issue | 用例设计错误    | 预期结果与业务规则冲突 |

这里还需要考虑间歇性失败、性能问题、安全问题、数据同步问题等子类型。

第二层：建立 Bad Case 自动分析流程

## Bad Case Intelligence Engine

输入：测试失败事件

Test ID / Run ID / Error / Screenshot / Trace / Logs / API / Environment

1\. Evidence Collector

自动采集截图、日志、执行记录、API 结果、版本信息

2\. Failure Classifier

判断产品缺陷、脚本、数据、环境、依赖、需求或用例问题

3\. Correlation Engine

按 Trace ID、Request ID、时间、版本、模块、历史缺陷关联证据

4\. Root Cause Analysis

提出多个根因假设，列出支持证据、反证和置信度

5\. Human Review

QA / 开发确认，修改分类和根因结论

6\. Defect & Knowledge Feedback

缺陷草稿、复测建议、回归用例、知识库更新

第三层：必须设计证据链，而不是让 AI 猜原因。

举一个实际类型的例子：

某保险理赔测试用例：

- 预期赔付金额：1,200；
- 实际返回金额：1,500；
- 测试结果：Failed。

一个不可靠的 AI 会直接说：

> 系统计算错误，开发需要修复理赔计算逻辑。

但真正的原因可能有四种：

| 假设          | 需要检查的证据            |
| ----------- | ------------------ |
| H1：业务计算逻辑错误 | 业务规则、计算服务日志、实际计算过程 |
| H2：测试数据错误   | 保单、理赔金额、免赔额、历史赔付数据 |
| H3：接口数据错误   | 请求参数、响应字段、数据映射     |
| H4：预期结果错误   | 需求版本、业务规则、BA 确认记录  |

AI 应该给出：

```
Bad Case ID: BC-2026-001

Failure Type:
Business Logic / Data / Requirement - Pending Confirmation

Observed:
Expected = 1200
Actual = 1500

Hypotheses:
H1: Calculation logic defect
H2: Incorrect test data
H3: API mapping issue
H4: Expected result is outdated

Evidence:
- API response indicates amount = 1500
- Test data contains historical claim record
- Business rule version has not yet been verified

Missing Evidence:
- Calculation service logs
- Approved business rule version
- Historical claim details

Recommended Next Actions:
1. Verify test data
2. Confirm applicable business rule
3. Trace calculation request
4. Escalate to developer if H1/H3 is supported

Final Root Cause:
Not confirmed
```

这才是能够交给测试人员和开发人员使用的分析结果。

第四层：建立历史 Bad Case 经验复用。

这部分很重要。

每一次已经确认的 Bad Case，都应该成为以后 AI 可以检索的经验。

例如：

- 历史上出现过类似的接口超时；
- 某个模块经常出现数据同步失败；
- 某个页面经常因为异步加载导致脚本误报；
- 某类保单状态组合经常出现业务逻辑错误。

下一次发生类似失败时，AI 就可以检索历史案例，给出相似案例、过去的根因和处理方法。

但要注意：相似案例不是当前案例的根因证据。历史经验只能帮助提出假设，不能直接定案。

### 5. 智能回归测试：不要每次都把全部用例跑一遍

中后期建设

我会专门设计一个 Regression Intelligence Engine。

它的工作方式是：

1. 接收本次需求变更或代码变更；
2. 识别涉及的业务模块、API、数据结构和依赖服务；
3. 查询历史测试用例和缺陷；
4. 计算变更可能影响的测试范围；
5. 结合风险、历史失败率、业务重要性给出回归建议；
6. 生成待执行测试集；
7. 由 QA 确认后触发执行。

例如，某次变更修改了保费计算服务。

不能只回归当前页面，而应分析：

- 新业务投保；
- 保单续期；
- 保单批改；
- 退保；
- 相关支付接口；
- 依赖该计算结果的报表或下游服务。

这里需要建立系统依赖图，而不只是简单做向量检索。

我会采用：

- Git Commit / PR 变更信息；
- API 契约和调用关系；
- 系统模块依赖图；
- 需求与测试用例关联；
- 历史缺陷关联；
- 执行记录和覆盖数据。

最终输出建议回归集，并明确列出没有覆盖到的风险。

### 2. 真实使用场景应该是什么样？

场景 A：QA 收到新需求

1. 打开工作台，上传需求文档；
2. 系统自动解析并识别业务规则；

测试人员不再从零开始翻日志。

## 五、技术架构：我会如何把它真正做出来？

但要特别强调：Power Platform 适合企业入口、流程和集成，不应该承担复杂自动化测试引擎的全部职责。

### 2. 为什么要引入 MCP？

我认为 MCP 值得纳入长期架构。

它解决的是 Agent 如何以统一方式连接外部工具和数据源的问题。

例如，测试平台可以提供这些 MCP 工具：

```
testing-mcp-server/
│
├── requirement/
│   ├── get_requirement
│   └── compare_requirement_versions
│
├── test_case/
│   ├── search_test_cases
│   ├── create_test_case_draft
│   └── validate_test_case
│
├── automation/
│   ├── generate_script
│   ├── validate_script
│   ├── execute_test_job
│   └── get_execution_result
│
├── badcase/
│   ├── get_failure_evidence
│   ├── search_similar_failures
│   └── create_defect_draft

    ├── get_change_impact
    └── recommend_regression_cases
```

这样，不管未来使用 Copilot Studio、其他 Agent 框架，还是 AI Coding Agent，都可以通过统一工具接口使用测试能力。

不过，MCP 不是安全边界。工具服务仍然必须自行执行身份验证、授权、参数校验、审计和敏感数据过滤。

### 3. 为什么要重视可观测性和 AI 评测？

这点非常容易被忽略。

传统自动化测试需要测试被测系统；AI 测试平台本身也需要被测试。

例如：

- 同一份需求，重复运行会不会生成完全不同的关键用例？
- AI 会不会遗漏业务规则？
- AI 会不会把历史缺陷错误地当成当前根因？
- 是否调用了错误工具？
- 是否把不该读取的数据交给模型？
- 模型升级后，输出质量是否下降？

Microsoft Foundry 已经提供 AI 应用的评测、Tracing 和生产监控能力，可以评估 Agent 的任务完成度、工具调用准确性、RAG Groundedness 等，并把评测集接入 CI/CD 质量门禁。

## 六、真正企业级的核心：测试资产、知识和数据模型

很多 AI 项目做不大，不是模型不够聪明，而是缺乏结构化资产。

我会建立一套统一的数据模型。

### 1. 核心数据关系

Requirement

需求版本、来源、验收条件

Business Rule / Risk

业务规则、风险、确认状态

Test Scenario

测试场景、覆盖目标

Test Case

前置条件、数据、步骤、预期结果

Automation Script / Execution

脚本版本、环境、结果、证据

Bad Case / Defect / RCA

失败类型、根因、证据、修复结果

Knowledge Feedback

已确认经验、规则更新、回归资产

这里有一个重要设计原则：

每个测试结果都必须能够反向追溯到需求和业务规则。

比如一个自动化测试失败，系统应该可以找到：

- 对应哪个测试用例；
- 用例依据哪个场景；
- 场景验证哪个业务规则；
- 规则来自哪一版需求；
- 需求是否已经被 BA 确认；
- 当前执行使用了哪个脚本版本；
- 当前运行在哪个环境和应用版本；
- 历史上是否发生过类似缺陷。

没有这些关系，后续的 Bad Case 分析、回归推荐、质量统计都很难做准确。

### 2. 知识库不应该只是上传文档然后向量检索

我会将知识分成四类：

| 知识类型  | 内容                   | 更新机制       |
| ----- | -------------------- | ---------- |
| 业务知识  | 保险规则、产品规则、业务流程       | BA 确认、版本更新 |
| 测试知识  | 测试标准、用例模板、测试策略       | QA 维护      |
| 缺陷知识  | 历史 Bad Case、RCA、解决方案 | 缺陷关闭后沉淀    |
| 自动化知识 | 脚本、页面对象、API 契约、执行规范  | Git 版本管理   |

检索时不能只依赖语义相似度。

还需要结合：

- 系统和业务模块；
- 产品和渠道；
- 需求版本；
- 缺陷状态；
- 时间范围；
- 权限；
- 知识有效期。

尤其是保险业务，不同产品、不同版本、不同业务流程可能有不同规则，不能因为两份文档语义相似就直接混用。

## 七、企业项目必须考虑的安全和可靠性问题

保险企业对数据、权限和审计要求高，我会把治理设计放在开发初期，而不是上线前补充。

### 1. 不能让 AI 拥有无限权限

建议按能力设置权限：

| 操作        | 默认策略         |
| --------- | ------------ |
| 查询已授权测试用例 | 可自动          |
| 检索已授权历史缺陷 | 可自动          |
| 生成测试用例草稿  | 可自动          |
| 生成自动化脚本草稿 | 可自动          |
| 在隔离测试环境执行 | 经策略授权后自动     |
| 修改正式测试资产  | 人工审核         |
| 创建正式缺陷单   | 人工确认或受控规则    |
| 修改业务数据    | 严格授权         |
| 访问生产数据    | 默认禁止 AI 直接访问 |
| 发布和生产操作   | 人工审批         |

尤其不能使用开发者个人账号作为所有 Agent 的共享执行身份，否则容易出现权限扩大和越权读取。

### 2. 保险数据必须经过治理

我会要求：

- 优先使用合成测试数据；
- 真实数据必须经过审批和脱敏；
- 身份证、手机号、保单号、账户信息等敏感字段按政策处理；
- 不把未经批准的生产数据发送到外部模型；
- 日志、截图、Trace 和 API 请求都要考虑敏感字段泄漏；
- 数据访问、模型调用和工具执行都要有审计记录。

### 3. AI 本身也要做安全测试

至少应覆盖：

- Prompt Injection；
- 敏感信息泄露；
- 越权工具调用；
- 恶意文档和恶意日志；
- 知识库投毒；
- Agent 无限循环；
- 不可信输出执行；
- 错误的业务建议。

OWASP 2026 LLM Top 10 已将 Prompt Injection、Sensitive Information Disclosure、Excessive Agency 等列为重点风险。NIST 的 Generative AI Profile 也提供了生成式 AI 风险管理框架。

## 八、怎么实施？我会采用四个阶段，而不是一次性开发完整平台

这里给出一个可以拿去做项目立项和内部讨论的实施路线。

## 实施路线图

1. 阶段 0：Discovery 与现状盘点

   建议 2–3 周

   交付：
   - 测试流程地图；
   - 现有 Skills / Agent / 工具清单；
   - 当前测试管理系统和自动化框架清单；
   - 重复工作和耗时基线；
   - 数据权限和系统接口清单；
   - MVP 范围和验收标准。
   不能跳过这一阶段，否则很容易重复建设现有能力。
2. 阶段 1：Test Design Assistant

   建议 4–6 周

   先实现：
   - 需求解析；
   - 业务规则提取；
   - 风险识别；
   - 测试场景生成；
   - 测试用例生成；
   - 用例覆盖和质量评审；
   - 历史用例检索；
   - Excel / 现有测试平台导出。
   这一阶段不自动批准用例，也不直接自动修改正式测试资产。
3. 阶段 2：Bad Case Intelligence

   建议 4–6 周

   先实现：
   - 统一失败事件格式；
   - 日志、截图、Trace 采集；
   - Bad Case 分类；
   - 历史缺陷检索；
   - 根因假设和证据链；
   - 缺陷报告草稿；
   - 人工确认和知识反馈。
   这一阶段应先接入一个真实测试项目，而不是只用人工构造的日志演示。
4. 阶段 3：Automation Engineering

   建议 6–10 周

   实现：
   - 自动化候选识别；
   - Playwright / API 脚本生成；
   - 静态检查；
   - 沙箱执行；
   - 执行结果归档；
   - Bad Case 自动分析；
   - QA 审批后纳入正式脚本库。
5. 阶段 4：Regression Intelligence & CI/CD

   建议 6–10 周

   实现：
   - 需求变更影响分析；
   - 代码和接口变更分析；
   - 测试依赖图；
   - 智能回归集推荐；
   - CI/CD 集成；
   - 质量趋势分析；
   - 持续评测和优化。

时间为初步规划估算，实际工期取决于系统接口开放情况、团队人数、历史资产质量、环境和审批周期，不是承诺工期。

### 第一阶段到底应该交付什么？

我建议第一阶段不要追求全自动化，而是交付一个可以被真实 QA 使用的产品。

MVP 的验收标准应该包括：

| 验收项目 | 需要达到的结果         |
| ---- | --------------- |
| 需求解析 | 能准确提取需求内容和来源    |
| 规则识别 | 能区分已确认规则和待确认规则  |
| 用例生成 | 输出符合团队模板的完整用例   |
| 覆盖检查 | 能指出缺少的场景和覆盖依据   |
| 历史检索 | 能找到真正相关的历史用例    |
| 去重   | 能识别明显重复或高度相似的用例 |
| 结果导出 | 能进入现有 QA 工作流程   |
| 质量评估 | 有固定测试集和可量化结果    |
| 权限安全 | 不会越权读取或修改资产     |
| 可追溯  | 生成内容能追溯到需求和规则来源 |

一个重要的工程建议：先接入现有测试管理系统，不要第一天就自己造一个测试管理系统。

如果富卫已经有 Azure DevOps Test Plans、Jira、Xray、Zephyr 或其他平台，就应该优先通过 API、Connector 或 MCP 接入。Azure DevOps 官方目前也提供通过 MCP Server 查询测试运行、失败用例、执行趋势和回归情况的相关能力。

## 九、如何证明它真的提速了？必须建立量化评估体系

我不会用“AI 生成了 500 条用例”作为项目成果。

因为生成数量并不等于质量，甚至可能制造大量无用工作。

我会建立三层指标。

### 1. 效率指标

| 指标              | 计算方法              |
| --------------- | ----------------- |
| 需求分析时间          | 需求分析总耗时 / 需求数量    |
| 用例编写时间          | 用例设计总耗时 / 有效用例数量  |
| 用例评审时间          | 评审总耗时 / 评审用例数量    |
| Bad Case 初步分类时间 | 失败分类总耗时 / 失败数量    |
| 根因分析时间          | RCA 总耗时 / 已分析失败数量 |
| 回归测试耗时          | 实际回归总时长           |

### 2. 质量指标

| 指标             | 衡量什么                   |
| -------------- | ---------------------- |
| 需求追溯率          | 用例是否能追溯到需求             |
| 业务规则覆盖率        | 应测规则是否被测试场景覆盖          |
| 用例有效采纳率        | AI 生成内容中被直接采纳或修改后采纳的比例 |
| 用例重复率          | 新生成用例与现有用例的重复程度        |
| Bad Case 分类准确率 | AI 分类与人工确认结果的一致程度      |
| RCA 有用率        | 根因建议是否帮助人工定位问题         |
| 自动化稳定率         | 排除已确认环境故障后，脚本稳定执行的比例   |
| 回归漏测率          | 被推荐范围之外实际发现的相关问题比例     |

### 3. AI 平台自身指标

- 模型调用失败率；
- 平均响应时间；
- 单任务 Token / 计算成本；
- 工具调用成功率；
- RAG 检索准确率；
- 输出格式合格率；
- 任务完成率；
- 越权调用拦截率；
- 模型升级前后质量变化。

我会为每个 Skill 建立 Golden Dataset：

例如 `test-case-design`：

- 50 份经过 QA 确认的需求样本；
- 每份需求对应人工确认的业务规则；
- 对应标准测试场景；
- 对应标准测试用例；
- 已知的边界和异常场景。

之后修改 Prompt、Skill、模型或工作流，都要在这批数据上回归评测。

不能今天改了 Skill，明天发现生成质量下降，却不知道问题出在哪里。

## 十、哪些能力值得长期投入？哪些容易被快速替代？

你提出的一个问题非常重要：AI 发展很快，不希望投入的工具很快被替代。

我的判断是：

不要把核心竞争力押在某一个模型、某一种 Agent 框架或某一个 Prompt 上。应该把核心资产放在业务知识、测试数据、执行框架、评测体系、系统集成和治理能力上。

| 技术或能力                         | 长期价值判断 | 我的建议               |
| ----------------------------- | ------ | ------------------ |
| 单一 Prompt                     | 较低     | 只作为能力实现的一部分        |
| 某一模型品牌                        | 较低     | 保持模型可替换            |
| SKILL.md                      | 中高     | 作为可复用能力封装，但不绑定某个厂商 |
| Agent                         | 中高     | 负责复杂判断，不要过度拆分      |
| Workflow                      | 高      | 保障流程稳定和可审计         |
| MCP / API 工具层                 | 高      | 统一外部系统访问接口         |
| Playwright / API 自动化          | 高      | 建立稳定的确定性执行能力       |
| 测试资产与业务规则库                    | 很高     | 作为企业长期积累           |
| Bad Case 证据链与历史知识             | 很高     | 建立企业独有的质量数据资产      |
| AI Evaluation / Observability | 很高     | 保障持续升级和质量稳定        |
| 权限与治理体系                       | 很高     | 企业级应用的基本要求         |

我认为真正值得长期发展的方向是：

1. Spec-to-Test：从需求、业务规则到测试资产的自动化；
2. AI-assisted Test Automation：AI 辅助脚本开发、维护和执行；
3. Evidence-based RCA：以证据为基础的故障定位；
4. Change Impact & Regression Intelligence：变更影响分析和智能回归；
5. Continuous Quality Engineering：把 AI 评测、测试质量和 CI/CD 融合起来。

这几类能力不会因为某个模型更换就失去价值。

## 十一、如果让我现在负责这个项目，我会怎么做？

我会给领导提交以下建设决策，而不是直接要求批准开发十几个 Agent。

## 我的项目决策建议

第一优先级

Test Design Assistant

需求解析、业务规则提取、场景生成、用例生成、用例审查、历史用例复用。

原因：重复工作明显、输入输出相对明确、容易人工验收，也容易量化效率和质量。

第二优先级

Bad Case Intelligence

自动采集失败证据、失败分类、历史案例匹配、根因假设、缺陷报告草稿。

原因：解决测试人员排查问题耗时、经验依赖和信息分散的问题，同时沉淀企业质量知识。

第三优先级

Automation Engineering

自动化脚本生成、检查、隔离执行、结果校验、脚本资产管理。

原因：必须建立在稳定的测试用例、数据、环境和自动化框架基础上。

第四优先级

Regression Intelligence

需求变更、代码变更、依赖分析、风险评估、回归集推荐。

原因：依赖高质量的历史用例、缺陷、执行和系统依赖数据，前期不适合直接追求全自动。

### 我会明确拒绝的五种做法

1. 不做一个万能 Testing Agent：任务边界太宽，结果难以验证。
2. 不做只会生成测试用例的聊天机器人：没有业务规则、历史资产和质量检查，价值有限。
3. 不让 AI 自由执行所有测试操作：执行权限和业务风险必须受控。
4. 不让 AI 单独判定根因和关闭缺陷：它可以提出证据充分的候选结论，但最终需要责任人确认。
5. 不先做复杂多 Agent 架构：先验证能力价值，再按实际瓶颈拆分 Agent。

## 十二、现在最重要的一步：盘点富卫现有能力，而不是从零造轮子

你之前提到，当前企业内部已经有一些 Skill，但你还不清楚具体有哪些、怎么使用。我认为这件事应该作为正式项目的第一个工作包。

我会安排一次 Testing Capability Discovery，盘点：

| 盘点对象      | 需要弄清楚什么                               |
| --------- | ------------------------------------- |
| 现有 Skills | 名称、说明、文件、输入输出、调用方式                    |
| 现有 Agents | 已有功能、模型、工具、权限、使用人                     |
| 自动化框架     | Selenium / Playwright / Appium / 自研框架 |
| 测试管理系统    | 用例、测试计划、执行记录、缺陷在哪管理                   |
| 日志系统      | 日志来源、Trace ID、API 请求记录、查询方式           |
| 测试知识      | 历史用例、业务规则、历史 Bad Case                 |
| 流程工具      | Power Automate、Azure DevOps、Jira 等    |
| 安全策略      | 数据分级、模型访问、权限、审计和审批                    |

我不会假设富卫已有哪一种具体 Skill。盘点时应当把它们归为：

- 已有可直接复用；
- 已有但需要增强；
- 有工具但没有 Skill 封装；
- 有 Skill 但没有可靠执行工具；
- 完全缺失，需要开发。

尤其要区分“某个团队有一段 Prompt”和“企业已经拥有一个可维护、可评测、可复用的 Skill”。这两者差别很大。

### 建议第一周先拿到这五项材料

1. 目前测试部门使用的自动化框架及脚本仓库说明；
2. 测试用例模板和 10–20 份已脱敏的历史需求及用例；
3. 近期 20–50 个已确认结果的 Bad Case 样本，包含日志、错误和最终根因；
4. 现有 Skills、Agent、MCP Server、API 工具清单；
5. 测试管理系统、缺陷系统和 CI/CD 的集成方式。

拿到这些资料后，就能用真实工作样本评估哪些环节值得做 AI，而不是凭空设计功能。

我建议接下来直接形成一份《FWD AI Testing Engineering Platform — Technical Design & Implementation Blueprint v1.0》，里面具体落到 Skill 目录、Agent 职责、工具 API、数据表设计、工作流、Bad Case 分类和分析 Schema、权限矩阵、部署架构、测试评测集以及分阶段验收标准。这样就可以从方案讨论进入工程实施。
