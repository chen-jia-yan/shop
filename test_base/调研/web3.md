一、先查「点节点没反应」（5 分钟） ￼

1. 打开 F12 并设置好（Edge 浏览器） ￼

1. 在图谱页面按 F12，或右键空白处 →「检查」。

2. 点开发者工具顶部的 「网络」（Network） 标签。

3. 勾选 「保留日志」（Preserve log）。

4. 点筛选按钮 「Fetch/XHR」，只看接口请求。

5. 在筛选框里输入 ‎`kg`，只看图谱接口。

6. 点左上角的 🚫 图标清空列表。

2. 点一个节点，看列表有什么变化 ￼



|你看到的                                       |说明                       |谁来改                                  |

|-------------------------------------------|-------------------------|-------------------------------------|

|**列表里没有新增任何请求**                            |前端没有给节点绑定点击事件，或者点击后只在本地处理|前端。再切到「控制台」（Console）标签，看有没有红色报错，截图给前端|

|有新请求，状态码是 **422**                          |参数格式不对                   |看下面第 3 步                             |

|状态码 200，返回 `"code": "CCB001"`              |业务错误，看 message 的内容       |看下面的对照表                              |

|状态码 200，返回的列表是空的（`items: []` 或 `nodes: []`）|接口通了，但没查到数据              |看下面的对照表                              |

|状态码 200，有数据，但页面没变化                         |前端拿到数据后没有画出来             |前端                                   |

|状态码 404                                    |前端调的路径不对，或者 dit 上还是旧版后端  |对一下路径；确认 dit 部署的版本                   |

|状态码 500，或请求一直转圈                            |后端出错                     |后端，需要看 dit 日志                        |

3. 有请求时，点开那一行，看三个地方 ￼



|标签              |看什么                                                       |

|----------------|----------------------------------------------------------|

|**标头**（Headers） |`Request URL` 是不是 `…/nodes/expand` 或 `…/nodes/chunks/list`|

|**负载**（Payload） |前端传了什么。重点看节点 id 是不是节点的 `id`（而不是 `name`），有没有带 `saas_id`    |

|**响应**（Response）|后端返回了什么                                                   |

4. 后端返回结果的对照表 ￼



|返回                   |原因                                            |处理                  |

|---------------------|----------------------------------------------|--------------------|

|422，`entity_types` 相关|传了空列表 `[]`                                    |前端：全部取消勾选时，这个字段不传   |

|422，缺少字段             |少传了 `saas_id`，或者节点 id 放错了字段                   |按《前端对接说明》对字段名       |

|CCB001「节点不存在」        |传的是 `name`，或 id 被转义了（id 里含 `::`，前端要原样传）       |前端改成传 `id`          |

|CCB001「该租户未配置知识图谱」   |传的 `saas_id` 没有对应的图谱                          |确认 dit 用的是哪个 saas_id|

|`expand` 返回空         |节点本来就没有相邻节点，或过滤条件把相邻节点都过滤掉了                   |换一个度数大的节点试；不带过滤条件再试 |

|`chunks/list` 返回空    |jp-poc 的旧数据大多数切片没有正文（16,427 个切片里只有 1,300 个有摘要）|已知问题，等 K5 补全切片后解决   |

5. 先确认 dit 上跑的是不是新代码 ￼

dit 上只有已经合并、并且流水线跑完的代码。如果「KG 接口调整」还没提 PR 合并，dit 上跑的就是旧接口：节点没有 ‎`type_zh`、‎`degree` 这些字段，也不认识 ‎`saas_id`，前端按新文档调用自然会出错。

快速判断方法：在网络列表里点开总览接口（overview）那一行 →「响应」，看节点里有没有 ‎`type_zh` 和 ‎`degree` 字段。没有，就说明 dit 还是旧版本。

把这几样发我，我帮你判断： 点击后那条请求的 URL、负载、响应（打码规则见第三节第 4 步）；或者「列表里没有新请求」的截图。

二、自测和联调：分四层 ￼



|层       |谁      |在哪          |目的         |

|--------|-------|------------|-----------|

|① 本地自测  |你      |自己电脑        |代码本身没问题    |

|② dit 自测|你      |dit 页面 + F12|部署上去以后也没问题 |

|③ 联调    |你 + 前端 |dit（或各自本地）  |前后端字段、交互对得上|

|④ 测试验收  |测试 / 组长|dit / sit   |按用例签字      |

① 本地自测（每次提 PR 之前） ￼

第 1 步：跑测试

```powershell
Set-Location C:\Users\234393\Desktop\tap-ai-backend
& .\.venv\Scripts\python.exe -m pytest -q

```

第 2 步：本地启动后端，打开 swagger

1. 用你平时的方式启动后端。

2. 浏览器打开 ‎`http://localhost:8000/docs`（端口以启动日志为准）。

3. 找到 ‎`library-kg` 分组，点开一个接口，例如 ‎`POST …/graph/overview`。

4. 点右上角 Try it out。

5. 在请求体里填：

```json
{"saas_id": "jp", "limit": 50}

```

6. 点 Execute。

7. 往下拉到 Server response：看 ‎`Code` 是不是 200，‎`Response body` 里是不是有节点。

第 3 步：按页面上的操作顺序，在 swagger 里依次调用

总览 → 复制一个节点的 ‎`id` → 调 ‎`nodes/expand` → 调 ‎`nodes/chunks/list` → 调 ‎`nodes/search`。这样走一遍，就等于在 swagger 里模拟了前端点击的完整过程。每一步都对照自测用例表（‎`TAP-10366_自测用例.csv`）填写「实际结果」和「是否通过」。

② dit 自测（PR 合并、流水线跑完以后） ￼

1. 确认部署好了：在 Azure DevOps 里打开 Pipelines，找到 ‎`tap-ai-backend-cd`，最新一次运行是绿色的，并且对应的是你那次提交。

2. 打开页面：‎`https://tap-ctc-dit.fwdasia.intranet` → 左侧 Library → Knowledge Graph。

3. 开着 F12 逐项操作（按第一节的设置），每做一个操作，就看网络列表里对应的那条请求：



|页面操作           |应该出现的请求                     |检查                      |

|---------------|----------------------------|------------------------|

|打开图谱页          |overview、stats（或 types/list）|200，有节点；左下角各类型数量和返回数据对得上|

|左下角取消勾选一个类型    |overview（带 `entity_types`）  |图里这类节点消失                |

|搜索框输入名称        |nodes/search                |有结果，点结果能定位到节点           |

|点节点            |nodes/expand                |出现相邻节点                  |

|看节点关联的切片       |nodes/chunks/list           |按文档分组显示                 |

|切到 Documents 标签|files/list                  |有文件列表                   |

4. 把结果填进用例表：哪条不通过，就在备注里写上请求 URL 和返回内容。

③ 联调（和前端一起） ￼

联调就是一起走一遍页面，发现字段对不上就当场定位，决定由谁改，不是一起写代码。

1. 联调前

- 把《前端对接说明》（‎`p4_前端对接说明.md`）发给前端，他按里面的字段写代码。

- 你自己先做完 ② dit 自测，保证接口本身是好的。

2. 联调时（Teams 共享屏幕，一般前端操作页面）

- 前端点页面，你看他的 F12，或者让他把那条请求的负载和响应截图发给你。

- 每个问题按下表判断归属：



|现象                |归谁          |

|------------------|------------|

|没有发请求、请求的参数和文档不一样 |前端          |

|参数和文档一致，但返回错误或数据不对|后端（你）       |

|文档本身没写清楚          |一起商量，然后你更新文档|

- 每个问题记一行：现象、请求 URL、归谁、状态。

3. 联调后

- 改代码 → 本地自测 → 提 PR → 流水线部署到 dit → 通知前端「已修，可以再测一下」。

- 一次 PR 可以带上多个问题的修复，不用每个问题单独提。

4. 能不能不等部署？

可以问前端：他本地启动的前端，能不能把接口地址指向你电脑上的后端（你电脑的 IP 加 8000 端口）。如果公司网络允许，联调时改了就能马上看到效果，不用每次等流水线。这取决于你们的网络和他的代理配置，问他一句就知道。

④ 测试验收 ￼

把填好的自测用例表交给组长或测试，由他们决定要不要在 sit 上再测一轮。

三、F12 里的几个常用操作 ￼

1. 看某个请求的完整内容：点开那一行 →「负载」看传了什么，→「响应」看返回了什么。

2. 复制返回内容发给别人：在那一行上右键 → 复制 → 复制响应（Copy response）。

3. 重新发一次同样的请求：右键那一行 →「重新发送」（Replay XHR），不用再点页面。

4. 截图发人之前先打码：「标头」里的 ‎`Authorization`、‎`Cookie` 不要截进去，也不要复制出来。
