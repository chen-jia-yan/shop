# Skill description 写作规范

模型判断要不要调用某个 skill，主要看它 frontmatter 里的 `description`。
description 写得含糊，skill 就不会被自动调用，用户只能靠记名字来用，这是利用率低的常见原因。

## 一条好的 description 要包含三部分

1. **做什么**：一句话，说清楚产出什么。
2. **什么时候用**：列出用户的典型说法和触发场景，越贴近用户原话越好。
3. **什么时候不用**：写出容易混淆的场景，并指向正确的 skill。

## 对比示例

❌ 不好：
```
description: 会议纪要处理工具。
```
问题：没说什么时候用，用户说"把会议结论存一下"时模型不会联想到它。

✅ 好：
```
description: 把会议纪要或 Teams 转写整理成决策、待办和负责人，并按规范写回 TAP 知识库。当用户粘贴会议纪要、说"整理一下会议""把会议结论存到知识库""提取待办"时使用。不用于会前准备（用 meeting-prep），也不用于普通文档入库（用 doc-ingest）。
```

## 检查清单

- [ ] 第一句就说清楚产出，而不是技术手段
- [ ] 至少列出 3 种用户的常见说法
- [ ] 写了至少 1 条"不用于"，并指明替代的 skill
- [ ] 提到关键对象（会议纪要、合同、Word、邮件……），方便模型匹配
- [ ] 没有和其他 skill 的 description 高度重复；如果两个 skill 的触发说法相近，在各自的"不用于"里互相区分
- [ ] 长度控制在 2-5 句，太长会占用上下文、稀释匹配

## 改完后怎么验证

拿 5-10 句用户真实说法（可以从问答日志里挑）去试：
- 该触发的有没有触发
- 不该触发的有没有误触发
- 两个相近的 skill 有没有选错

把这些说法记录到对应 skill 的 `evaluations/` 里，以后每次修改都回归一遍。
