# 报告写作与 notes.json

> **judgments.json 和 notes.json 的分工**：判断类内容（性质、级别、对谁生效、理由、证据、受影响内容的处置、修订建议稿）都写在 judgments.json，格式见 `methods.md`。notes.json 只写报告的补充信息（摘要、对客告知、负责人、部门、读者、密级等）。下面的 `overrides` 是旧写法，仍然支持；同一条变更两边都写时，以 judgments 为准。

## 1. notes.json 完整格式

所有字段都可选。`score.py` 读 `overrides`，`build_report.py` 读其余字段（两个脚本传同一个文件即可）。

```json
{
  "overrides": {
    "<变更编号>": {
      "level": "P0 | P1 | P2 | P3",
      "category": "<类别 key，见 impact.json categories>",
      "actions": [["<事项>", "<责任部门>", <相对生效日的天数，负数为生效前>]],
      "comment": "<分析意见，显示在该条变更下方>",
      "reason": "<调整级别或忽略时必填>",
      "ignore": true
    }
  },
  "title": "<报告标题，默认《文档名》变更影响分析报告>",
  "summary": "<结论摘要，默认自动生成>",
  "highlights": ["<需要优先关注的要点，排在自动要点之前>"],
  "conclusions": ["<结论与建议，显示在摘要下方>"],
  "notice": "<对客告知要求>",
  "owners": {"<责任部门>": "<负责人>"},
  "sources": ["<补充的数据来源说明>"],
  "department": "<编制部门>",
  "audience": "<阅读对象>",
  "confidentiality": "<密级>",
  "version": "<报告版本>",
  "doc_no": "<报告编号>",
  "brand": "<机构名称覆盖>",
  "fonts": {"cn": ["<中文字体候选>"]},
  "config": {"<任意 tap-config 片段，只对本次生效>": "..."}
}
```

规则：

- `level` 与 `ignore` 必须配 `reason`，否则 `score.py` 拒绝运行。
- `actions` 会**替换**该条的自动处置事项，不是追加。要保留自动的，把它们抄进来再加。
- `ignore` 的变更不进入正文、统计和跟踪表，但仍在 changes.json 里可查。
- 负责人只填你确实知道的；不知道的留空，报告显示【待补充】，交付说明里列出。

## 2. 版本选择

| 版本 | 内容 | 适合 |
|---|---|---|
| full（默认） | 摘要、概览、P0–P2 逐条分析、影响范围、处置计划、合规告知、附录、签批 | 执行落地、存档、审核附件 |
| brief | 摘要、概览、P0–P1 逐条分析、处置计划、合规告知 | 发管理层、例会通报 |

正文逐条分析最多 `detail_max`（12）条，按级别和分数取最重要的；其余在附录二的全部变更明细里。

## 3. 文字规范

**结论摘要**（一段话，3–5 句）：总数 → 实质变更与级别 → 主要涉及哪些方面 → 知识库影响 → 最关键的一项是什么、要谁在什么时候完成。自动生成的摘要只有前四项，**最后一句由你补上**（写进 `summary`）。

**变化说明**

| 写法 | ✅ | ❌ |
|---|---|---|
| 数值 | 等待期由 90 天调整为 30 天 | 等待期大幅缩短 |
| 新增 | 新增“质子重离子治疗费用”为医疗费用保障范围 | 新增若干保障 |
| 删除 | 删除责任免除第（六）项“既往症” | 优化了免责条款 |
| 义务表述 | “应当在 10 日内通知”改为“可以在 10 日内通知”，由强制改为可选 | 表述调整 |
| 范围 | 投保年龄上限由 60 周岁调整为 65 周岁，覆盖人群扩大 | 放宽投保条件 |

**分析意见**（comment）写脚本看不出来的判断：对客户是利是弊、与其他条款的联动、是否涉及定价或再保、监管口径。每条 1–3 句，有依据写依据。

**处置事项**：动词 + 对象 + 结果，时限写相对生效日（报告自动换算日期）。

**禁止**：“未发现影响”（除非确实全量查过，写明范围）；“建议关注”“加强管理”这类无法执行的表述；把推测写成事实。

## 4. 版式

报告默认使用 Word 的 blue 商务蓝风格（浅蓝封面、蓝色强调），可用 `--style` 换成 soft 淡雅蓝、navy 深蓝稳重或橙色系的 classic / premium / minimal。修订前后对照使用左右卡片、变化处加粗；四象限、时间轴、指标卡、图表都由 kb-to-word 渲染，品牌色与字体来自 tap-config。需要调整文字或补内容时，改 `_报告内容.json` 后单独运行：

```bash
python ../kb-to-word/scripts/render_docx.py out/xx_报告内容.json out/xx.docx
python ../kb-to-word/scripts/review_docx.py out/xx.docx --doc-type impact --out out/xx_质检报告.md
```
