# 自动触发：文档提交审核时出具预分析

目标：一份条款、制度新版本提交审核时，自动比对上一个生效版本，生成“审核前预分析”给审核人参考。审核人从第一眼就能看到改了什么、影响哪些内容、有哪些需要确认，不用等发布后再补做影响分析。

> 下面的 TAP 接口和字段名是按常见做法写的示意，**以实际系统为准**。接入时只需要把 TAP 事件转成 event.json，脚本本身不依赖 TAP。

## 1. 流程

```
TAP：新版本状态变为“待审核”
  └─ 钩子 / 定时任务：查上一个“已生效”版本，导出两个文件和相关知识库内容 → 写 event.json
       └─ run.py prepare  → 工作包（workpack.md + judgments.template.json）
            └─ 模型按 methods.md 判断 → judgments.json → judgments.py check 自查
                 └─ run.py finish → 预分析报告 + 跟踪表 + 修订建议稿
                      └─ 以附件形式挂到审核单上（只挂附件，不改审核状态）
审核人：看报告 → 在“待人工确认”清单里确认或修改 → 正式发布后按跟踪表处置
处置完成：verify.py 核验 → 确认过的经验用 experience.py add 入库
```

## 2. event.json

```json
{
  "trigger": "review_submitted",
  "event_id": "TAP-REV-20260105-0012",
  "doc": {"id": "DOC-10023", "name": "示例重大疾病保险条款", "type": "条款", "owner": "产品部"},
  "old": {"file": "v2.3.docx", "label": "v2.3（2025-03）", "version_id": "DOC-10023-v2.3"},
  "new": {"file": "v3.0.docx", "label": "v3.0（2026-01）", "version_id": "DOC-10023-v3.0", "effective_date": "2026-03-01"},
  "source": "产品条款修订",
  "scope_terms": ["示例重大疾病"],
  "exclude": ["DOC-10023"],
  "corpus": ["kb_export.jsonl", "retrieval_results.json"],
  "submitter": "提交人",
  "reviewer": "审核人"
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `trigger` | 是 | `review_submitted`（提交审核）/ `published`（已发布，事后补做）/ `manual`（手工发起）。除 `manual` 外，报告都按“审核前预分析”出具 |
| `old.file` / `new.file` | 是 | 路径相对 event.json 所在目录。**找不到上一个生效版本时不要触发**，流程会直接停止 |
| `new.effective_date` | 否 | 没有的话，报告标【待补充】，时限按默认窗口估算 |
| `scope_terms` | 否 | 产品名 / 制度名。不写会扫全库，误报会增加 |
| `exclude` | 否 | 被修订文档本身的 ID。文档名会自动加入排除 |
| `corpus` | 否 | 知识库导出、Retrieval / qa_advance 结果、知识图谱查询结果，可以写多个。不写则只生成补查语句 |

## 3. 语料从哪里来

建议在钩子里一次性准备好，减少后面人工补查：

1. **同产品内容**：按 `scope_terms` 从知识库导出（FAQ、说明书、话术、操作指引……）。
2. **关键词检索**：先跑一遍 `run.py prepare`，把工作包里的“建议补查”语句交给 TAP Retrieval，结果存成 JSON。
3. **语义检索**：同样的语句再走一次向量检索，每条结果加 `"via": "vector"`。
4. **知识图谱**：以被修订文档和其中的产品、责任、期间等实体为起点，查“引用 / 依据 / 适用于”关系的一跳、两跳内容，每条加 `"via": "graph"`。

第 2-4 步的结果追加进 `corpus` 后重新 `prepare`。报告会按 `via` 写明每篇候选内容是从哪条路径找到的。

## 4. 回写 TAP（只挂附件）

`run.py finish` 的输出：

| 文件 | 挂到审核单 | 用途 |
|---|---|---|
| `<名称>.docx` | 是 | 预分析报告，封面标“审核前预分析” |
| `<名称>_跟踪表.xlsx` | 是 | 发布后分派处置用 |
| `<名称>_修订建议.json` | 可选 | 各篇受影响内容的“原文 → 建议改为”，状态为“待审核” |
| `<名称>_质检报告.md` | 否 | 内部自查用 |

钩子只做“上传附件 + 在审核单上留一条说明”，**不改审核状态、不改知识库、不发通知**（见 `boundaries.md`）。

## 5. 失败与降级

| 情况 | 处理 |
|---|---|
| 没有上一个生效版本（新产品首发） | 不触发 |
| 旧版是扫描件 / 图片 | 先 OCR。OCR 不了就不触发，在审核单上说明“无法自动比对” |
| 判断文件没通过检查（退出码 2） | 不出报告，把检查结果作为说明留在审核单上 |
| 没有语料 | 照常出报告，“影响范围”一节写明“未提供语料，以下为待补查语句” |
