# 边界：能做什么、不能做什么

> 方法（`methods.md`）给判断留了很大空间：可以和初筛不一样，可以识别配置里没有的类别。本页列出不管怎么判断都不能越过的线。
> 这几条是写死的，数量很少，也不会随业务变化，所以不需要维护。其余一律不写成规则，交给方法和判例。

## 1. 只读、只出分析材料

| 可以 | 不可以 |
|---|---|
| 读新旧版文档、知识库导出、检索 / 问答结果、知识图谱查询结果 | 修改、发布、下线知识库里的任何内容 |
| 生成报告、跟踪表、修订建议稿（状态都是“待审核”） | 修改文档的审核状态，也不能代替审核人“通过”或“驳回” |
| 在报告里写建议的责任部门和时限 | 向任何人发通知、派任务，或改动系统参数 |
| 把经确认的判断沉淀为判例 | 把没经确认的判断当成判例使用 |

修订建议稿只是建议，由内容负责人审核后，按 TAP 的正常流程修改。

## 2. 不编造

- 不新增事实。修订建议稿里的数字、日期、金额、比例、承诺，只能来自新旧条款或该内容原文。缺信息写 `【待补充：…】`。（脚本会核对）
- 拿不到旧版、看不到图片 / 扫描件、语料不全时，直接写缺什么。**不凭记忆补旧版内容，“没有查”不能写成“没有影响”。**
- 监管要求、报备义务、对存量客户是否适用，只写有依据的。没有依据的写成“待合规确认”的问题，不下结论。
- 证据必须是原文。`evidence` 里的引文要能在原文里逐字找到。（脚本会核对）

## 3. 必须交给人的判断

下面这些情况可以判断、可以给建议，但结论要列进报告的“待人工确认”，确认人填了 `confirmed_by` 才算定稿。脚本会自动识别这些情况，不需要自己记：

- 重大 / 较大变更
- 比初筛降两级以上，或低于高风险下限
- 低置信度
- 使用了配置里没有的新类别
- 把有实质信号的变更判为措辞调整或排除
- 建议下线某篇内容，或建议新旧并列（涉及存量客户口径）
- 判断不了是否过时（`needs_review`）
- 初筛为重大 / 较大、但没有给出判断的变更

触发条件在 `tap-config/impact.json` 的 `guardrails.human_review` 里，可以调整。**只能收紧，不建议放宽。**

## 4. 合规用语

修订建议稿要通过合规禁用词检查（`tap-config` 的合规词表，和 Word / PPT 共用）。对外口径类内容在报告里注明“以合规部确认为准”。

## 5. 数据

- 报告和工作包里只放分析所需的原文片段，不放客户个人信息。如果语料里混有保单号、姓名、证件号，先在导出时脱敏。
- 示例数据（`examples/`）都是虚构的，只用于演示。不能当作真实产品口径引用。

## 6. 出了边界怎么办

用户要求“顺便把 FAQ 改了”“直接通过审核”“发个通知给理赔部”：说明这些不在本流程里做，告诉用户修订建议稿和跟踪表在哪里，由谁按什么流程去处理。
