# 下一步设计：语义匹配、引用链、经验入图谱（第 3、6、7 项，尚未实现）

> 这是设计草案，用于和 TAP / 知识图谱团队对齐接口。原则和现在一样：**检索负责多找候选，模型负责判断，人负责确认**。不为语义匹配另写一套规则。

## 现状和接入点

现在的流程已经为这三项留好了位置，接入时不需要改判断方法：

| 位置 | 现在 | 接入后 |
|---|---|---|
| `find_refs.py --corpus` | 读入任何来源的候选，`via` 字段原样保留 | 向量 / 图谱结果直接作为 corpus 输入 |
| `refs[].via` | keyword 或空 | `keyword` / `vector` / `graph`，报告写明候选来源 |
| `experience/cases.jsonl` | 判例文本文件，按术语 / 类别 / 信号打分 | 可迁入图谱，成为“判例”节点 |
| 工作包“建议补查” | 关键词检索语句 | 再加上语义问法和图谱查询起点 |

## 第 3 项：语义匹配（向量）

**解决什么**：关键词探针只能找到写了"等待期 90 天"的内容，找不到"观察期三个月""买了多久能赔"这种说法。

**做法**：

1. 为每条实质变更生成 2-3 个**业务问法**（站在客户、一线人员的角度）。由模型写，不靠模板，比如等待期变更 →"买了多久之后得病能赔""观察期是多长"。
2. 用 TAP 的向量检索召回 top-k（建议 20），结果加 `"via": "vector"` 和 `"sim"`（相似度）。
3. 合并到 corpus，和关键词候选一起交给模型判断。**向量召回的内容不会自动判为“过时”**：脚本只标“相关”，读全文后由模型决定。
4. 报告的“分析方法与局限”写明召回的阈值和 k 值。

**要对齐的**：向量检索接口（入参：问题、过滤条件如产品 / 文档类型；出参：doc_id、片段、相似度）、是否能按 `scope_terms` 过滤。

## 第 6 项：引用链（知识图谱）

**解决什么**：有些内容不包含旧值，但依据被修订的条款，例如引用"按条款第 2.3 条执行"的操作指引、由条款派生的培训课件、按等待期配置的系统规则说明。关键词和向量都容易漏掉这些。

**做法**：

1. 起点：被修订文档节点，以及变更涉及的实体（产品、责任、期间、费率表……）。
2. 沿“引用 / 依据 / 派生 / 适用于”关系查一跳、两跳。每条结果带 `"via": "graph"` 和 `"path"`，例如 `条款 v3.0 —依据→ 理赔操作指引 —引用→ 理赔 FAQ`。
3. 模型判断时，把路径作为“它为什么可能受影响”的线索。路径越长，越要读原文确认，不能仅凭关系就判为过时。
4. 报告“受影响内容清单”增加“发现路径”列。处置时按路径顺序改：先改上游，再改下游。

**要对齐的**：图谱里有哪些实体和关系类型、文档节点和 doc_id 怎么对应、查询接口（Cypher / GQL / REST）、关系是人工维护还是抽取出来的（这决定可信度）。

## 第 7 项：经验沉淀入图谱

**解决什么**：jsonl 判例靠术语重合找相似，能用但不够准；判例多了也不好管。

**做法**：

- 判例作为节点：`判例 —关于→ 实体（等待期）`、`判例 —来源→ 文档版本`、`判例 —确认人→ 人员`。
- 查找相似判例：在图上找“关于同一实体或相近实体”的判例，再用向量对判例文本做相似度排序，替代现在的术语打分。
- 状态（active / pending / retired）和确认人原样保留。**仍然只有确认过的判例参与参考**。
- 迁移：`experience.py list --all` 导出的 jsonl 可以直接批量导入。迁移后 `experience.py find` 改为调图谱接口，输出格式不变，工作包和报告都不用动。

## 验收方式

用 `evaluations/cases.md` 里的样例，加上 3-5 份真实修订（脱敏），对比接入前后：

- 召回：人工标注的受影响内容，找到了几篇
- 误报：候选里最后判为 `not_affected` 的比例
- 判断一致性：同一份修订两次运行，结论是否一致
