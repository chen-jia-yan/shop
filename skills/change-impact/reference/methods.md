# 分析方法：怎么判断（给模型看的）

> 这里写的是**思考方法**，不是规则清单。`tap-config/impact.json` 里的类别、权重、下限、处置建议库都是"参考先验"：脚本用它们做初筛，给你一个起点。你要读原文作出判断，可以和初筛不一样、可以超出配置的范围，但要写清依据。
>
> 遇到这里没写到的情况，回到本页第 1 节的四个问题去想，不要因为"没有规则"就跳过。

---

## 1. 核心：每处变更都回答四个问题

| 问题 | 想清楚什么 | 写进 judgments.json |
|---|---|---|
| **它改变了谁的什么权利或义务？** | 客户能不能赔、赔多少、什么时候能退、要做什么；公司要承担什么；一线人员要怎么做 | `summary`（一句话事实）、`direction` |
| **对谁生效？** | 只对生效后的新投保、也对存量保单、还是只是内部管理 | `applies` |
| **不改会出什么事？** | 客户被告知错误口径、错赔 / 拒赔、系统按旧参数运行、监管认定违规 | `reasoning` 里写清后果，据此定 `level` |
| **谁要在什么时候做什么？** | 具体到部门、动作和时限，时限相对生效日计算 | `actions` |

级别（`level`）不是算出来的，而是看"不改的后果有多严重、波及多广"：

- **重大（P0）**：直接改变客户可得的保障或要承担的义务，且对外口径或系统参数必须在生效前改完，否则会产生错赔、拒赔、误导或违规。
- **较大（P1）**：改变保障、费用、期间、核保或理赔规则，但影响面可控，或者有明确的过渡安排。
- **一般（P2）**：流程、时效、材料、职责类调整，内部要更新，对客户的影响有限。
- **轻微（P3）**：不影响任何人怎么做。

初筛给出的分数和下限是参照：你判断得比下限还低，脚本会自动把它列入"待人工确认"，这是正常的，写清理由就行。

## 2. 判断受影响内容：不是"含旧值就是过时"

脚本找出的是**候选**（同一句里出现了旧值或被删除的原文）。每篇候选都要读全文（refs.json 的 `doc_text`），回答：

1. **这篇内容在讲哪个产品、哪个时点的口径？** 另一款产品、历史说明（"原等待期为 90 天"）、案例回顾都不算过时 → `not_affected`。
2. **它的读者是谁、在什么场景下用？** 给存量客户的保全话术、理赔指引，旧条款对他们仍然有效 → `valid_for_existing`，不能直接改成新口径。
3. **整篇过时，还是只有一部分？** → `outdated` / `partly`。
4. **该怎么处置？**（`disposal`）

| 处置 | 什么时候用 |
|---|---|
| `replace` 直接替换 | 只面向新投保 / 新流程，生效后旧口径不再适用 |
| `parallel` 新旧并列 | 新旧客户都会看到，写明"x 年 x 月 x 日（含）后投保的适用……，此前投保的按原合同约定" |
| `switch_on_date` 生效日切换 | 生效前旧口径仍然正确；建议稿先备好，到生效日再上线（写 `switch_date`） |
| `annotate` 加注说明 | 内容本身没错，但读者容易混淆，加一句提示 |
| `retire` 下线 | 内容整体失去意义（如已删除责任的专题 FAQ） |
| `keep` 保持不变 | 读过全文，确认不受影响 |

存量保单是保险最容易出错的地方：**条款修订一般只对新契约生效，存量保单按原合同约定执行**（具体以合规意见为准）。判断不了时写 `needs_review`，交给人。

## 3. 写修订建议稿

每篇需要改的内容，逐句写"原文 → 建议改为"（`revisions`）：

- `original` 从该内容里**逐字**摘原句（脚本会核对，摘不到就报错）。
- `proposed` 只能用新旧条款和该内容原文里已有的事实，**不新增数字、日期、承诺**（脚本会核对数值和日期，也会做合规禁用词检查）。
- 保持原内容的语气和读者：FAQ 还是问答体，话术还是口语。
- 新旧并列时把两种情况都写全，不要只写新口径。
- 改不了、或需要业务补信息的，写 `【待补充：…】`，不要编。

## 4. 比对结果本身要复核（review_flags）

比对算法有已知盲区，脚本会在可疑处打上复核提示，你读原文后把结论写进 `diff_review`：

| 提示 | 可能的情况 | 怎么处理 |
|---|---|---|
| 段落拆分 / 合并 | 一段拆成两段，被识别为"修改 + 新增" | 内容没变的，把新增那条判为 `merged`（`merge_into` 指向主条）；真有新内容的照常判断 |
| 同义改写 | "不予赔付"→"不承担给付责任"被当成否定词变化 | 语义等价就判为 `wording`，写明"语义等价" |
| 表格列结构变化 | 增删一列，整表每行都"变了" | 找出真正变化的值，其余行判为 `wording` 或 `merged` |
| 图片、公式、扫描页 | 没参与比对 | 有原件就自己看，看不到的在报告里写明"未比对"，不能当作没变化 |

也要反过来看：**被判为措辞调整的，有没有其实是实质变更的**（"或"改"且"、"30 日内"改"30 个工作日内"、标点改变了并列关系）。发现了就把 `verdict` 写成 `substantive`。

## 5. 用好判例和检索

- **参考判例**（工作包里列出，来自 `experience/cases.jsonl`）：先看情况是否真相似（产品、条款、对谁生效）。相似就借鉴，在 `precedents` 里写编号；不相似就说明哪里不同。判例不是规则，不机械套用。
- **补查**：关键词没匹配上，不等于没有影响。用工作包里的检索语句，加上同义说法（"观察期"之于"等待期"）、口语问法（"多久能赔"），到 TAP 的检索里再查一遍。语义检索、知识图谱的结果同样存成 JSON 用 `--corpus` 加入。
- **回测问题**：每条重大 / 较大变更写 1-2 个，站在客户或一线人员的角度问旧口径（"xx 产品等待期多少天？"），写明答案里应出现的新口径（`expect`）和不应出现的旧口径（`reject`），处置完成后用来核验。

## 6. 置信度与"不知道"

- `confidence`：high（原文清楚、没有歧义）/ medium（需要一点推断）/ low（原文有歧义或缺信息）。低置信会自动列入待人工确认。
- 看不到原文、缺旧版、语料不全：直接说缺什么，不要用推测填空。"没有查"不能写成"没有影响"。

## 7. 沉淀经验

判断过程中发现了值得以后参考的东西，写进 `lesson`（针对某一条）或顶层 `lessons`（通用方法）。比如：

- "宽限期条款只是编号顺延时，宽限期天数没变，不需要通知渠道。"
- "理赔时效缩短对客户有利，但理赔操作指引里的旧时效会被客服引用，要和系统参数同日切换。"

经业务或合规负责人确认后，用 `experience.py add --confirmed-by` 入库，下次遇到相似变更自动作为参考判例出现。**这就是"维护"的方式：沉淀判例，而不是补规则。**

## judgments.json 格式

```json
{
  "analyst": "分析人",
  "changes": {
    "C04": {
      "verdict": "substantive",
      "summary": "等待期由 90 天调整为 30 天",
      "level": "P0",
      "category": "重要期间",
      "direction": "favorable",
      "applies": "new",
      "reasoning": "等待期缩短，30-90 天内确诊的客户由不赔变为可赔；FAQ、说明书、话术都写着 90 天，生效后仍按旧口径答复会导致误导和错误拒赔。",
      "evidence": [{"side": "old", "quote": "等待期为 90 天"}, {"side": "new", "quote": "等待期为 30 天"}],
      "confidence": "high",
      "actions": [{"action": "核心系统等待期参数改为 30 天并回归测试", "owner": "信息技术部", "offset": -10}],
      "comment": "建议精算部评估对早期理赔率的影响。",
      "precedents": ["EXP-0002"],
      "diff_review": "",
      "lesson": "",
      "confirmed_by": ""
    }
  },
  "refs": {
    "KB-FAQ-0102": {
      "changes": ["C04"],
      "verdict": "partly",
      "applies": "all",
      "disposal": "parallel",
      "reasoning": "FAQ 面向全部客户，存量保单仍按 90 天，需新旧并列。",
      "evidence": ["等待期为 90 天"],
      "revisions": [{"original": "答：等待期为 90 天，等待期内确诊重大疾病的不承担保险责任，无息退还已交保险费", "proposed": "答：新版条款生效后投保的，等待期为 30 天；此前投保的，等待期按原合同约定为 90 天。等待期内确诊重大疾病的不承担保险责任，无息退还已交保险费"}],
      "confidence": "high"
    }
  },
  "verify_questions": [
    {"change_id": "C04", "question": "示例重大疾病保险的等待期是多少天？", "expect": ["30 天"], "reject": ["等待期为 90 天"]}
  ],
  "lessons": []
}
```

| 字段 | 取值 |
|---|---|
| `verdict`（变更） | substantive 实质 / wording 措辞 / merged 并入其他条（配 `merge_into`）/ ignore 排除 |
| `level` | P0 / P1 / P2 / P3 |
| `category` | 可写配置里的类别 key 或中文名，也可以写新类别（会列入待人工确认） |
| `direction` | favorable / unfavorable / mixed / neutral / unclear |
| `applies` | new / existing / all / internal / unclear |
| `verdict`（内容） | outdated / partly / valid_for_existing / needs_review / not_affected |
| `disposal` | replace / parallel / switch_on_date / annotate / retire / keep |
| `confirmed_by` | 人工确认后由确认人填写；填了才从"待人工确认"清单移出 |
