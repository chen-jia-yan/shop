# 变更影响分析

目标是回答管理层和执行人最关心的四个问题，并且每个结论都能追溯到原文：

1. **改了什么** —— 逐条列出，数值写“由 A 调整为 B”，不漏、不重复、不把措辞调整当成实质变更。
2. **有多严重** —— 每条给出重要度、影响度、综合分和级别（重大 / 较大 / 一般 / 轻微），并写明加分依据。
3. **影响到哪里** —— 知识库里哪些内容还写着旧口径（疑似过时），哪些需要人工复核（相关），对客材料、系统参数、培训话术是否受影响。
4. **谁在什么时候做什么** —— 处置事项、责任部门、完成时限，可直接分派跟踪。

脚本负责“不漏”和“口径一致”，你负责“判断对”：**脚本的评分只是初筛，每条重大 / 较大变更都必须由你读原文确认。**

```
① 明确范围 → 分析卡片
② 取得两个版本 → 旧版、新版文件 + 版本信息
③ 比对 → changes.json
④ 查影响范围 → refs.json（本地语料 + TAP 检索补查）
⑤ 人工复核 → notes.json（改级别、改类别、补意见、排除误报）
⑥ 评分定级 → scored.json
⑦ 生成报告与跟踪表 → .docx + .xlsx
⑧ 质检交付 → 质检报告 + 交付说明
```

脚本在 `scripts/`，配置在 `../tap-config/`（找不到时设置环境变量 `TAP_CONFIG_HOME`）。所有命令都支持
`--config 额外配置.json`、`--font-cn` 等覆盖项，见 `../tap-config/README.md`。

## ① 明确范围 → 分析卡片

从用户的话里判断下面几项，**能推断的不问**，只问会明显改变结论的，一次最多 3 个：

| 项 | 说明 | 没给时 |
|---|---|---|
| 被修订的文档 | 名称、类型（条款 / 制度 / 规则 / 话术…） | 必须明确 |
| 新旧版本 | 版本号或发布日期 | 新版取最新，旧版取上一个生效版本 |
| 生效日期 | 决定紧迫度和处置时限 | 报告里标【待补充】，时限按 `default_window_days` 估算并注明 |
| 变更来源 | 监管新规 / 产品修订 / 内部制度调整 | 可不写 |
| 影响范围 | 只看本产品，还是全公司知识库 | 用文档里的产品名 / 制度名作 `--scope-term` |
| 读者与用途 | 上报管理层（brief）还是执行落地（full） | full |

输出分析卡片（简短展示即可，不必等确认）：

```
📋 分析卡片
文档：《xx 产品条款》｜v2.3 → v3.0｜生效：【待补充】｜来源：产品条款修订
范围：本产品相关内容｜版本：完整版（含附录与签批）
```

## ② 取得两个版本

- 在 TAP 中按文档名查元数据（MySQL 文档表：文档 ID、版本号、状态、生效日期、负责人、文件地址），取新版和上一个**已生效**版本。字段名以实际库表为准，查询方式见 `reference/impact-search.md`。
- 支持 .docx / .md / .txt / .pdf / kb-to-word 内容 JSON。PDF 需要 pdfplumber，扫描件需先 OCR。
- 两个版本格式不同也可以比对（如旧版 PDF、新版 docx），但标题层级可能识别不一致，比对后要抽查“移动”类变更。
- **拿不到旧版时不要凭记忆写旧内容**，明确告诉用户缺什么。

## ③ 比对

```bash
python scripts/diff_docs.py 旧版.docx 新版.docx -o work/changes.json \
  --doc-name "xx产品条款" --old-label "v2.3（2025-03）" --new-label "v3.0（2026-01）" \
  --effective-date 2026-01-01 --source "产品条款修订"
```

算法：按全文顺序对齐 → 不同区间按相似度配对（同条款号加分）→ 跨区间二次配对找“移动” → 字词级差异 → 识别信号（数值、日期、义务表述、否定词、适用范围、术语）→ 标记措辞调整。详见 `reference/change-taxonomy.md`。

比对完先看输出的统计：

- **变更数异常多**（超过总块数的一半）：多半是两个版本格式差异太大或标题识别失败，检查后再继续。
- **某条重要条款没有出现**：先确认它是不是被识别成了“删除 + 新增”或“移动并修改”。
- **表格**按行比对；合并单元格、跨页表格容易误报，要抽查。

## ④ 查影响范围

```bash
python scripts/find_refs.py work/changes.json --corpus 知识库导出.jsonl -o work/refs.json \
  --scope-term "xx产品" --exclude "xx产品条款"
```

- `--corpus` 可以是 TAP 导出的 jsonl / json / csv、Retrieval 或 qa_advance 的结果 JSON，或一个文档目录，可写多次。
- **一定要 `--exclude` 被修订的文档本身**（新旧版都排除），否则它会把自己算作“过时内容”。
- 没有本地语料时，脚本仍会为每条实质变更生成检索语句（refs.json 的 `queries`）。逐条用 TAP Retrieval 检索（重大 / 较大的再用 qa_advance 问一遍），把结果存成 JSON，用 `--corpus` 再跑一次。做法见 `reference/impact-search.md`。
- 匹配规则：同一句里同时出现“上下文词 + 旧值”且没有新值 → **疑似过时**；出现被删除的原文短语 → **疑似过时**；只出现相关术语 → **相关**。

## ⑤ 人工复核 → notes.json（关键步骤，不能跳过）

先不带 notes 跑一次评分，看初筛结果：

```bash
python scripts/score.py work/changes.json --refs work/refs.json -o work/scored.json
```

然后**逐条阅读**下面这些变更的修订前后原文（`changes.json` 里的 `old.text` / `new.text`），把判断写进 notes.json：

| 必看 | 要判断什么 |
|---|---|
| 所有重大 / 较大 | 级别是否合理；类别是否认对；“变化说明”是否准确；处置事项是否完整 |
| 含否定词变化的 | 是否真的含义反转（“不承担”→“承担”），还是只是句式调整 |
| 义务表述变化的 | “应当”→“可以”是放宽，“可以”→“必须”是收紧，对客户是利是弊 |
| 删除类 | 是真的取消了，还是挪到了别处（看是否有对应的新增） |
| 疑似过时内容 | 抽查证据句，排除同名不同义（如另一款产品的“90 天”） |
| 被评为轻微、但你觉得重要的 | 例如只改一个字但改变了责任范围（“或”→“且”） |

notes.json 的完整格式见 `reference/report-guide.md`，常用：

```json
{
  "overrides": {
    "C03": {"level": "P0", "reason": "等待期缩短直接扩大赔付责任，需报备", "comment": "建议同步评估定价影响"},
    "C07": {"ignore": true, "reason": "仅为条款编号顺延，内容未变"}
  },
  "summary": "（可选）自己写的结论摘要，不写则自动生成",
  "notice": "（可选）对客告知要求",
  "owners": {"产品部": "张三"}
}
```

**调整级别或忽略某条必须写 reason**，报告会保留“人工调整：原因（自动评级为 x）”的痕迹，评分脚本会拒绝没写原因的调整。

复核后带 notes 重新评分：

```bash
python scripts/score.py work/changes.json --refs work/refs.json --notes work/notes.json -o work/scored.json
```

## ⑥ 评分口径（了解即可，调整去改配置）

- 重要度 = 类别权重（多类别取最高）+ 信号加分；只改措辞时设上限。
- 影响度 = 过时内容数、相关内容数（各有封顶）+ 是否对客 + 是否涉及系统参数 + 距生效日的紧迫度。
- 综合分 = 重要度 × 0.55 + 影响度 × 0.45（权重在 `rules.json`），按阈值定级；高风险情形设级别下限。
- 类别、关键词、加分点、下限、处置建议库都在 `tap-config/impact.json`，详见 `reference/scoring.md`。

**不要为了让结果“好看”去改配置**。某个产品线的口径确实不同，用 `--config` 叠加一个专门的配置文件，并在报告的数据来源里写明。

## ⑦ 生成报告与跟踪表

```bash
python scripts/build_report.py work/scored.json --notes work/notes.json --out-dir out/ --render
# 发管理层的精简版：--variant brief（只含摘要、概览、重大/较大变更、处置计划、合规告知）
```

生成：
- `<名称>_报告内容.json` / `<名称>_跟踪表内容.json`：可以人工微调后再用 kb-to-word / kb-to-excel 渲染
- `<名称>.docx`：分析报告（默认 premium 风格，可 `--style` 指定）
- `<名称>_跟踪表.xlsx`：变更清单（级别条件着色）、处置跟踪（甘特与逾期预警）、受影响内容（逐条销项）
- `<名称>_质检报告.md`

报告结构（完整版）：

| 章节 | 内容 |
|---|---|
| 结论摘要 | 一段话结论 + 4 个指标卡 + 需要优先关注 + 重大变更提示 |
| 变更概览 | 级别分布图、类别分布图、全部实质变更一览表 |
| 重点变更逐条分析 | 修订前 / 修订后对照（变化处加粗）、变化说明、评级依据、受影响对象、受影响内容、建议处置、分析意见 |
| 影响范围 | 重要度 × 影响度四象限、受影响内容清单（按文档合并）、待补查的检索语句 |
| 处置计划 | 时间轴（分析 → 各到期节点 → 生效）、事项表、各级别处置要求 |
| 合规与对客告知 | 报备、客户告知、对客材料、培训、旧内容下线 5 项核对 |
| 附录 | 措辞类修订、全部变更明细、分析方法与口径、数据来源、签批栏 |

## ⑧ 质检交付

`--render` 会自动跑 Word 质检。交付前再按 `reference/quality-rubric.md` 自查，至少确认：

- [ ] 每条重大 / 较大变更你都读过原文，变化说明与原文一致
- [ ] 数值写成“由 A 调整为 B”，单位、口径与原文一致
- [ ] 没有把被修订文档本身算进受影响内容
- [ ] 【待补充】都是确实缺的信息（生效日期、负责人等），并在交付说明里列出
- [ ] 人工调整都写了原因
- [ ] 对外引用（如报备、告知客户）的结论已注明“以合规部确认为准”

交付说明（在对话里）：

```
✅ 已生成《xx产品条款》变更影响分析报告（12 页）与处置跟踪表
实质变更 9 项：重大 2、较大 3、一般 4；知识库疑似过时 6 处、需复核 11 处
最需要关注：C03 等待期由 90 天调整为 30 天（重大）……
待补充：生效日期、理赔部负责人
人工调整 2 处：C03 升为重大（原因…）；C07 排除（原因…）
```

## 写作要求

- **变化说明写事实，不写评价**：“等待期由 90 天调整为 30 天”，不写“大幅优化了等待期”。
- **影响写到具体对象**：“产品说明书第 3 页、理赔 FAQ 第 12 条、核心系统等待期参数”，不写“相关材料”。
- **处置写成可执行的动作**：动词 + 对象 + 时限，“生效前 15 天完成理赔 FAQ 修订”，不写“加强关注”。
- **不确定就说不确定**：缺旧版、语料不全、检索没查到，都在报告里写明，不能用“未发现影响”代替“没有查”。
- 对外口径、监管要求只写知识库里有依据的，没有依据的写成待合规确认的问题。
