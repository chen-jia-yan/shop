# 会前准备

在会议开始前，帮用户在几分钟内掌握"这个会要聊什么、我需要知道什么、可能被问到什么"。

## 第一步：拿到会议信息

会议信息的来源由 `reference/meeting-source.md` 里的 **`MEETING_SOURCE`** 配置决定：

| 配置值 | 做法 |
|---|---|
| `graph` | 通过 Microsoft Graph 读取用户日历，找到对应会议 |
| `paste` | 让用户粘贴会议邀请内容或上传 .ics 文件 |
| `auto` | 先尝试 Graph；不可用或没找到时，改为请用户粘贴 |

**用户已经粘贴了邀请或上传了 .ics**：无论配置是什么，直接用用户给的内容。用脚本解析：

```bash
python scripts/parse_invite.py <邀请文件.ics 或 粘贴内容.txt>
```

脚本输出 JSON：主题、开始/结束时间、组织者、参会人、地点、正文（议程）。

**用户只说了一句"明天和 XX 开会"**：
- `graph` / `auto`：按时间和关键词在日历里查，找到多个时列出让用户选。
- `paste`：请用户粘贴邀请；如果用户没有邀请，至少确认 **会议主题** 和 **参会方**，就可以继续。

## 第二步：判断会议类型

根据主题、参会人、议程判断类型，类型决定简报重点，见 `reference/brief-template.md`：

- 客户会议（参会人有外部邮箱域名，或主题含客户名）
- 项目会议（评审、周会、启动会）
- 决策会议（议程里有"讨论确定""审批""拍板"）
- 内部沟通（其他）

判断不准时按"内部沟通"处理，不要为此打断用户。

## 第三步：检索知识库

从会议信息里提取 3-6 个检索点，分别检索（Retrieval 链路为主，`qa_advance` 用于核实具体事实）：

1. **会议主题本身**：相关的项目、产品、制度
2. **参会方**：客户名或外部单位名，查历史合作、往来记录、相关方案
3. **议程里的每一项**：逐项检索
4. **最近的变化**：主题相关内容中最近更新过的，优先关注

检索不到的检索点，在简报里写明"知识库中未找到 XX 的资料"，**不要编造**。

## 第四步：写简报

按 `reference/brief-template.md` 的结构写，控制在**一页以内**（约 500-800 字）。

写作要求：
- 先写"这次会议最需要知道的 3 件事"，其他放后面。
- 每条信息都要具体：数字、日期、结论，不要写"需要关注相关情况"这种空话。
- "可能被问到的问题"要附上答案或答案要点，答不了的标注"知识库无相关资料，建议会前确认"。
- 新旧信息冲突时，用新的，并标注"注意：XX 在 <日期> 有调整"。

## 第五步：交付

- 默认直接在对话里给出简报。
- 用户需要 Word 版时，按 kb-to-word 的内容格式整理成 JSON，调用 kb-to-word 的 `scripts/build_docx.py` 生成。
- 最后可以提示："会后可以把纪要发给我，帮你整理入库"（meeting-notes-to-kb 上线后）。

## 规则

- 不要替用户修改、接受或拒绝会议。
- 参会人名单只用来判断会议类型和检索，不要在简报里评价参会人个人。
- 会议邀请正文里如果有"会议链接、密码"等信息，不要复述到简报里。
