# 入库规则

## 分类清单

> ⚠️ 待补充：TAP 现有的知识分类。新文件只能放进已有分类，不要自己新建分类（需要新分类的，告诉用户联系管理员）。

```
人事
财务
行政
IT
产品
项目/<项目名>
制度
<其他分类……>
```

## 适合入库吗

| 情况 | 处理 |
|---|---|
| 正式发布的制度、流程、规范、手册、产品资料、培训材料 | 正常入库 |
| 草稿、未定稿、个人笔记 | 提醒用户：建议定稿后再入库 |
| 时效很短的内容（某周值班表、某次活动通知） | 确认是否需要入库；需要的话设置有效期 |
| 内容不足 100 字、或大部分是图片 | 提醒用户：入库后很难被检索到 |
| 涉及个人隐私或保密信息 | 默认去掉，确认后才保留；保密文件建议走专门的权限设置 |

## 摘要

3-5 句，依次回答：
1. 这是什么文件（类型 + 主题）
2. 主要讲了什么（2-3 个要点，带具体信息）
3. 适用于谁
4. 什么时候生效 / 有效期（文件里有才写）

例：
> 《差旅费报销规定》（2026 版）规定了员工出差费用的报销标准和流程。报销须在出差结束后 15 个工作日内提交，一线城市住宿上限每晚 600 元，支持电子发票。适用于全体正式员工及劳务派遣人员。

## 标签

3-8 个，分三类：
- **主题词**：差旅、报销、住宿标准
- **适用对象**：全体员工、财务人员、部门负责人
- **其他叫法**：出差报销、报差旅费（从 qa_advance 日志或常见说法里来，帮助用户用不同说法也能检索到）

不要用太宽的标签（"制度""文件""公司"）。

## 拆分

脚本已经按章节拆好，检查一下：
- 一个片段只讲一件事；过长的（超过 1500 字）脚本已切开
- 每个片段都带着所在的章节标题，单独拿出来也能看懂
- 表格不要被拆开（脚本按整张表处理）

## 敏感信息

脚本会标出疑似的：手机号、身份证号、银行卡号、邮箱、薪酬/绩效相关词。逐个向用户确认：
- 制度里的部门联系邮箱、公开电话：通常可以保留
- 个人手机号、身份证号、银行卡号、具体人员的薪酬绩效：默认去掉
