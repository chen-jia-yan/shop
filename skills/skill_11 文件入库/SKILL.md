# 文件入库

把一份文件变成知识库里**好检索、不重复、有归属**的内容。和会议纪要入库一样：**提交后进入审核，审核通过才对其他人可见。**

## 流程

### 1. 提取内容

```bash
python scripts/extract_file.py <文件> --out /tmp/ingest/
```

支持格式和依赖：

| 格式 | 依赖 |
|---|---|
| .docx | python-docx |
| .pptx | python-pptx |
| .xlsx | openpyxl |
| .pdf | pypdf（`pip install pypdf`）；扫描件没有文字层，需要先 OCR |
| .txt / .md / .csv | 无 |

脚本输出：
- `content.md`：按标题/页/工作表组织的全文
- `chunks.json`：按章节拆分的片段（每段 300-1500 字，保留所在章节标题）
- `meta.json`：文件名、格式、页数/工作表数、字数、提取时的警告（如"第 3 页没有文字，可能是图片"）

`.doc` / `.ppt` / `.xls` 旧格式：请用户另存为新格式。

### 2. 检查文件是否适合入库

按 `reference/ingest-rules.md` 检查，有以下情况先告诉用户：
- **内容过少**（不足 100 字）或大部分是图片
- **含敏感信息**（脚本会标出疑似手机号、身份证号、银行卡号、薪酬等）：问用户是否去掉
- **是草稿或个人文件**（如文件名含"草稿""个人""temp"，或内容明显未完成）
- **时效性很强**（如某一周的值班表）：确认是否真的需要入库

### 3. 查重和冲突

拿文件标题和 2-3 个核心片段去知识库检索（Retrieval 链路）：

| 结果 | 处理 |
|---|---|
| 已有同名或内容基本一致的文档 | 告诉用户，建议**更新已有文档**而不是新增 |
| 已有同主题文档，但规定不一致 | 列出冲突点；建议先确认哪个是现行的，必要时用 change-impact 分析 |
| 没有相似文档 | 正常新增 |

### 4. 生成入库信息

按 `reference/ingest-rules.md` 生成，保存为 `/tmp/ingest/submission.json`：

- **标题**：用文件里的正式标题；没有就根据内容拟一个，不用文件名里的"终版v3"之类
- **摘要**：3-5 句，写清楚这份文件讲什么、适用于谁、什么时候生效（有的话）
- **分类**：从 TAP 现有分类中选（见 `reference/ingest-rules.md` 的分类清单）；拿不准给 2 个候选让用户选
- **标签**：3-8 个，包括主题词、适用对象、**用户可能用的其他叫法**（帮助检索，比如"差旅报销"加"出差报销""报差旅费"）
- **生效日期 / 有效期**：文件里写了才填
- **负责人**：默认是上传人，用户可以改

### 5. 用户确认

展示：标题、摘要、分类、标签、拆分出的章节列表、查重结果、敏感信息处理。**用户明确确认前不提交。**

### 6. 提交审核

```bash
python scripts/build_ingest.py /tmp/ingest/submission.json --chunks /tmp/ingest/chunks.json --out /tmp/outputs/
```

按 `reference/submission.md` 的 **`SUBMIT_MODE`** 提交（与 meeting-notes-to-kb 共用同一套配置和接口）：
- `api`：提交到审核队列，状态为待审核，记下提交编号；接口失败时改为生成文件
- `file`：把生成的文件交给用户，告诉用户在哪里上传

### 7. 告诉用户结果

- 提交成功（或文件已生成），状态：**待审核**
- 标题、分类、标签
- 如果是"更新已有文档"，提醒用户在提交说明里写清改了什么

## 规则

- 不改写文件的实质内容。摘要和标签是新增的，正文按原文入库。
- 敏感信息默认不入库，用户确认后才保留。
- 不覆盖已有文档；更新已有文档也要走审核。
- 一次上传多个文件时，逐个处理，最后汇总；每个文件都要用户确认。
