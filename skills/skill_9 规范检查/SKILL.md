# 规范检查

用知识库里的公司规范检查用户的文档，结果要**每一条都能说清依据**，用户拿到就能改。

## 流程

### 1. 读取文档

- **Word（.docx）**：用脚本按段落编号提取，后面批注要用到编号：
  ```bash
  python scripts/extract_docx.py <文件>.docx > /tmp/paras.json
  ```
- **PDF 或其他格式**：提取文字后检查，只输出问题清单，不做原文批注。告诉用户："如果需要直接在原文上批注，请提供 Word 版。"
- `.doc` 旧格式：请用户另存为 .docx。

### 2. 判断文档类型，确认检查范围

根据内容判断类型：**合同 / 方案 / 制度文件 / 其他**。每类的检查重点见 `reference/doc-type-checklists.md`。

用户没指定对照哪份规范时，不要追问，按类型自动检索；用户指定了（"对照 XX 模板"），以用户指定的为准。

### 3. 检索适用的规范

按 `doc-type-checklists.md` 里该类型的"要检索的规范"逐项检索（Retrieval 为主，`qa_advance` 核实具体条款）。

- 记下每条规范的**名称和版本/更新时间**，后面每个问题都要写依据。
- 同一事项有新旧两版规范时，用新版，并在报告里提示。
- **检索不到某类规范时**，这部分不做判断，在报告里写"知识库中未找到 XX 规范，此项未检查"。不要用通用常识代替公司规范来判定"不合规"。

### 4. 逐条检查

对照规范检查文档，每发现一个问题，记录：

| 字段 | 说明 |
|---|---|
| `para` | 问题所在段落编号（来自 extract_docx 输出） |
| `quote` | 原文中有问题的那句话（原样摘录，方便定位） |
| `level` | `必须修改` / `建议修改` / `提示`（定义见下） |
| `issue` | 问题是什么，一句话 |
| `rule` | 依据：规范名称 + 具体条款 |
| `suggestion` | 怎么改；能给出改后文字的，直接给 |

**等级定义：**
- **必须修改**：违反了规范中的强制要求（"必须""不得""应当"），或缺少规范要求的必备内容
- **建议修改**：不违反强制要求，但与模板或推荐写法不一致，可能带来风险或歧义
- **提示**：需要用户自己判断或向相关部门确认的事项（比如金额是否在授权范围内）

缺失类问题（文档里应有但没有的内容），`para` 写离它最近的相关段落；整篇都没有的，写 `0`（放在文档开头）。

把结果保存为 `/tmp/issues.json`，格式见 `examples/issues.json`。

### 5. 生成批注版文档（Word）

```bash
python scripts/annotate_docx.py <原文件>.docx /tmp/issues.json /tmp/outputs/<原文件名>_检查意见.docx
```

- 批注加在对应段落上，批注里写明等级、问题、依据、建议。
- 运行环境里的 python-docx 版本较旧、不支持批注时，脚本会自动改为在段落后插入红色的【检查意见】文字，并在输出里说明。
- 原文件不会被修改。

### 6. 交付

在对话里给出检查结论，结构：

```
**结论**：<一句话：可以使用 / 修改后可使用 / 问题较多建议重写>
必须修改 X 条，建议修改 Y 条，提示 Z 条

**必须修改**
1. 第 N 段「原文摘录」：问题。依据：规范名 第 X 条。建议：……

**建议修改**
……

**提示**
……

**未检查的项**（知识库中缺少对应规范）
……
```

附上批注版文档。必须修改的问题一条不漏地列出；建议修改和提示超过 10 条时，对话里只列前 10 条，其余看批注。

## 规则

- **每个问题都要有依据**。说不出依据的，最多算"提示"，不能算"必须修改"。
- 只查规范问题。错别字、标点等文字问题合并成一条"提示"，不逐个列出（用户要求时除外）。
- 不替用户做业务判断（比如"这个价格太低了"），涉及商务、法律判断的，用"提示"建议用户向相关部门确认。
- 检查结论只是辅助，合同类文档在交付时加一句："正式签署前请按公司流程走法务审核。"
