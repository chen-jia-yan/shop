图谱是从哪些文档来的？

图谱不是凭空生成的——它是从一批源文档里"读"出来的。这些文档登记在入库库 state.db 的 files 表里（当前 239 份，多为业务设计 / 系统说明的 .pptx 教材）。例如：

#01_当社システムの全体概要.pptx #02_OPEN系基礎.pptx #06_新契約システム概要.pptx #15_SFDC.pptx … 共 239 份

每份文档 → 算内容指纹(sha256) → 得 doc_id = doc:: + 指纹前16位 → 切成若干 chunk → 从 chunk 抽取实体与关系。所以图谱里每个节点和边都带 source_docs 标签，记着"我是从哪几份文档来的"——删文档时就靠它做引用计数。

⚠ 要对领导讲清的一点：当前这版图谱是在语料改版前构建的（约 145 份文档的量），和现在的 239 份不完全同步。本增量流程正是用来把缺的补进去、把变的更新掉，让图谱追上语料。

怎么存储 · 怎么操作

▶ 展开

存在哪：SQLite 本地库 kg.db

表存什么
kg_nodes所有节点（实体 + 切片）：id、类型、名称
kg_edges所有边：谁→谁、什么关系
kg_node_sources节点来源标签：一行=“这节点来自这文档”。引用计数就是数这里行数
kg_edge_sources边的来源标签，同上
kg_changelog每次变更流水 + 可回滚 delta + 状态（committed / rolled_back）
kg_meta版本号、最新序号等元信息

查"文件↔节点"时，只读挂载 state.db（绝不写它），用 doc_id = 'doc::' + 指纹前16位 关联。换生产只需把这套换成图数据库，上层操作不变。

人怎么操作：预演 → 确认 → 应用 → 可回滚

1--status 看现状：当前版本、节点/边数、健康度
2--pending 看哪些文档还没同步
3--plan 预演：只算不写，给出"会加/删/改什么"
4人工看报告，确认无误（可剔除新实体）
5--apply --confirm 应用：事务写入，落成新版本
6--rollback 出问题一键回退上一版

关键原则：所有写入都先预演、经人工确认、且可回滚；全程不碰检索索引、不删源文件；开关默认关，不启用时系统与现在完全一致。
