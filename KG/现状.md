# 1. 根目录：程序文件
| 文件 | 用途 |
| ---- | ---- |
| `knowledge_graph.py` | **图谱载入与查询核心**。把 JSON 载入内存，提供实体查找、模糊 / 语义匹配、邻居查询、子图展开、实体 → Chunk 来源查找，以及供回答使用的图谱文字。 |
| `embedding_index.py` | **图谱节点的向量索引工具**。将节点名称与邻居资讯组成可搜寻文字，再透过传入的 embedding 函数建立向量；也负责索引保存、载入和相似度搜寻。它不负责抽取新实体或关系。 |
| `kg_extractor.py` | **LLM 实体 / 关系抽取器**。输入带正文的 Chunk，呼叫配置的 LLM，产出实体节点、语义关系与 `mentioned_in` 来源连结。注意：其中的 dry-run 函数仍会呼叫 LLM，只是不写档，**不等于离线或零费用**。 |
| `kg_incremental.py` | **图谱增量管理引擎**。根据 `source_docs` 计算文档新增 / 更新 / 删除造成的变更，支持预览、保存新版本和回退；会读取版本清单、图谱及档案状态资料。 |
| `__init__.py` | **Python 套件入口**。对外汇出 `KnowledgeGraph` 和 `get_default_kg`，方便其他模组引用。 |

> **重要区别：** 目前 `kg_incremental.py` 的单文档子图建构，**没有呼叫上述 LLM 抽取器**。它从现有 KG 找到 Chunk，再用 Chunk 标题 / 位置资讯匹配已有实体。因此，不能把「增量程式」理解成「已能从新文档正文完整抽取新实体与语义关系」。

# 3. 版本管理目录
`kg_versions` 里面的文件：

| 文件 | 用途 |
| ---- | ---- |
| `kg_backfill_provenance.py` | **来源回填工具**。读取原图谱与状态库的档案 hash，生成文件 → `doc:id` 映射，再给节点 / 边补 `source_docs`；预设输出预览，明确 apply 才建立正式新档。 |
| `business_kg_enriched.provenance.json` | **补过来源资讯的图谱**。目前也是增量引擎的基线，以及预查询载入器优先考虑的资料。 |
| `business_kg_enriched.source_file_to_doc.json` | **文件名 → doc:id 映射结果**。包含 `source_file_to_doc_id` 和未解决来源清单；不是图谱。 |
| `manifest.json` | **版本指针与历史清单**。记录目前 active 版本、父版本、操作及变更摘要。目前文件的 `active` 是 **v2**。 |
| `v1.json` | **第一个版本快照文件**，保存该版本的图谱。 |
| `v2.json` | **第二个版本快照文件**，目前被 manifest 指向。 |
| `KG增量_调研.md` | **阶段0的历史调研报告**。你之前问的这份文件目前就在这里；其中「未找到抽取器」等结论是当时状态，不代表现在仍没有。 |
| `__init__.py` | Python 套件标记，内容只有简短说明，没有操作逻辑。 |

> 注意：**manifest 指向 v2，不代表正在运行的 Agent 必然使用 v2。** 还取决于版本开关和进程中已读取的图谱。

# 6. Python 快取
两个「根目录快取」、「版本目录快取」里的 `.cpython-312.pyc`，都是对应 Python 模组自动生成的编译快取：
- 不保存图谱资料。
- 不需要手动编辑。
- 不是另一套业务程式。

# 现在到底优先读哪份图谱？
根据目前「载入程式」：
1. **版本开关开启**且 active 文件存在：优先载入 manifest 指定版本，目前为 v2。
2. 否则先尝试 **上一层的正式 provenance 图谱**。
3. 再尝试原 enriched 图谱。
4. 再尝试基础图谱与其他备选位置。

> **因此，现在已不是「预设一定读原 enriched」的旧状态。** 而且它首次载入后会在进程内快取，不是每次查询都重新读档。
